# Оценка остатка NTSD по объёму исходного кода

Дата оценки: 2026-09-08. Срез: `c2c2c91bcb7ec9bd19fc1013ceab6aa5908e12f2`
(22:39:01, UTC+3). Более поздние изменения работающего агента не учитываются.
Это документ планирования, не новое доказательство соответствия оригиналу и
не изменение исследовательской очереди.

## Рабочий прогноз

**Для планирования: около 250 часов продолжения работы в наблюдаемом режиме;
осторожный сценарий — около 500 часов.** При непрерывной работе это примерно
10–11 и 21 сутки соответственно. При восьми часах в день — 31 и 62 рабочих
дня. Простой оптимистичный сценарий даёт около 130 часов / 5–6 суток.

Числа 250/500 не являются статистическим доверительным интервалом или обещанием
завершить всю игру. Они получены из измеренной скорости увеличения описанных
участков кода, с явно выбранными допущениями ниже. Непокрытые ветви, AI,
реальная сеть и Windows/macOS-проверки могут вывести работу за этот диапазон.
Оснований утверждать верхнюю границу срока сейчас нет.

Ориентир в календарных неделях при круглосуточном продолжении: **около двух
недель, с резервным сценарием около трёх недель**. Округление учитывает бытовую
непрерывность запуска, но не заменяет учёт реальных простоев. Прежние устные
«1–3 месяца» не были расчётом; смешивать их с этим прогнозом нельзя.

Это площадь объединения выбранных адресных диапазонов. Внутри них есть

границей завершённого поведения.

Число проанализированных с пониманием семантики инструкций и число ветвей,
проверенных против Swift, отдельно установить по текущим артефактам нельзя.
Линейное дизассемблирование всех инструкций само по себе не считается анализом
поведения. Суммарные количества тактов, PCM-байтов, объектов и snapshots не
прибавляются к объёму уникального кода.

## Метод отбора

1. Из каждого исторического среза извлекаются Swift-исходники и исследования.
   Рабочие незакоммиченные файлы не читаются как основания расчёта.
2. Учитываются явные диапазоны адресов в комментариях NTSDCore, попадающие
   внутрь `.text`. Отдельные константы и адреса глобальных переменных исключены.
3. Добавляются вручную отобранные положительные описания объёма переноса из
   исследований. Файл соответствующего нативного модуля должен уже существовать,
   а диапазон должен быть написан в документе на соответствующем историческом
   срезе. Общие адресные справочники и разделы «следующая задача» автоматически
   не суммируются.
4. Для восьми функций, описанных как целые тела только по адресу входа,
   добавлены явно перечисленные границы до терминального `ret`: local/remote/
   playback input, panel update, settings loading, menu input, packet read/write.
   Наличие начальной инструкции и терминального `ret` проверяется по EXE.
   У этих восьми историческая дата — наличие исследования и модуля, а не
   отдельное доказательство даты переноса каждой внутренней ветви.
5. Все пересечения убираются побайтным объединением. Повторная ссылка на функцию,
   400 Actor и 137 Object не создают дополнительного объёма кода.
6. Конец диапазона трактуется как включённый адресный маркер. При подсчёте
   инструкций учитываются лишь те, чьи байты полностью лежат внутри объединения.

Дизассемблирование получено `llvm-objdump` из самого EXE. Байты каждой строки
сверены с PE. Количества инструкций четырёх ранее описанных основных функций
совпали с существующим `docs/evidence/tick-address-index.json` из того же коммита.
Сборщик не восстанавливает полный граф потока управления и не предполагает,
что каждая декодированная инструкция достижима: в секции возможны inline data.
Статическая плотность переходов не доказывает сложность алгоритма.

| За последние примерно 6 часов | 1 277 байт в час |

В отличие от числа коммитов, объёмный показатель показывает замедление в
последнем окне. Оно совместимо с ростом доли соединения и перепроверки старых
частей, но по Git нельзя доказать причину. Это также может быть изменением
подробности документации. Прогноз по последнему окну учитывает эффект без
предположения о его причине.

История включает 50 нативных коммитов. Git-интервалы не являются измерением
активных часов агента: в них входят проверки, паузы и прочие работы. Поэтому
«час» прогноза означает час продолжения в сопоставимом режиме. Данные не дают
оснований обещать линейное ускорение при увеличении числа агентов.

## Независимые варианты линейной экстраполяции

Формула: `(весь объём − текущий объём) / наблюдаемый прирост в час`.
Это сопоставление масштабов, не доказательство одинаковой трудоёмкости остатка.

| Основа | Линейный остаток |
| --- | ---: |
| Байты диапазонов, средний темп за 25,9 часа | 86 часов |
| Инструкции внутри тех же диапазонов | 93 часа |
| Условные переходы внутри тех же диапазонов | 143 часа |
| Байты диапазонов, темп последних 5,9 часа | 165 часов |
| Только адресные диапазоны комментариев Swift, без дополнений из документов | 180 часов |

Таким образом, сама метрика даёт **примерно 90–180 часов линейного остатка**.
Это разброс способов подсчёта и временных окон, а не доверительный интервал.
143 часа по переходам показывают, что оценка только по байтам чувствительна
к структуре оставшегося кода. Разница 86/180 часов показывает значимость
неполноты адресных аннотаций.

В знаменателе оставлена вся `.text`. Её служебную, платформенную и возможную
недостижимую часть пока не вычитаем: для этого нужен отдельный полный реестр.
С другой стороны, DLL CRT, устройство macOS и проверка вывода не представлены
этим знаменателем. Эти ошибки действуют в разных направлениях и не считаются
автоматически компенсирующими друг друга.

## Плановые сценарии до конечного результата

Обычные исследования и сравнительные тесты уже входят в наблюдаемое время.
Дополнительно выбран резерв **50%** на соединение с приложением, оставшиеся
внешние адаптеры и итоговую проверку режимов/вывода. Это **плановое допущение**,
а не измеренная длительность этих работ. Если такого резерва не хватит,
прогноз требуется пересмотреть.

| Сценарий | Перенос по модели | С резервом 50% | При 24 ч/сутки | При 8 ч/день |
| --- | ---: | ---: | ---: | ---: |
| Средний исторический темп сохраняется | 86 ч | 129 ч | 5,4 суток | 16 рабочих дней |
| Сохраняется недавний более медленный темп | 165 ч | 248 ч | 10,3 суток | 31 рабочий день |
| Остаток ещё вдвое медленнее недавнего темпа | 331 ч | 496 ч | 20,7 суток | 62 рабочих дня |

Вторую строку выбираем как рабочий ориентир, третью — как риск-сценарий.
Дополнительное замедление вдвое в третьей строке — также предположение,
без приписывания вероятности. Утверждение «всю игру точно закончим за 21 день»
из таблицы не следует. При резерве 100% вместо 50% вторая строка становится
331 часом, третья — 662 часами.

## Что способно существенно изменить прогноз

- Внутри учтённых диапазонов остаются неподдержанные условия. Их реализация
  не даст прироста адресного объёма, но потребует времени.
- Общий полный такт ещё не сравнен: неизвестно, сколько дополнительных
  зависимостей и расхождений появится при соединении боя с новой основой.
- Для захватов, оружия, AI и исключений по ID нет достаточной собственной
  выборки темпа. Плотность ветвлений только частично описывает их сложность.
- Режимы, реальная сеть, файловый жизненный цикл повторов, пиксели, аудиосведение,
  задержки ввода и проверка чистой macOS требуют самостоятельного завершения.
- Полный результат включает сравнение с работающим оригиналом под Windows.
  Доступность и фактическое выполнение этих проверок этим расчётом не установлены.
