# R02.1 — общая подготовка выбранного матча

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.

Участок `42d1ff..42d6ed` внутри меню `429730` перенесён в
[OriginalMatchPreparation](../../native/Sources/NTSDCore/OriginalMatchPreparation.swift).
Это общая подготовка после подтверждения выбора. Она **ещё не доказывает весь
путь меню → начало матча**: пролог режима, формирование выбора, создание повтора
и последующие ветви меню остаются открытыми. Приложение practice не переключено
на новый World; полный игровой такт также ещё не перенесён.

## Происхождение данных

[Стенд](../../tools/oracle_match_preparation.py) восстанавливает точные байты,
маски и адреса из закреплённого полного [каталога](LOADED_CATALOG.md) text/a5.
Проверяются SHA-256 всего capture, всех использованных блоков и исходных
Object/BG/Stage-файлов. В память возвращаются **все** 60 Stage, 101 BG, 137 Object,
таблица каталога, bitmap и живые/старые malloc-записи. Это не синтетические
заголовки и не повторный вызов загрузчиков в придуманном порядке.

Далее исполняются настоящий конструктор World `419e40` и загрузочный пул
`41c052..41c2f5`: 400 аллокаций Actor, 408 вызовов конструктора, связывание с
каталогом[0]. В Native Core тот же полный каталог заново строится исходными
нативными загрузчиками и проверяется прежним сравнением всех загруженных записей;
его результат передаётся bootstrap и подготовке матча. Состояние ресурсов
сохраняется через `OriginalLoadedCatalog.resources`, новые слои добавляются
в существующий bitmap-реестр.

Входы **на границе меню** заданы стендом и сохранены отдельными записями:

- `451288 + 4*seat`: восемь кодов выбора; Object/team в базовых Actor 0–7 и
  флаги активности. Их происхождение из реального меню ещё не восстановлено.
- `ESP+14 = World`, `ESP+1c = pointer-to-mode`, `EBX=0` при входе в `42d1ff`.
  Значение селектора World=2 также подано отдельно.
- `44d024` — индекс арены, `44d028` — флаг случайного выбора. Числовое значение
  mode=1 обозначает исследуемую ветку Stage; для остальных значений фиксируются
  только наблюдаемые условия, без догадок о полном наборе режимов.
- Начальная таблица RNG из исходного повтора, с указанным SHA-256, плюс явно
  заданные index/counter в контрольных случаях. Это не доказательство генерации
  новой таблицы при запуске Windows-игры.
- Остальные globals получены из PE/BSS, восстановленных sound/checksum и
  объявленных входов. Их наличие в снимке **не доказывает реальную историю меню**.
  Для проверки сброса буферы заполняются ненулевыми байтами.

Все случаи одного корпуса выполняются последовательно на одном World и одном
каталоге. Перед очередным запуском меняются только перечисленные `stimulus`;
прошлый результат продолжает жить. Нативный проверяющий код не инициализирует
модель ожидаемым состоянием после подготовки.

| `42d290..42d504` | Сохранить Object/team из базового Actor, выполнить `4061d0`, восстановить ссылки/team, скопировать Object `+90` в Actor `+31c`, установить активность и Actor `+8=75` |
| `42d305..42d504` | Задать x/z через RNG, синхронизировать целые и double-координаты, y=0; `+308=200` либо 500 при mode=1; `+354=номер целевого слота` |
| `42d51d..42d5bc` | Для всех 400 активных Actor с team=0 назначить team=slot+10; ненулевые team сохранить |

| `42d665..42d6ae` | Только mode=1: всем активным Actor с Object type=0 повторно назначить x через RNG `(0xdf,30)+50` |

Геометрия появления берётся из записи выбранной арены:

```text
x = RNG(width / 2) + width / 4
z = RNG(upper - lower) + lower
y = 0
```

Деление signed Int32 округляется к нулю; вычитание/сложение сохраняют wrap32.
Для кода `>10` используются метки RNG `0xdb/0xdc`, для `1..10` — `0xdd/0xde`.
`417170` не использует саму метку как отдельный поток: все вызовы расходуют
одни общие index/counter/table. Метки и их порядок сохранены в свидетельстве.
Stage меняет x после прежних двух вызовов на бойца, **не отменяя их**.

При 17 BG случайный диапазон равен 15: результаты 0–13 выбирают эти записи,
14 превращается в 99. Это не равномерный выбор всех 17 исходных арен.
Прямой выбор остальных арен отдельно проверен. Особый BG99 не проходит
обычную загрузку слоёв; его встроенные bitmap из каталога сохраняются.

Участок не снимает активность базового места при коде `>10` и вообще не
обнуляет первые десять флагов. Нельзя переносить сюда догадку, что он сам
убирает бывших бойцов меню. В контрольных входах это задано явно.

`431c70` обнуляет семь dword `4513a4..4513bc`, восемь dword `451320..45133c`
и семь байт `cd..d3` каждого базового Actor 0–7. Буфер `455378` длиной 300
заполняется **0x75**, а не нулями. Более широкая семантика ввода остаётся R07.

## Сравнение

Два корпуса с одинаковыми 25 последовательными сценариями: заполнение памяти
Actor/World `a5` и возрастающие байты `00..ff`. Каталог в обоих — закреплённый
text/a5. Сценарии включают:

- Наруто/Саске на District и немедленный повтор: старые 15 слоёв освобождаются,
  новые 15 создаются в том же общем реестре.
- Все 137 исходных Object в 18 пакетах по восемь. Это пробы общего механизма
  привязки/копирования, включая объекты с type!=0; **не доступность этих объектов
  в меню**. В игровом коде нет ветвей по именам или ID персонажей.
- Все 17 исходных арен, Stage и ветки mode=0/2; сохранение ненулевых team,
  слотов 8–9, очистку ранее активных 20/399, пропуск type!=0 при Stage-x.
- Коды `1,10,11,Int32.max,0,-1,Int32.min,2`, случайный/прямой BG99, переход
  RNG index 2999→0 и counter 1233→0, пустой выбор.

В release совпали **50 случаев, 52 102 записи, 79 596 336 байт/масок**,
**19 324 вызова конструктора**, **720 RNG-вызовов**, **796 новых bitmap** и
**766 освобождений**. Загрузочные 816 вызовов конструктора двух bootstrap
не входят в число 19 324; их результат сравнивается отдельно в каждом корпусе.

Сравнение включает полные World/400 Actor/101 BG/globals до и после каждого
вызова и после bootstrap, все новые bitmap-записи, порядок реконструкций,
RNG с before/after index/counter, вызовы arena/input/music и порядок
освобождений. Globals сравниваются целиком как заданные PE/host-входы;
маски Actor/BG/bitmap сохраняют разреженное происхождение. Внутренний порядок
каждой отдельной записи памяти и промежуточные координаты внутри подготовки
не являются отдельными контрольными точками этого корпуса.

Стенд дополнительно проверяет неизменность всех исходных Object, прежней кучи,
таблицы Object, Stage и хвоста каталога. Чтений неинициализированной отслеживаемой
памяти нет, защитные области сохранены. Снимки не нормализуются заранее:
проверяющий код заменяет только подтверждённые World/Actor Object-поля на
непустые ordinals и BG bitmap-поля на index+1. Оpaque-байты остаются как есть.

Отчёты: [a5](../evidence/match-preparation.json),
[ramp](../evidence/match-preparation-ramp.json).
Полный `swift test --package-path native` прошёл: **31 тест, 0 ошибок,
398.752 с**. Новый тест двух последовательных корпусов занял 75.717 с;
все прежние тесты загрузчиков и игровой механики также прошли.

## Воспроизведение и границы

```bash
# Предварительно нужен закреплённый build/original/loaded-catalog.json:
# его воспроизведение описано в LOADED_CATALOG.md.
uv run tools/oracle_match_preparation.py
uv run tools/oracle_match_preparation.py --ramp
uv run tools/oracle_match_preparation.py --accept
swift test --package-path native
```

SwiftPM-команды запускать последовательно. `--accept` сначала сравнивает оба
корпуса с нативной загрузкой полного каталога и только после успеха сохраняет
автономные fixtures. Исследовательский код/EXE/Unicorn не являются зависимостями
приложения.

Оригинальные RNG, конструкторы, BG wrappers/load/release и input reset исполняются
инструкциями EXE. `new`, `memset`, surface creation/SetColorKey/Release и `free`
имеют явные host-границы. Аллокатор выдаёт только ненулевые адреса; освобождённые
байты сохраняются для исследования. Пиксели, звук и реальная политика allocator
этим не доказываются.

Музыкальный путь `4025b0` проверен с пустым `44eed0` и отключённой музыкой
`44d010=0`. Enabled-ветка `402020` использует **DirectShow**, а не MCI.
Нативная подготовка явно отклоняет её до фиксации своего состояния; общего
соответствия музыки нет. Ветка непустого пути при выключенной музыке статически
видна и предусмотрена в коде, но в текущих 50 случаях не исполнялась.

Позднейший этап [REPLAY_INITIALIZATION.md](REPLAY_INITIALIZATION.md) уже
продолжает этот путь через настоящий вызов и весь `43d2c0`, включая сброс
счётчика RNG, до `42d704`. Старые два корпуса этого документа не расширены
задним числом. Новая цепочка также проверяет непустой путь музыки при её отключении.

Следующее: восстановить пролог `42cf8a..42d1ff`, происхождение выбранных
Object/team/status/activity и RNG, затем продолжение после `42d704`.
Для воспроизводимого первого матча нужны эти записи и последующий полный такт
