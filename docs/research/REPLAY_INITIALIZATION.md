# R02.1 / R16 — создание буфера записи при запуске боя

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.

Перенесена **целиком функция `43d2c0..43db38`** и освобождение записи через
`43d280`. Она вызывается сразу после [общей подготовки матча](MATCH_PREPARATION.md).
Это необходимый участок запуска боя: в конце он сбрасывает счётчик RNG.
Формат готового файла, запись игровых тактов, воспроизведение, сеть и полный
путь меню пока не восстановлены. Practice на этот новый путь не переключена.

## Выполнение и происхождение

[oracle_replay_initialization.py](../../tools/oracle_replay_initialization.py)
продолжает проверенный полный каталог → World/400 Actor → общую подготовку.
Исполняется настоящий вызов меню `42d6fc`, функция `43d2c0`, возврат в `42d701`
и очистка её трёх аргументов вызывающим кодом; новая остановка — **`42d704`**.
Аргументы проверяются на входе функции: mode, `World+4` (активности),
`World+194` (таблица Actor). Сам вызов не заменён ручной сборкой полей повтора.

Нативный [OriginalReplayRecording](../../native/Sources/NTSDCore/OriginalReplayRecording.swift)
получает результат нативной полной загрузки, bootstrap и подготовки, проверенных
тем же запуском CLI. После каждого `begin` обновлённые globals продолжают жить
в следующем сценарии. [Проверяющий код](../../native/Sources/NTSDReferenceChecks/ReplayInitializationReference.swift)
не начинает следующую модель с ожидаемого снимка оригинала.

Сохранены прежние внешние границы: выбор меню, начальная таблица RNG из
исходного повтора, allocator/device и PE/BSS globals. Дополнительно задаются
байтовые пробы metadata/settings/names. Они перечислены в `replayStimulus`
отдельно от входов общей подготовки. Это **не наблюдение настоящих настроек
или имён игроков в Windows-меню**.

## Исходная последовательность

1. `43d2cc → 43d280`: если `4588a8 != 0`, освободить предыдущий буфер и
   записать в указатель ноль. Соседний `4588ac` этим вызовом не меняется.
2. `43d2d8`: `calloc(1, 0x630e18)` — **6 491 672 нулевых байта**.
   Указатель результата сохраняется в `4588a8`. Исследованы ненулевые результаты
   аллокатора; поведение при нехватке памяти не заявлено.
3. `450b8c=0`, `450b80=1`. Далее копируются mode, metadata, имена, массивы
   состояния 18 Actor, музыка, checksum, настройки и RNG по таблице ниже.
4. `43db19..43db2b`: **`450c34=0`**, также обнуляются `450bd0/450bd4/450bd8`.
   Индекс RNG `450bcc` остаётся тем, который получился после подготовки.

Таким образом, сохраняется таблица и индекс RNG, но **не текущее значение его
счётчика**. Нельзя использовать прежний снимок на `42d6ed` как окончательное
состояние RNG первого игрового такта. В новых последовательных сценариях этот
сброс изменяет результаты следующих подготовок; старые fixtures общей подготовки
сохраняют прежнюю, явно более короткую границу.

## Размещение буфера

Все смещения — относительно результата `calloc`. Неуказанные области также
сравниваются и остаются нулевыми. Названия неизвестных глобальных параметров
не угадываются по их числам.

| Смещение | Источник / содержимое |
| --- | --- |
| `000/004/008/00c` | dword `450c30`, `450b94`, `458428`, `45842c` |
| `148` | Аргумент mode |
| `14c` | Восемь строк из `44fcc0 + seat*11`, шаг назначения также 11 |
| `1a4` | Выбранная арена `44d024` |
| `1a8..54f` | 13 массивов по 18 dword, см. ниже |
| `550` | Строка из `44eed0` |
| `744/748` | Checksum `44f620` и dword `44d03c` |
| `74c..8ab` | Четыре блока по 22 dword из `44d5f8`, `44d650`, `44d6a8`, `44d700` |
| `8c4` | Индекс RNG `450bcc` |
| `8c8..1480` | **Ровно 3001 байт** из `44ff90`, включая байт после таблицы из 3000 элементов |
| `1488..14b3` | 11 dword из `44d324..44d34c` |
| `14b4` | dword `450b90` |
| `630bc0/630c24/630db4` | Строки из `44fd18`, `44f900`, `44f890` соответственно |

Строки копируются побайтно вместе с NUL. Шаг 11 у имён **не является
ограничением strcpy**. Нативный код сохраняет переход через границу имени и
порядок последующих записей; не превращает сырой текст в UTF-8 и не обрезает
его по придуманной длине. Выход за известные source/destination allocations
остаётся за пределами поддержанного нативного домена.

Исходный цикл `43d5c0..43d95d` развёрнут по три Actor, шесть итераций:

| База массива | Поле каждого Actor / World |
| --- | --- |
| `1a8` | Actor `+364`, team |
| `1f0` | **Object `+6f4`, исходный ID**, через Actor `+368`; не registry ordinal |
| `238` | World active byte, **знаковое** расширение до Int32 |
| `280` | Actor `+8` |
| `2c8/310/358` | Actor `+10/+14/+18`, целые координаты |
| `3a0/3e8/430` | Actor `+308/+354/+304` |
| `478/4c0/508` | Actor `+33c/+344/+340` |

Копируются **все 18 слотов, включая неактивные**. Остальные 382 Actor сюда
не экспортируются. Никаких ветвей по имени персонажа или его ID нет.
В нативном буфере эти значения сравниваются без нормализации похожих на адреса
слов: ID и числовые поля должны остаться исходными битами.

## Сравнение и ресурсный цикл

Два корпуса по 25 последовательных подготовок/созданий: a5 и ramp для памяти
Actor/World, один и тот же закреплённый полный text/a5 каталог. Используется
общая последовательность сценариев прежнего стенда: все 137 исходных привязок
Object, все 17 арен, District Naruto/Sasuke и перезапуск, Stage/BG99, граничные
коды выбора, переход RNG через конец таблицы и пустой выбор.

Дополнительные пробы:

- Все 13 экспортируемых массивов: разные старшие биты и значения во всех
  18 слотах. В активности используются `0/1/127/128/255`, чтобы отличить
  знаковое расширение от UInt8→UInt32.
- Пустые строки и строки длиной 1/10/99 байт, байты вне ASCII, имена с NUL
  за пределами номинального шага 11. Проверяется побайтовое копирование.
- Ненулевой байт после таблицы RNG: подтверждает фиксированный размер 3001,
  а не копирование до NUL. Остальные вызовы используют исходную таблицу RNG.
- 24 замены старого буфера и затем два вызова `43d280` на каждом корпусе:
  второй вызов на null ничего не освобождает. Флаги записи не обнуляются
  этим helper; нативный `clear()` также их не меняет.

Release-сравнение подтвердило **50 целых буферов / 324 583 600 байт и масок**,
**50 аллокаций / 50 освобождений**. В связанной подготовке дополнительно
совпали **77 252 записи / 115 486 336 байт и масок**: World/400 Actor/101 BG/
globals до и после подготовки, после создания буфера, bootstrap и новые bitmap.
Полный нативный каталог отдельно заново загружается и проверяется прежде,
чем запускается эта цепочка; его байты не включены в эти два счётчика.

Стенд проверяет, что Replay init не меняет World/Actor/BG, а исходные
Object/Frame/Stage/heap остаются неизменными. Чтений неинициализированной
отслеживаемой памяти нет. Все байты `calloc` имеют доказанное начальное
обнуление; неизвестные байты исходных Actor при экспорте не домысливаются.

Ресурсные адреса в capture настоящие для исследовательского allocator.
Нативная запись хранит optional buffer и логический номер аллокации;
reference явно сопоставляет их с указателем `4588a8`. Соседний playback pointer
в обоих корпусах исходно нулевой и остаётся нулевым; воспроизведение не проверено.
Память после `free` удерживается только в стенде для проверки защитных областей,
это не утверждение о содержимом реального освобождённого блока Windows.

Отчёты: [a5](../evidence/replay-initialization.json),
[ramp](../evidence/replay-initialization-ramp.json). Они содержат SHA-256,
таблицу диапазонов записей по исходным инструкциям, resource lifecycle и RNG
до/после каждого вызова. Полные capture сохраняют более подробный инвентарь;
автономные fixtures опускают его и неиспользуемые дубли блоков, сохраняя все
сравниваемые состояния, входы и байты.

Полный `swift test --package-path native` прошёл: **32 теста, 0 ошибок,
514.610 с**. Новая проверка двух корпусов заняла 113.006 с; прежняя подготовка,
загрузчики и игровые сравнительные сценарии также прошли без изменения fixtures.

## Воспроизведение и продолжение

```bash
# Нужен закреплённый build/original/loaded-catalog.json из LOADED_CATALOG.md.
uv run tools/oracle_replay_initialization.py
uv run tools/oracle_replay_initialization.py --ramp
uv run tools/oracle_replay_initialization.py --accept
swift test --package-path native
```

`--accept` сначала сравнивает оба корпуса с нативным кодом, затем сохраняет
fixtures. SwiftPM-команды запускать последовательно. Прежние fixtures подготовки
не менялись; общий сценарий вынесен в `run_scenarios`, чтобы не создавать вторую
последовательность тех же входов. В стенде новый явный stop-hook удерживает
границы внутри повторно используемых блоков Unicorn при смене точки остановки.

Позднейший [MATCH_PRELUDE.md](MATCH_PRELUDE.md) добавляет в связанную проверку
предшествующий `42cf8a..42d1ff`, реальный sprintf и sound/fill helpers.
Два корпуса этого документа остаются прежними.

Следующее в R02.1: menu/RNG provenance, продолжение
меню **после `42d704`** и полный такт R01.2. В частности, `450c2c==1` ведёт
к отдельной ветке `42d7a1..42ddba`, её нельзя незаметно обойти как обычный запуск.

Следующее в R16: `43db40/43dc50` работают с десятью байтами по адресу
`buffer+2b38+10*450b8c` (пока статическая отправная точка); нужны происхождение
индекса/ввода, запись и чтение тактов, упаковка/файл, восстановление состояния
и воспроизведение полной игры. Отдельная сеть остаётся открытой.

Отключённая музыка с непустым путём теперь также исполняется в следующей общей
подготовке: `4025b0 → 402020 → return` при `44d010=0`. Enabled DirectShow,
пиксели, звук, Windows startup и полный матч этим не подтверждаются.
