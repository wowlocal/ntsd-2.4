## Implementation contract

A typed request enum distinguishes window, bitmap(stage,request) and
front(stage,event); response enum preserves the corresponding full response.
Front replies reuse signed result/optional output. Nonnegative GetDC requires
an explicit output, including zero. Negative GetDC may omit output and retains
prior library DC; later numeric GDI errors stay ignored by game control flow.
String length and helper/read/store notifications are not external requests.

MenuSession obtains a front reply before emitting one new frontAPI terminal
effect. Its Graphics owner consumes that actual reply once. Text helper's
response callback emits its effect; the following old event remains observation
only. Other front operations record actual numeric results; surface Release
updates the bitmap owner with that result, and World-return observation retains
the actual presentation result (dispatcher's own return stays independent).
Prepared routes and old effect cases remain source-compatible and unchanged.
Front body/global/local/DC and all whole menu/Host state remain staged.

Bootstrap/Host gain optional surface/front providers; observed surface cannot
mix prepared surface arrays. Existing bitmap/lifecycle mixed-input guards stay.
The whole-iteration coordinator captures Host sequence, supplies one value cursor
through all three request families, and services only after Core unwinds.
Requests therefore retain cross-family order, including prefix fill before the
background bitmap constructor. Final publication validates complete consumption.
Reentry/stale/foreign/duplicate/cancelled/indeterminate outcomes remain distinct.
Value-owned earlier nonempty cursors retain owners across later/empty iterations;
inspection copies must not mutate Host or queued contexts. Physical work is not
rolled back: receipts/owners survive a retry. A committed graphics projection
must never be delivered again as a second execution of serviced requests.

Extend the existing Mac bitmap service with an overload for this coordinator,
reusing its same preparation/validation/perform/failure body. No physical front
raster or Window service is added. Validation uses actual Native bitmap work and
explicit controlled Window/front replies. Controlled requests are not Windows
observations or proof of a completed drawing operation.
