# R02.1/R15 — данные информационной панели меню

Эталон — EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`;
MSVCR80 DLL SHA-256
`c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
Выполнено всё тело `43c780..43cc53`, включая возврат, stack cookie и сохранение
nonvolatile registers. Настоящие DLL `sprintf`, `fgets`, `sscanf` исполняются
в том же CPU/стеке. Native `OriginalMenuContent` использует прежний общий
`OriginalFrameScanner` без изменений.

Это отдельная зависимость следующего обработчика начального экрана `4236d0`,
который вызывается в `427127`. Соединение с родителем ещё не выполнено.
Исходный дистрибутив содержит `data/adinfo.txt` с байтами `now 0 4 <end>\r\n`,
но **не содержит** `data/ad0.txt`, `data/ad1.txt`, `sprite/sys/ad0.bmp` и
`sprite/sys/ad1.bmp`. Их отсутствие проверяет источник и фиксирует корпус.
Успешные чтения исследованы на контрольных входах, составленных по формату EXE;
они не добавляются к игровым ресурсам и не изображают утраченные исходные файлы.

## Путь и открытие

Два `sprintf` читают signed Int32 из `44d784` и пишут через завершающий NUL:

| Destination | Формат | Возврат CRT |
| --- | --- | --- |
| `453c68` | `data\ad%d.txt` | `43c7ae` |
| `453d40` | `sprite\sys\ad%d.bmp` | `43c7c1` |

Старые байты после NUL сохраняются. `fopen` открывает первый путь в режиме `r`.
При отсутствии файла helper возвращает 0: остальные поля не сбрасываются,
`fclose` не вызывается. Ошибка `fclose` при открытом файле не меняет результат
парсера. Проверены крайние signed индексы и пять результатов закрытия.

## Формат и последовательность записей

Каждая строка получается через `fgets(...,500,FILE)`: не более499 байт плюс NUL.
Неудачный `fgets` сохраняет старый буфер, после чего исходник всё равно сканирует
его содержимое. Возвращённое число присваиваний `sscanf` напрямую не проверяется;
решение принимается по маркерам, первым байтам строк и значениям полей.

1. Заголовок: сначала `fgets`, затем `44d778=-99`, затем `%d ` в это поле.
   Оставшееся или прочитанное значение -99 означает неуспех.
2. Ровно24 строки `ba`: `%s %d %d %d %d %s %s`.
3. Ровно8 строк `ta`: `%s %d %d %d %s %s`.
4. Одна строка `un`: `%s %d %s %s`.
5. Одна строка `y`: `%s %d %d %s`.
6. Одна строка `%s`, результат которой должен начинаться точными шестью байтами
   `<end>\0`. Только после этого helper возвращает1.

| Строка | Числовые destinations в порядке scanf | Строка | Маркеры |
| --- | --- | --- | --- |
| `ba`, i=0..23 | `4583b8+4i`, `453c08+4i`, `453f70+4i`, `453ce0+4i` | `454a18+100i` | `ba\0`, `bae\0` |
| `ta`, i=0..7 | `452928+4i`, `4546d0+4i`, `453f50+4i` | `4546f8+100i` | `ta\0`, `tae\0` |
| `un` | `4554bc` | `453da8` | `un\0`, `une\0` |
| `y` | `453da4`, `45757c` | — | `y\0`, `ye\0` |

Каждое используемое числовое поле должно отличаться от -99. Допустимый первый
байт строки ba/ta/un — `?`, `h` либо `H`; полная проверка URL отсутствует.
Переход по ссылке этим helper не выполняется.

Порядок инициализации отличается от порядка scanf. Для ba сначала пишутся -99
в `453ce0`, `453f70`, `453c08`, `4583b8` текущей строки, затем только UInt16
`0x002d` (`-\0`) в строковый слот. Для ta порядок — `453f50`, `4546d0`, `452928`,
затем такой же UInt16. Для un — `4554bc=-99`, затем UInt16 в `453da8`.
Для y — сначала `45757c=-99`, затем `453da4=-99`.

При неуспехе ba повторно сбрасывается **только** первое scanf-поле `4583b8+4i`.
Для ta сбрасываются все три в порядке `452928`, `4546d0`, `453f50`; для un —
только `4554bc`. Для y пишется **0**, сначала в `45757c`, затем в `453da4`.
Уже прочитанные остальные поля и ещё не достигнутые строки остаются на месте.
Отмена всей загрузки или предварительное обнуление таблиц изменили бы поведение.

## Общая память строк

Проверяется область1104 байта начиная с entryESP−`454`; cookie лежит за ней.
Внутри неё два52-байтных участка маркеров имеют offsets0 и52, основной500-байтный
буфер начинается с104, а500-байтный буфер заголовка — с604. Для ba начальный
маркер идёт в52, конечный — в0; для остальных строк эти destinations меняются
местами. Финальный `<end>` пишется в0.

`%s` не ограничен шириной. Native хранит эту область совместно и сохраняет
наложения, старые хвосты и маски записи. Строковые global slots также не обрезаются
по stride100: длинные контрольные строки могут записывать соседние поля.
Числа используют проверенное 32-bit переполнение общего сканера.

В A5-проходе шесть случаев пустого входа не оставляют NUL в доступной части
буфера заголовка. Источник останавливается **перед** `sscanf` call `43c817`,
native сообщает такую же границу, сохраняя уже выполненные записи. Чтение за
пределами объявленной области и последствия повреждения стека не моделируются.
Ramp backing содержит NUL: соответствующие вызовы реально возвращаются и
сравниваются. Это различие тестовых входов, не доказательство Windows stack
provenance. Никакая маска чтением не переводится в defined=true.

## Проверка

Два прохода по352 случая каждый: отсутствие обоих исходных файлов, полный
контрольный формат, остановка и ошибочная строка на каждом месте, sentinel,
переполнение, неверный префикс/маркер, частичные поля, встроенный NUL и длинные
строки. Каждый основной вход проверяется с `_read` chunk1/7/4096. Globals
переходят из собственного предыдущего случая; scratch перед каждым вызовом
получает объявленный A5 либо ramp backing с нулевой маской.

| Проверка | A5 | Ramp |
| --- | ---: | ---: |
| Случаи | 352 | 352 |
| Actual sprintf / fgets / sscanf | 704 / 8 499 / 8 493 | 704 / 8 499 / 8 499 |
| События / parent writes | 58 225 / 39 833 | 58 237 / 39 833 |
| Успех / неуспех / граница | 32 / 314 / 6 | 32 / 320 / 0 |
| Полные records / bytes и masks | 36 096 / 852 731 904 | 36 108 / 853 015 392 |

Все global bytes и scratch bytes/masks сравниваются после каждого CRT возврата
и в конце случая. Проверяются форматы, аргументы, путь/режим открытия, позиции
файла, EOF, результаты CRT, точный порядок parent writes и закрытия. Источник
дополнительно проверяет реальные return PC, stack balance и nonvolatile registers.
После-снимки оригинала не используются как вход нативного следующего случая.

```sh
uv run tools/oracle_menu_content.py
uv run tools/oracle_menu_content.py --control
uv run tools/oracle_menu_content.py --accept
swift test --package-path native --filter OriginalMenuContentTests
swift build --package-path native -c release --product NTSDNative
```

Release-сравнения [основного](../evidence/menu-content.json) и
[контрольного](../evidence/menu-content-control.json) корпусов прошли до принятия
fixtures. Старые25 fixtures сохраняются; новые упакованы без потери исходных
байтов. SHA raw/packed и полное обратное распаковывание проверены. Оба новых
XCTest прошли за28.684 s, release NTSDNative собран за2.33 s. SwiftPM выполняется
последовательно. Приложение и графический вывод этим не запускались.

Fopen/fclose, уже переведённые текстовые `_read` bytes, CRT thread/locks и raw
scratch backing — объявленные входы стенда. Реальная Windows file translation,
assembly binding и происхождение стека ещё не проверены. Следом нужны bitmap
lifecycle `43cc60`, default/cache writers `43c690/43c710`, затем весь `4236d0`
через настоящий caller `427127` после ранних ресурсов/настроек/рисунка.
Более ранние `43cf40/43c4a0`, worker `43c240`, полный экран, пиксели, оконный
интерфейс и законченный матч остаются открытыми. Это исследование не увеличивает
проверенный игровой объём Practice.

Позднейший [MENU_INFO_READING](MENU_INFO_READING.md) переносит ранний43c4a0:
194 полных чтения и два отдельных отклонения неизвестного локального байта.
Его16 собственных цепочек с cache43c710 передают принятые байты записи следующему
читателю. Эти controlled ABI-связи не исполняют весь43cf94..43cfb4 с content/
panel/defaults и не закрывают WinMain/Windows или подключение к приложению.
