# R02.1 / R07 / R09 / R11 — сбор контактов и слияние

Эталон: NTSD 2.4 EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.

[OriginalWorldContacts](../../native/Sources/NTSDCore/OriginalWorldContacts.swift)
переносит caller `41eed8..41eefb`, всю `419380` и её настоящие helpers.
[OriginalWorldFusion](../../native/Sources/NTSDCore/OriginalWorldFusion.swift)
содержит обязательный хвост `4064d0`. Контакты сохраняются в исходных буферах
Actor; урон и последующие переходы применяют ещё не соединённые проходы `42e100`.

## Порядок прохода

| Адреса | Правило |
| --- | --- |
| `41eed8..41eefb` | При44d05c==2 сбросить флаг в0 и пропустить весь419380; иначе передать451160 как mode |
| `419380..4195ff` | Все400 активных слотов: сохранить currentFrame70 в collisionFrame7c; условно сбросить arestEC |
| `4195ff..4196d3` | Пары i<j по возрастанию; signed vrest обоих направлений,417200/417400 сначалаi→j, затемj→i |
| `417200..4173fa` | Общая предварительная проверка наличия ITR/BDY, таймеров и прямоугольных границ |
| `4171c0..4171fc` | Четыре строгих сравнения signed32 разностей прямоугольников |
| `417400..417f7b` | Исходный вложенный обход ITR/BDY, фильтры, геометрия, nearest/multiple buffers и RNG133/134 |
| `4196d3..4196df` | Безусловный4064d0 и настоящийret4 |
| `4064d0..406a1f` |20 слотов: cooldown, исходное слияние7/8→51 и разделение51 через реальный4061d0 |

Активность контактов — любой ненулевой byte. Префикс сбрасывает ActorEC, если
в текущем кадре itrCount128==0, либо его state1001 и wpoint.attackingE8 текущего
кадра владельца ActorA0 равен0. Эта ссылка владельца не проходит проверки
активности и обратной связи из417f80: у функций разные исходные правила.

Для каждой активной пары положительный **signed Int8** vrest[F0+otherSlot]
уменьшается на1 с обеих сторон до обеих проверок. Отрицательные байты остаются
прежними. Неактивный участник не расходует vrest. World-слоты могут ссылаться
на одну Actor-аллокацию; все изменения сохраняются в порядке исходного прохода.

## Кадры, геометрия и исходная память

417200 проверяет itrCount/bdyCount **текущих** кадров70, arest атакующего и
vrest защищающегося по номеру атакующего слота. Нулевой count отвергает пару;
отрицательный не заменяется нулём. Кэшированные границы138..154, centerx50 и
centery54 читаются из collisionFrame7c. Обычный x=ix−centerx+box.x; при любом
ненулевом facing x=centerx+ix−box.w−box.x. Y=iy−centery+box.y.

4171c0 использует `(x2−x1)<w1`, `(x1−x2)<w2`, `(y2−y1)<h1`, `(y1−y2)<h2`.
Разности32-битные с переполнением; равные границы не пересекаются. Не заменять
это стандартным CGRect/abs. Проверки глубины здесь нет.

417400 сохраняет обе ссылки collisionFrame при входе. Массив ITR находится
по Frame130 со stride80, BDY — Frame134 со stride40. Используются настоящие
сырые записи из общего загруженного каталога, включая masks и внутренние
смещения ссылок. OriginalContactFrameMemory ищет исходный32-битный адрес в
нативных аллокациях; это доступ к данным, не эмуляция или разыменование host
pointer. Неизвестный адрес, чтение за пределами аллокации или неопределённых
байтов явно отвергаются. Неподтверждённое соседнее backing memory не выдумывается.

Точные прямоугольники вычисляются заново для каждой ITR/BDY. ITR.zwidth48==0
означает15. Проверка `delta<zwidth && delta>−zwidth` использует signed overflow
и строгие границы. Оригинал вызывает rectangle helper и при непрошедшей глубине.
Frame78 отдельно используется фильтрами effect2/20/21; его нельзя объединять
с текущим70 или collision7c.

## Фильтры и выбор контактов

417492..417919 переносится вместе с исходными переходами к **следующему ITR**,
а не только к следующему BDY. Общие фильтры учитывают kind/type/effect, state,
invulnerability8, команды, владельца и mode. У kind8/14 есть исключение из
invulnerability; kind3/8 требуют type0. Kind5 сравнивает команду владельцаA0,
остальные исходные командные ветви — команду самого атакующего.

EXE содержит явные исключения для атакующих sourceID200/203/205/206/207/215/216
против209, kind9, а также sourceID212 с остатками кадров по10. Mode1 допускает
BDY.kind>=1000 для type0 или ID201/202 с team!=5, а также удерживаемого предмета
с активным **ровно1** владельцем type0/team!=5. Ни имя персонажа, ни список
разрешённых приёмов в нативной реализации не участвуют.

State12 защищающегося при fall<=40 отвергает контакт, кроме kind10/11.
При vrest==0 и kind вне1/2/7 обычная ветвь выбирает ближайшую по x цель:
Actor2e8 — signed расстояние,280 — слот,2d0 — byte ITR index,2e4=1.
У удерживаемого предмета расстояние берётся от владельца; сам владелец имеет
расстояние2000. При равенстве вызывается исходныйRNG(133,2), результат0 принимает
цель. Abs сохраняет переполнениеInt32.min.

Остальная ветвь использует исходный предел20 контактов. Kind1 отдельно
обновляет ближайшее расстояние2ec защищающегося с RNG(134,2); эта запись может
состояться и при последующем отклонении контакта. Направление и state16,
нажатие атакиD1/previousCA, state1004/2004 и удержание98 определяют исходные
захваты/подбор. Kind7 имеет отдельный прямой переход к добавлению.

При добавлении2e4 перечитывается после каждой записи, как в EXE. Signed
отрицательный count может адресовать более ранние байты **внутри** Actor;
он не исправляется в0. Запись за восстановленным размером0x420 отвергается.
Списки не сортируются и не заменяются высокоуровневым множеством попаданий.

## Слияние и разделение

4064d0 обходит первые20 слотов. Положительный338 уменьшается даже у неактивных;
само слияние/разделение требует activity==1. Инициатор ID7/8 должен иметь HP>0,
state2,cooldown0 и HP<177 либо глобальный458428==1. Другой боец имеет ID15−id,
положительный HP, ту же команду и cooldown0. Его frame должен быть0..<400;
state2 допустим напрямую, другой state — только не14, приiy0 и слоте>9.
Пределы abs(dx)<50/abs(dz)<8 строгие. Инициатор должен быть справа от другого
либо другой слот>9; собственный слот инициатора<10. Выбирается первый catalogID51.

Слияние складывает HP/redHP, ограничивает redHP поmaxHP, затемHP поredHP.
Ставит frame290/328=1, обнуляет **собственнуюvx и чужуюvy**, усредняет integer
x/z с переполнением суммы и делением к0, затем записывает binaryx/z. Сохраняет
слот32c, прежниеID330/334,cooldown4500, назначает Object51/MP500 и деактивирует
другой слот. Поиск продолжается с перечитыванием изменившегося ID.

Разделение требуетID51,328==1,frame<9 либо>260,cooldown<=0. Оно выставляет
328=−1/338=900 и сканирует **весь** каталог. Каждый ID330 меняет собственный
Object; каждый ID334 в else-ветви реконструирует слот32c настоящим конструктором,
сохраняя маску прежних нетронутых байтов, назначает Object/31c и активирует слот.
Повторные ID могут назначить/реконструировать объект несколько раз; совпавшие
330/334 идут только по первой ветви. Отсутствие совпадения не пропускает хвост.

Хвост последовательно делит HP/redHP обоих пополам, копирует x/z, задаёт другому
y0/binary координаты, обнуляет обеvx, делает facing=byte(1−ownFacing), обоим
frame112/MP0 и копирует team. При alias последующие чтения видят уже изменённые
поля. Вновь активированный более поздний слот также будет обработан этим обходом.

## Доказательства и границы

[oracle_world_contacts.py](../../tools/oracle_world_contacts.py) исполняет
полные419380/417200/417400/4171c0/4064d0 и вложенные RNG/abs/Actor constructor
с настоящими ABI. Единственная оставленная внешняя граница функции — прежний
constructor memset. Проверяются сохраняемые регистры, стек/ret, CW037f/пустой
FPU stack, весь400-slot pool/маски, globals, неизменность Objects/Frame heap и
порядок RNG/реконструкций. Входы синтетические: четыре объявленных Object,
Frame/ITR/BDY, активность и Actor patches над оригинальными a5/ramp конструкторами.
Они не выдаются за все естественные DAT-последовательности или полный матч.

Первое сравнение6640 случаев прошло без расхождений за5.164с; release build
106.98с. Проверка недостигнутых инструкций выявила полезные пробелы корпуса:
разворот cached bounds, state/effect gates, расстояния удерживаемых предметов,
все пять развёрнутых полос префикса и fusion clamps. Добавлены отдельные сценарии
этих правил и caller44d05c. Итоговый объём —7925 случаев/188787 helper returns,
1578 уникальных инструкций/3737 событий. Все инструкции указанных четырёх тел
достигнуты, кроме пропускаемой выравнивающей41960d; это **не** доказательство
всех исходов ветвлений, произвольных входов или естественной достижимости.

[oracle_gameplay_contacts.py](../../tools/oracle_gameplay_contacts.py) заново
воспроизводит оба закреплённых GAMEPLAY_LINKS целиком, включая их загрузку,
меню, выбор матча, музыку, запись, управление и физику. На том же CPU/стеке
продолжает собственный41eed8 до41eefb без новых игровых стимулов. Оба source
процесса завершились с code0. Каждый:163 инструкции,4 helpers,0 undefined
catalog reads. Оба417200 возвращают0, далее исполняется полный4064d0/419380.
В исходном первом проходе меняются только два byte в полном pool: Actor7c
Наруто и Саске с0 на219. Все masks/globals/resources/music/replay сохранены.

Native MatchLaunchReference принимает contacts только после собственной
physics/links цепочки и проверки SHA родительского packed fixture. Сравнивает
полные состояния до/после, все сохранённые ресурсы, CRT и replay, ABI/порядок
helpers. Снимок EXE не становится входным состоянием нативной модели.

Оба собственных Native сравнения прошли за36.749с; вместе с7925 контролями и
проверками raw-memory/rollback:5 XCTest/42.869с, release build105.97с. С учётом
сохранённых родителей:67462 records/626775884 bytes+masks/920 helpers/66
checkpoints. Сам новый участок добавляет8 helper returns и два полных
before/after сравнения; исторические родители не считаются новыми сценариями.

[accept_gameplay_contacts.py](../../tools/accept_gameplay_contacts.py) проверяет
SHA/размер исходных корпусов, родительские fixtures и все transport blobs,
сравнивает вместе synthetic и обе собственные Native цепочки, затем публикует
три lossless fixtures. Acceptance:5 XCTest/42.719с, build106.97с.
Отчёты: [World](../evidence/world-contacts.json),
[own a5](../evidence/gameplay-contacts.json),
[own ramp/reverse addresses](../evidence/gameplay-contacts-control.json).
Все120 прежних fixtures сохранили SHA. Три новых проверены по raw/packed
SHA/размеру и полному распакованному JSON;123 pins записаны в
`build/research/gameplay-contacts-fixture-pins.json`.

После публикации новые packed fixtures и предыдущие Actor/World physics,
WorldLinks, GameplayControl/Physics/Links и MatchLaunch прошли вместе:
19 release XCTest/220.175с, build107.37с. NTSDNative также скомпилирован и
связан; UI этим прогоном не проверяется. Все source/Swift процессы завершены.

Весь public caller атомарен по World/pool/globals: при неизвестном чтении,
выходе за восстановленное хранилище или ошибке наблюдателя ничего не публикует.
Отдельный тест требует реальныйRNG133 после prefix и проверяет полный откат.
Это политика обработки неперенесённого поведения в порте, не правило Windows.
Внешние события следует буферизовать до принятия всего такта.

```sh
uv run tools/oracle_world_contacts.py
uv run tools/oracle_gameplay_contacts.py
uv run tools/oracle_gameplay_contacts.py --control
python3 tools/accept_gameplay_contacts.py
swift test --package-path native -c release --filter 'Original(ActorPhysics|WorldPhysics|WorldLinks|WorldContacts|GameplayContacts|GameplayLinks|GameplayPhysics|GameplayControl|MatchLaunch)Tests'
```

SwiftPM и публикация fixture ресурсов выполняются последовательно. Старые
control/physics/links fixtures сохраняют прежние остановки и области доказательства.
Новая цепочка всё ещё находится внутри первого4246b0, SP1000e9bc,phase1/tick1,
frame219,HP500/MP200,RNG39/0. Она заканчивается41eefb перед подсчётом предметов,
первыми42e100 и новым item-spawn RNG. Далее нужны оба прохода применения
попаданий с появлением предметов между ними, остальные cpoint/link helpers,
второй417f80, вывод/камера/планировщик/восстановление и полный возврат такта.
Естественные последовательности всех DAT, UI приложения, Windows-проверка,
первый законченный матч и чистая macOS остаются открытыми.
