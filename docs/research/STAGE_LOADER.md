# R02.1 / R03.1 — исходный загрузчик Stage

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Следующий дочерний загрузчик после [Object](OBJECT_LOADER.md) и
[BG](BACKGROUND_LOADER.md). [oracle_stages.py](../../tools/oracle_stages.py)
исполняет весь `40c910..40d09d` и декодер `414a30..414b6f`.
[OriginalStageLoader](../../native/Sources/NTSDCore/OriginalStageLoader.swift)
переносит этот путь в Native Core, сохраняя полные байты и маски.

**Загружены данные Stage, не перенесён игровой режим Stage.** Создание врагов,
условия завершения фазы, переходы, музыка, AI и выбор режима через меню ещё
не восстановлены этим компонентом. Новый loader не подключён к практике,
родителю каталога или широкому такту R01.2. Сравнение полной игры под Windows
остаётся открытым.

## Файл и внешний порядок

`40c910` получает Catalog через ECX, не принимает аргументов и возвращается
обычным `ret`. `40c92d..40c939` **безусловно** декодирует `data\stage.dat` в
`data\temporary.txt` через `414a30(source,destination)`. Проверки суффикса/
plaintext marker здесь нет. Побайтовый алгоритм совпал с общим native decoder
при его фиксированном имени `data\stage.dat`: пропуск 123 логических байт,
продвижение ключа во время пропуска, вычитание ключа, временный поток.
Это новый оригинальный decoder entry, он не подменён вызовом Python decode_dat.

Затем открывается temporary, сбрасываются 60 dword-счётчиков стадий в -1,
читаются целые `<stage>`/`<phase>` до исходных завершающих токенов. После EOF
файлы закрываются и temporary получает `Do not erase this file.`. Все файлы
в стенде виртуальные; исходное распределение не меняется.

**Stage не добавляет вклад в `44f620`.** В полном теле загрузчика/декодера нет
обращений к этому checksum (S), при всех шести выполнениях он остался равным
заданному ненулевому `ffff1234` (D). Не нужно добавлять checksum для каждого
токена по аналогии с Object/BG. Звуковой кэш и bitmap здесь также не заполняются.

В исходном файле 25 stage declarations с ID
`0..4, 10..14, 20..24, 30..34, 40..44`, **138 фаз и 818 записей `id:` внутри фаз**.
Числа подтверждены исполняемыми scanf/checkpoints, а не только поиском маркеров.
Есть 191 чтение `ratio:`; ни одного `music:` в этом исходном файле, поэтому
музыка проверяется отдельным контрольным потоком.

## Размещение и provenance

Весь участок Catalog `7d0..<4d45db0` — **81 024 480 байт**:
60 записей по `149b08` = 1 350 408 байт. В Native Core сохраняются все 60 записей
`OriginalStateRecord`. Это текущее представление основания состояния, а не
требование использовать такое размещение для окончательного renderer/runtime.

Для stage s и phase p ниже смещения относительно `Catalog + 7d0 + s*149b08`.
`P = p*34c0`; число возможных фаз в цикле инициализации — 100.

| Offset | Размер / назначение загрузчика | Адреса |
| --- | --- | --- |
| `0` | Int32 число фаз; -1 до первой фазы / при отсутствии стадии | `40c962`, `40cb6e`, `40cbd1` |
| `4` | 4 байта, не записываются этим загрузчиком | полный снимок/маска |
| `P+8` | Int32 bound, default -1 | `40ca0d`, `40cc32` |
| `P+c` | NUL пути music при инициализации и начале фазы | `40ca33`, `40cbaf`, строка `40ccff` |
| `P+34c0` | Int32 when_clear_goto_phase, default -1 | `40ca20`, `40cf38` |
| `P+ec + e*e0` | ID и параметры записи e, e=0..59 | `40ca43..40cb48`, парсер ниже |

Деление на фазы и шаг `e0` не доказывают существование независимого C-struct
размером `e0` с началом в `P+ec`. В частности, произвольное копирование 60 таких
структур вместе с заголовком пересекло бы следующую фазу. Восстановленные записи
касаются только первых 48 байт каждого шага; промежутки остаются в полном storage.
Последняя установленная запись последней фазы заканчивается в `149afc`, за ней
до `149b08` сохраняются ещё 12 байт. Их не обнуляют и не исключают из сравнения.

`40c957..40c970` при **каждом вызове** сбрасывает только первый dword всех
60 стадий. Когда найден stage-level `id:`, `40c9f5..40cb79` инициализирует
все 100 фаз/6000 записей выбранной стадии, а не только встреченные в DAT.
Порядок: фаза → запись → исходные поля; `fldz/fst` сохраняет **положительный**
binary64 zero. Впервые инициализированная стадия содержит **288 904 определённых
байта**, остальные 1 061 504 сохраняют allocator backing. В ненайденной стадии
на этом проходе определены только 4 байта счётчика.

| Entry-relative offset | Поле | Default | Чтение / изменение |
| --- | --- | --- | --- |
| `0` | id | -1 | `40ccc2` |
| `4` | x | 500 | `40cd37`; все 60 перезаписываются при bound |
| `8` | hp | 500 | `40cd78` |
| `c` | times | 1 | `40cdb9`; `<soldier>` записывает 50 |
| `10` | reserve | 0 | `40cdfa` |
| `14` | join | 0 | `40ce6c` |
| `18` | join_reserve | 0 | `40ceaf` |
| `1c` | act | 9 | `40d001` |
| `20` | y | 0 | `40cfbe` |
| `24` | ratio, binary64 | +0 | `40cf7b` |
| `2c` | маркер boss/soldier | 0 | `<boss>` → 2 (`40ce2b`), `<soldier>` → 1 (`40cee2`) |

Названия полей получены из токенов загрузчика. Их игровые значения и условия
потребителей нельзя выводить только из названий/defaults.

## Почему порядок токенов важен

- `bound:` записывает bound, затем **все 60 x = bound + 80** с Int32 wrap
  (`40cc38..40cc75`). При failed `%d` используется прежний bound; проход
  присваиваний всё равно выполняется. Если bound стоит после x, раннее x теряется.
- `id:` внутри фазы продвигает индекс записи даже при matching failure.
  Записи разделяются этими токенами, не строками. Каждая фаза начинает индекс с -1.
- До первого `id:` те же поля адресуются по entry=-1 и попадают в область music.
  Например, раннее x записывается в `P+10`. Нативный перенос сохраняет это
  перекрытие, а не переставляет значения к «будущему первому объекту».
- `<soldier>` перезаписывает маркер и times=50, `<boss>` меняет только маркер.
  Поэтому `<boss> <soldier> times: 13 <boss>` оставляет маркер 2 и times 13.
- `music:` копирует строку и NUL без очистки хвоста. Повторное имя X сохраняет
  старые байты за NUL. Повторная инициализация пишет только первый NUL и также
  сохраняет прежние хвосты/их маски.
- Повторный stage-level `id:` заново инициализирует ту же стадию и сбрасывает
  номер следующей фазы. Он не объединяет фазы двух определений.
- `#...` не является комментарием парсера. Это обычные неизвестные токены.
  Например, исходное `#bomb ratio: 4:0` всё равно присваивает ratio=4.0 через
  десятичный префикс, после чего `:0` игнорируется как другой токен.

Контрольные снимки подтверждают: `bound: -50` меняет ранее заданные x на 30;
во второй фазе `id: 33 x: 123 bound: 800 id: 44 x: -17` оставляет x=880 и -17.
Проверяются крайние Int32, переполнение bound+80, -0.0, .125, 1e-3 и 4:0,
порядок boss/soldier, повторные ID/поля, короткий music после длинного и повторный
разбор поверх ранее загруженных записей. Исходный файл не исправлен.

## Сравнение и воспроизведение

```sh
uv run tools/oracle_stages.py --suite
swift test --package-path native
```

[StageReference](../../native/Sources/NTSDReferenceChecks/StageReference.swift)
проверяет полные decoded bytes, каждый выбранный Stage после полного initializer
и каждой законченной фазы, затем **все 60 полных записей при EOF каждого вызова**.
Сравниваются байты и provenance, включая нетронутые области и ранее загруженные
стадии. Нет нормализации указателей: ни одно слово здесь не объявлено указателем.

| Корпус | Вызовы / stage initializer / фазы | Checkpoints | Полные Stage records | Байты + такие же маски |
| --- | --- | --- | --- | --- |
| Исходный stage.dat, text stdio, fill a5 | 1 / 25 / 138 | 163 | 223 | 301 140 984 |
| Тот же stage.dat, raw stdio, fill 00 | 1 / 25 / 138 | 163 | 223 | 301 140 984 |
| Контроли, text stdio, backing 00..ff по всей таблице | 4 / 5 / 105 | 110 | 350 | 472 642 800 |
| Всего | **6 / 55 / 381** | **436** | **796** | **1 074 924 768** |

Это сумма сравниваемых контрольных точек, **не объём уникального контента** и не
процент игры. В четырёх последовательных контрольных вызовах проверены поля,
перезагрузка, последняя стадия 59 / 100 фаз / 60 записей последней фазы, затем
поток без стадий. Последний сбрасывает все счётчики в -1, сохраняя старые данные.
В последней фазе предельного контроля `bound: 2147483647 bound: nope`
оставляет во всех 60 x значение **-2147483569**: результат переполнения
не перекрыт позднейшими присваиваниями и прямо сравнивается в снимке.
Контроль `id: nope hp: 444` продвигает индекс и меняет hp новой записи, сохраняя
её ID=-1. Stage-level `id: nope` повторно использует ранее прочитанный stage ID.
При повторной инициализации stage 59 остаются определёнными **288 931** байт:
дополнительное происхождение старой строки/ранних полей не теряется.

Полные снимки в `build/original/stages-*.json` сжаты без потерь raw DEFLATE,
каждый блок имеет размер и SHA-256. Маска также сохраняется целиком. Swift
распаковывает их через системный Compression в development-only target,
проверяет длину/хеш и сравнивает все байты. Это сжатие fixture, не реконструкция
эталона по правилам нативного загрузчика. Runtime Core не зависит от Compression,
CryptoKit, EXE или Python. Общая offline fixture занимает около 4.3 MiB.

[stage-loader.json](../evidence/stage-loader.json) содержит хеши корпусов,
fixture/исходников и сгруппированные обращения. `offsetRuns` — тройки
[start, step, count], с проверкой точного восстановления множества смещений.
Списки stage IDs и local offsets в группе — отдельные множества наблюдений,
не утверждение об их декартовом произведении. Полные списки смещений этих групп
и stdio trace остаются в исследовательском корпусе.

Регрессия: **24 Swift-теста без ошибок**, включая все прежние сохранённые
конструкторные, BG, Object, movement/combat/projectile сценарии. Отдельный тест
проверяет отсутствие частичного commit после валидной стадии и последующего
неподдержанного stage ID. Общие предыдущие загрузчики/их fixture не менялись.

## Оставшиеся границы

Стенд использует общий объявленный CRT-контракт: ASCII/C-locale whitespace,
Int32 decimal prefixes в диапазоне, конечные десятичные binary64, `%s/%c`,
text/raw stdio. Реальный MSVCR80 overflow/rounding/locale/EOF и ошибки открытия
не исполняются. Точное поведение конкретного Windows CRT остаётся открытым.
Два stdio-контракта дают разные decoded tails: text `b4`, raw `b7 a5`;
для исходных стадий они не меняют загруженные поля и checksum.

Нативный поддержанный домен: stage 0..59, phase 0..99, до 60 записей; scratch
токены короче 192 байт (консервативная граница перед cookie), music короче
224 байт до первого ID-поля. Переполнение таблиц/строк, uninitialized stage ID
и незакрытые секции отклоняются вместо попытки воспроизвести произвольную порчу
памяти. Source Stage целиком внутри этого домена. No-read-before-write относится
к отслеженной таблице, не ко всему стеку/globals/CRT. `load` сохраняет live table
только при успехе; диагностические callbacks могут быть вызваны до ошибки.

[LOADED_CATALOG.md](LOADED_CATALOG.md) теперь соединяет `4122f0` с настоящими
Object/BG/Stage и встроенными bitmap, с общим checksum/звуком и полным исходным
реестром. Этот новый корпус также исполняет настоящий VC80 scanf в Stage;
исторические границы самостоятельного Stage-корпуса выше не изменены.
Следующий этап — использовать загруженный каталог в World/Actor и R01.2,
восстановить выбранный матч отдельно от загрузочного пула. R02.1/R03.1 не закрыты.
