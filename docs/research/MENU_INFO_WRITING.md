# R02.1/R15 — запись настроек информационной панели

Эталон — EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`;
MSVCR80 DLL SHA-256
`c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
Выполнены целые `43c690..43c708` и `43c710..43c77e`, настоящие DLL `sprintf`
(`7817775d`), `fprintf` (`7813ed1f`) и `fclose` (`781422fc`) на том же CPU/стеке.
Функции вызываются отдельно на собственных продолжающихся globals; это ещё
не весь `4236d0` или его настоящий caller `427127`.

## Default writer `43c690`

1. Открыть `data\adinfo.txt` в режиме `w`.
2. Если файл открыт, вызвать `fprintf(FILE,"now 0 4 <end>\n")`, затем `fclose`.
3. Независимо от открытия/записи/закрытия записать UInt32 `0x776f6e` в `4527b0`
   (`now\0`), затем `44d784=0`, затем `44d788=4`.
4. Через два `sprintf` записать `data\ad0.txt` в `453c68` и `sprite\sys\ad0.bmp`
   в `453d40`. Сначала пишутся указанные global words, затем выполняется первый
   форматирующий вызов.

Это частичные записи через NUL. Старые байты после него сохраняются. Результаты
файловых операций игнорируются этим helper. На обычном ret остаётся длина
результата последнего `sprintf`; её не следует интерпретировать как успех записи.

## Cache writer `43c710`

1. Прочитать signed Int32 `44d784` и сначала сформировать оба пути ad%d в тех же
   globals. Эти операции выполняются и при последующем неуспешном открытии.
2. Открыть `data\adinfo.txt` в режиме `w`.
3. При успехе выполнить `fprintf(FILE,"%s %d %d <end>\n",4527b0,44d784,44d788)`,
   затем `fclose`. Сама дата, индекс и период этим helper не меняются.

`%s` копирует исходные байты до первого NUL; пробелы, TAB, CR/LF, знаки `%` и
старшие байты внутри строки не экранируются и не считаются новым format string.
Числа форматируются как signed32 без ограничения ширины. Никакой проверки даты
или допустимого периода здесь нет.

При неуспешном открытии EAX на ret равен0. При открытом файле остаётся результат
`fclose` (0 либо -1 в проверенном домене), даже если более ранний `fprintf`
вернул -1. Например, ошибка первого сброса и последующее успешное закрытие могут
оставить ret0. Возврат helper не доказывает полноту записанного файла.

## Проверенный домен CRT output

Fopen в стенде является платформенной границей: при успехе он предоставляет
предварительно настроенный FILE с32 байтами состояния и пользовательским буфером
размера1/7/64/4096. Начальные поля: ptr=base=INPUT, count=size, flags=`102`,
descriptor=`ffffffff`, char buffer=0, buffer size=size, temporary filename=0.
Это объявленный response, а не восстановление настоящего Windows fopen/allocator.

Внутренние `fprintf`, `_flsbuf` (`7813ef8b`), flush (`7813e93b`) и `fclose`
исполняются реально. Границы `_write` (`7814e3f1`), `_close` (`7814e83f`) и
`_isatty` (`7814e74a`) предоставляют ответы для непрозрачного descriptor.
`_isatty` возвращает0; append и wide/Unicode modes отсутствуют. `_getptd` и
`_getptd_noexit` (`78132db2`) привязаны к одной реально инициализированной PTD.
Thread/locks остаются прежними объявленными границами CRT.

Обычный символ уменьшает count, записывается по ptr и увеличивает ptr. Когда
count становится отрицательным, `_flsbuf` **до `_write`** меняет ptr на base+1,
count на size−1, сбрасывает EOF и устанавливает write bit. Затем
он передаёт старый полный блок в `_write` и записывает новый символ в base[0].
Последняя запись происходит даже при коротком/неуспешном `_write`. После неё
ставится error bit`20`, а `fprintf` прекращается с -1.

При `fclose` оставшийся prefix буфера снова передаётся в `_write`, включая
сохранённый после ошибки новый символ. После flush ptr становится base, count0.
Затем вызывается `_close` независимо от ошибки flush и очищаются flags. При
пользовательском буфере base/size и байты самого буфера сохраняются; free не
вызывается. Результат `_close` считается ошибкой только при отрицательном значении.
Предыдущий error bit сам по себе не превращает успешный flush/close в -1.

Для `_write` исследованы полная запись, -1, 0 и count−1 на первом, втором и
третьем запросе. Отрицательные низкоуровневые ответы задают errno28 как часть
платформенного response; короткие положительные ответы errno не меняют. Ветвь
замены символа при EILSEQ42 и иные stream modes не проверены. Native
`OriginalBufferedTextOutput` явно ограничен этим user-buffered byte domain.

Передаваемые `_write` байты находятся **до Windows text translation**. В коде
формата используется LF; исходный `data/adinfo.txt` содержит CRLF, его точные
байты и SHA сохранены. Реальная трансляция LF→CRLF, создание/усечение файла,
ошибки диска и Windows FILE/descriptor initialization остаются открытыми.
Ни один вызов capture не пишет в исходный дистрибутив или внешний файл игры.

## Сравнение

Native `OriginalMenuInfoWriting` формирует данные из собственных globals и
вызывает общий новый byte-output механизм. Предыдущие после-снимки оригинала
не становятся входом следующего случая. Перед каждым helper явно задаются
только date/index/period, открытие, размер/backing буфера и ответы IO.
Буфер получает A5 либо ramp backing с нулевой маской; нетронутые байты сохраняются.

Каждый из двух проходов содержит267 случаев:73 defaults и194 cache. Они
проверяют все объявленные capacities, open/write/close failures, крайние signed
index/period, пустую/длинную дату, внутренний NUL, управляющие и старшие байты.

| Наблюдение на проход | Число |
| --- | ---: |
| Actual sprintf / fprintf / fclose | 534 / 259 / 259 |
| `_write` / неуспешные или короткие ответы | 1 309 / 74 |
| События / parent writes | 3 106 / 219 |
| Полные records / bytes и masks | 9 462 / 147 664 942 |

После каждого actual CRT возврата и на границах fopen/_write/_close сравниваются весь
global region, все32 FILE bytes и весь buffer с маской. После каждого helper
проверяется конечное состояние. Отдельно сравниваются форматы, строки, аргументы,
каждый блок `_write`, результаты, global write order и реальные CRT return sites.
Источник проверяет stack balance и все nonvolatile registers на каждом возврате.

```sh
uv run tools/oracle_menu_info_writing.py
uv run tools/oracle_menu_info_writing.py --control
uv run tools/oracle_menu_info_writing.py --accept
swift test --package-path native --filter OriginalMenuInfoWritingTests
swift build --package-path native -c release --product NTSDNative
```

Release-сравнения [основного](../evidence/menu-info-writing.json) и
[контрольного](../evidence/menu-info-writing-control.json) корпусов прошли до
принятия fixtures. Все29 прежних fixture hashes неизменны; SHA raw/packed,
размеры и полное обратное распаковывание проверены. Два новых XCTest прошли
за4.738 s, release NTSDNative собран за2.30 s. SwiftPM выполнялся последовательно.
Существующие shared helpers не менялись. Запуск окна или запись файла на Windows
этими проверками не выполнялись.

Следующий шаг — весь `4236d0` через настоящий `427127`: соединить проверенные
content43c780, bitmap43cc60 и оба writer после свежих ранних ресурсов/настроек/
первого рисунка. Worker, более ранний startup43cf40, остальной экран и интеграция
в приложение остаются открытыми; это не доказательство полного матча или Windows W.

Последующее [сохранение настроек](SETTINGS_WRITING.md) обнаружило отдельные
prefix/value segments в настоящем CRT printf. После failed minus цифры могут
продолжить вывод и снова сделать shared count неотрицательным. Оба menu-info
writer теперь используют этот же `OriginalBufferedTextOutput.printFormat`.
Прежние два корпуса и joined panel повторно прошли без изменения fixtures;
их исторический объём не расширяется автоматически до новых settings сценариев.
