# R02.1 — загрузочный пул и области каталога

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Этот этап продолжает [STATE_LAYOUT.md](STATE_LAYOUT.md). Перенесён участок
создания загрузочного пула; полная загрузка файлов и появление выбранных игроков
при начале раунда остаются открытыми.

## Пул после загрузки каталога

Путь находится внутри `41bc90`, в ветке `44d05c == 1` (`41be8b`). Перед ним
исходный код загружает звуки и вызывает каталог `4122f0("data\\data.txt", surface)`
в `41c013`; после него создаёт bitmap-объекты интерфейса. Конец всей загрузочной
ветки сбрасывает `44d05c=0` в `41c577`. Она не является самостоятельной функцией
появления выбранного бойца.

| Исходный участок | Правило |
| --- | --- |
| `41c052..41c06b` | Сохранить возвращённый каталог в World `+7d4`, начать таблицу Actor `+194` со слота 0 |
| `41c070..41c0d6` | Ровно 400 аллокаций по 0x420; конструктор `4061d0` каждой; ссылка на **первую запись каталога**, координаты binary64 `(200,0,300)`, World pointer слота, активность 0 |
| `41c0d8..41c2f1` | Повторить конструктор для слотов 0–7, снова связать с каталогом[0], скопировать Object `+90` в Actor `+31c`, задать координаты и активность 1 |
| `41c2f5` | Следующий вызов allocator уже запрашивает bitmap 0x1f50; это граница нового стенда |

После повторной инициализации:

| Слот | x | y | z |
| --- | --- | --- | --- |
| 0 | 200 | 0 | 300 |
| 1, 2, 3 | 210 | 0 | 300 |
| 4, 6 | 580 | -200 | 300 |
| 5, 7 | 570 | 0 | 300 |
| 8–399, неактивные | 200 | 0 | 300 |

Константы прочитаны из `449470` (200), `449468` (210), `449460` (570),
`447938` (580), `447930` (-200), `447928` (300). **Целые** `ix/iy/iz` на этом
участке остаются нулевыми; синхронизации с новыми double-координатами здесь нет.
Скорости/накопленные импульсы остаются конструкторными 0.1, owner=99, team=0.
Нельзя подменять ими нейтральное появление игроков в текущей практике.

Проверенный исходный `data/data.txt` начинается с ID **50**, `chars\\pein.dat`.
Загрузочный пул использует индекс **0**, без проверки этого ID. В нативном коде
нет выбора Pein/Naruto/Sasuke для этой операции. Особые восемь позиций —
подтверждённые записи загрузочной ветки EXE, а не правила отдельных персонажей.

## Проверка и нативная модель

[oracle_bootstrap.py](../../tools/oracle_bootstrap.py) исполняет исходные инструкции
`41c052 → 41c0d8 → 41c2f5`, сохраняя состояние на обеих границах. Предварительно
выполняется настоящий конструктор World; значения селектора, catalog[0] и Object
`+90` задаются как входы стенда. **Внешний загрузчик этим не подменяется:** он
вообще не входит в исполняемый фрагмент.

Подменены только `operator new` в `4450ac` и `memset` в `4450a0`. Проверяется
каждый размер запроса/место вызова, записанные и нетронутые байты, защитные
области, порядок 400 аллокаций и 408 вызовов конструктора (0–399, затем 0–7).
Чтение ещё не инициализированных байтов World/Actor останавливает стенд.
Для всех аллокаций в этом корпусе возвращается ненулевой адрес; пути отказа
выделения памяти не проверены. Устройств графики и звука на этом участке нет.

Восемь случаев: четыре исходных шаблона памяти × два размещения. Второе размещение
меняет шаг между Actor и располагает слоты в обратном порядке в памяти. Пробы
Object `+90`: 0, -1, Int32.min, `12345678` hex. Внешний селектор World также
меняется: 0, 2, -7, 17; участок обязан сохранить его, не угадывать режим матча.

Нативный [OriginalWorldBootstrap](../../native/Sources/NTSDCore/OriginalWorldBootstrap.swift)
совпал по **6416 записям, 6 790 528 байтам и флагам инициализации** на 16 контрольных
точках. В World определены все 2008 байт исследованного префикса; после первого
прохода в каждом Actor определены 917 байт, после второго у первых восьми — 921.
Остальные байты сохраняются из исходного шаблона. Отчёт:
[bootstrap.json](../evidence/bootstrap.json).

При сравнении только доказанные указатели заменяются на **непустые ссылки по
индексу**: World actor table → номер слота, World catalog → каталог 0,
Actor `+368` → объект каталога 0. Перед заменой проверяется исходный адрес,
ненулевое значение и инициализация поля. Ноль в канонической записи обозначает
индекс существующего объекта, **не null**. Другие dword не нормализуются;
неизвестные байты не теряются. Это нормализация данного пула, не всех указателей
полного матча из `state-trace.json`.

`OriginalStateRecord.reconstructActor()` теперь сохраняет ранее установленную
маску для нетронутых полей. Вызов конструктора на старой записи не делает её
поле `+368` или `+31c` снова неинициализированным и не очищает непрозрачные области.
Прежний корпус конструкторов остаётся неизменным и проходит повторное сравнение.

Корпус проверяется модулем `NTSDReferenceChecks`, который используют CLI и тесты;
приложение NTSDApp от этого модуля не зависит. Новый загрузочный пул пока также
не подключён к игре: нужен настоящий каталог и последующая инициализация режима.

## Каталог: статически восстановленные границы

[inspect_catalog.py](../../tools/inspect_catalog.py) заново дизассемблирует EXE,
проверяет байты и текст 23 опорных инструкций, затем выводит границы из их
смещений/шагов/числа итераций. Результат —
[catalog-layout.json](../evidence/catalog-layout.json), **S, не D всего каталога**.

| Область относительно Catalog | Размещение | Основание |
| --- | --- | --- |
| `0..<7d0` | Таблица Object*, шаг 4; помещаются 500 указателей | Запись `4126a4`, начало следующей области `40c957`. Ёмкость выведена из границы, проверка переполнения таблицы не доказана |
| `7d0..<4d45db0` | 60 областей стадий по `149b08` байт | Цикл `40c957..40c970` |
| Внутри стадии | 8 байт перед 100 областями с шагом `34c0` | `40cb4e..40cb54`: `149b00 / 34c0 = 100`; `149b08 = 8 + 100*34c0` |
| Повторяющиеся данные внутри фазы | 60 итераций по `e0`, записи ID/параметров и промежутки | `40cb33..40cb48`: `3480/e0 = 60`. Шаг не является доказательством отдельного sizeof(spawn entry); все поля/перекрытия ещё требуют анализа |
| `4d45db0..<4d82380` | **101** область фона по `990` | Шаг `40c220`, базовый адрес из `41a2dd`, начало счётчиков из `412543`; точное совпадение границ |
| Фон 99, база `4d81060` | Встроенные поля, имя Lee On Road, shadow1/back99_1..3 | Прямые записи `41233b..4124f3`; особый путь рисования при `44d024=99` в `41a255..41a271` |
| Фон 100, база `4d819f0` | Имя Random по `+3cc` | `4124f9..41251c` записывает строку в `4d81dbc`; другие поля этого слота не считать заполненными |
| `4d82380`, `4d82384` | Число загруженных объектов и фонов, по 4 байта | Обнуление `41253d/412543`, увеличение `4126a8/412780`; это не ёмкости |
| `4d82388..<4d823a8` | Хвост 32 байта с именем исходного файла | Цикл копирования `412529..41253b`, конец аллокации `41bfeb`; проверки длины в этом цикле нет |

Эти области ровно покрывают **81 273 768 байт / 0x4d823a8**. Большая аллокация
объясняется прежде всего таблицами стадий. Это не основание обнулять их целиком
или требовать такого же физического размещения в Swift. Старый `state-trace`
по-прежнему имеет неотображённый промежуток каталога; новый статический словарь
не превратил его автоматически в загруженные данные.

Часть статической инициализации стадий уже видна: 60 dword `Catalog+7d0 + n*149b08`
получают -1. При обнаружении stage ID выполняется большой цикл по фазам и
повторяющимся полям (`40c9ef..40cb79`). Загрузчик `40c910` вызывается из конца
конструктора каталога (`4127cd`). Весь исходный поток и числовые преобразования
этих файлов ещё не проверены исполнением; исходные значения не выводим из
нынешних синтетических заголовков.

## Воспроизведение и продолжение

```bash
python3 tools/inspect_catalog.py
uv run tools/oracle_bootstrap.py
uv run tools/oracle_state.py
swift test --package-path native
```

SwiftPM-команды выполняются последовательно: они используют один `native/.build`.
Полный bootstrap-корпус находится в `build/original/bootstrap.json`; автономная
фикстура сохраняет все состояния/маски/адреса, удаляя только повторный инвентарь
инструкций. CLI проверяет SHA-256 каждого блока фикстуры.

Продолжение уже выполнено для [родительского прохода каталога](CATALOG_REGISTRY.md)
`4122f0`, с явно непрозрачными дочерними загрузчиками. Следующее в R02.1:
Object `40ef70` уже [проверен отдельно](OBJECT_LOADER.md) на объявленных файлах;
далее исполнить фоновый `40c160` и стадийный `40c910` и
проследить происхождение полей. Их целый файловый поток относится к R03.1;
границу загрузочного пула
больше не нужно подменять ручной сборкой. Начало/перезапуск матча искать отдельно
в ветвях меню `429730`: например, `42d649..42d6fc` сбрасывает счётчики боя,
переинициализирует неактивные слоты 20–399 и вызывает дальнейшие функции. Наличие
этого адреса пока не означает восстановление всей ветки режима.
