# R02.1 / R03.1 — совместная загрузка исходного каталога

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
[oracle_loaded_catalog.py](../../tools/oracle_loaded_catalog.py) выполняет
**4122f0 от входа до возврата с настоящими дочерними загрузчиками**. Родитель
сам читает реестр, выделяет Object и вызывает `40ef70`, `40c160`, `40c910`.
Вызовы больше не заменяются запросами или последовательностью из regex-импорта.

[OriginalLoadedCatalog](../../native/Sources/NTSDCore/OriginalLoadedCatalog.swift)
соединяет нативные загрузчики в том же порядке. Весь исходный каталог совпал
по объявленным ниже данным. Это завершение совместной загрузки данных,
**не инициализация выбранного матча, игровой режим Stage или готовая игра**.
Практика пока использует прежний импорт; полный такт и Windows W остаются открытыми.

## Исходный порядок и общее состояние

| Граница родителя | Исполняемый участок |
| --- | --- |
| `4123d2`, `412430`, `41248b`, `4124e6` | Четыре настоящих конструктора bitmap `43ee50`, с ресурсными ключами встроенной арены |
| `41265b` | Оригинальный loading progress `4242e0`; постоянные часы выбирают уже объявленный путь ожидания |
| `412665`, `412695` | Аллокация `25360`, полный Object loader `40ef70`, возвращение в `41269a` |
| `4126a4..4126a8` | Запись возвращённого Object* в таблицу, затем увеличение счётчика |
| `41277b` | BG metadata `40c160`, возвращение в `412780`, затем увеличение счётчика |
| `4127c2`, `4127cd` | Закрытие файла реестра, полный Stage loader `40c910` и decoder `414a30` |
| `4127d2..4127fb` | Возврат самого Catalog, восстановление стека/SEH/cookie, `ret 8` |

В одной VM сохраняются общие `44f620` checksum, `455638` sound cache,
`458438` sound count, heap bitmap/строк/Frame и все области каталога.
Object, Frame, DAT decoder, bitmap wrapper и sound registration используют
существующий стенд [OBJECT_LOADER.md](OBJECT_LOADER.md), расширенный двумя
форматами scanf родителя: `%d %s %d %s %s` и `%d %s %s`.

**Каждый scanf, кроме байтового `%c` декодера, выполняется настоящим MSVCR80
8.0.50727.6195**: DLL SHA-256
`c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
Границы `_read`/TLS/locks и ограничения Windows binding описаны в
[CRT_SCANNER.md](CRT_SCANNER.md). Это распространяет проверку настоящего scanf
на родительский реестр, все исходные BG и Stage, а не только Object.

Уточнение контекста: [COORDINATE_PRECISION](COORDINATE_PRECISION.md) динамически
проверил, что этот scanf остаётся в отдельной CRT VM и при присоединении
загрузчика к инициализированному игровому CPU. Слово023f основного потока не
передаётся этому scanner автоматически; он сообщает не записанный CW0, что
не определяет его фактическую точность. Сохранённые результаты остаются
эталонами данной границы. Последующий [CATALOG_PRECISION](CATALOG_PRECISION.md)
исполнил все919 912 сканов при явных53 битах: весь исходный снимок побайтно
повторился. Независимая нативная загрузка и все863 исходных%lf также совпали;
само разделение CPU и общие CRT/Windows ограничения этим не устраняются.

Native `OriginalLoaderResources` объединяет bitmap-реестр, checksum,
sound registry и Frame heap. `OriginalCatalogRegistry.onLoad` исполняет
дочернюю работу непосредственно в точке запроса и получает её новый checksum.
Родительский вклад остаётся отдельным `parentChecksum`; итог всего прохода —
`checksum`. Значения сравниваются до и после **каждого** дочернего вызова.
Файлы и bitmap получает общий provider; имена персонажей не выбирают обработчик.

Суммы получены из исполненного родителя и его дочерних вызовов; разложение

стендам. Дополнительный вклад последнего `<background_end>` при EOF сохранён.
Оба stdio-варианта оставляют **400 звуков**, 15388 определений кадров,
25 стадий / 138 фаз; различия decoded tails и checksum не скрыты.

## Встроенные bitmap и BG

Четыре первых ресурса получены по ключам из EXE. Стенд извлекает размеры из
исходных DIB и передаёт их в существующую границу `43ed10`; сам wrapper `43ee50`
исполняется. Имя ключа не трактуется как отсутствующий файл на диске.

| Ключ запроса | Ресурс PE | Размер |
| --- | --- | --- |
| `shadow1` | RT_BITMAP / SHADOW1 / 1028 | 37 × 9 |
| `back99_1` | RT_BITMAP / BACK99_1 / 1028 | 126 × 9 |
| `back99_2` | RT_BITMAP / BACK99_2 / 1028 | 88 × 88 |
| `back99_3` | RT_BITMAP / BACK99_3 / 1028 | 14 × 154 |

Полный проход выделяет **829 bitmap**: 4 встроенных + 808 Object + 17 теней BG.
Обычные слои арен здесь не загружаются: их отложенный lifecycle отдельно проверен
в [BACKGROUND_LOADER.md](BACKGROUND_LOADER.md). Повторяющиеся пути не объединяются.

BG99 сохраняет разреженные поля Lee On Road из родителя; BG100 — только Random.
Необъявленные поля и записи BG17..98 сохраняют backing и неопределённую маску.
Нативный `registry.records` сохраняет прежнее связывание известных ненулевых
указателей с ordinal, где **0 — существующий ресурс**. Массив
`OriginalLoadedCatalog.backgrounds` переводит четыре доказанных указателя BG99
в **index+1 / 0=null**, как у остальных BG и Object header. Обе формы проверяются;
это явное изменение представления ссылок, не изменение данных оригинала.
Сырые Frame pointers не нормализуются вообще.

## Объём сравнения

Все 81 273 768 байт Catalog разложены без пробелов: таблица 500 Object*,
60 Stage по `149b08`, 101 BG по `990`, хвост счётчиков/имени файла.
При завершении сравниваются все байты и маски, включая неиспользованные записи.
Указатели таблицы объектов связаны с **порядковыми индексами**, не ID.

[LoadedCatalogReference](../../native/Sources/NTSDReferenceChecks/LoadedCatalogReference.swift)
дополнительно сравнивает:

- запросы родителя, внешние токены, порядок чтения файлов и полные decoded bytes;
- checksum и полный звуковой кэш при каждом возврате дочернего загрузчика;
- все байты каждого полного Object, включая 400 сырых Frame, заголовок и хвост;
- каждый bitmap wrapper, все живые/старые Frame malloc с порядком, размером,
  адресом, байтами и маской;
- порядок stage initializers/фаз и полные 60 записей после EOF.

Frame malloc addresses предоставлены на границе аллокатора; частично
перезаписанные указатели и имена сохраняются побайтно. Проверка каждого
промежуточного определения Frame остаётся отдельным корпусом
[RAW_FRAME_STORAGE.md](RAW_FRAME_STORAGE.md); здесь проверяются их количество
и полное конечное хранилище. Старые weapon-string malloc сохраняются в исходном
дампе, но нативное сравнение проверяет только конечные поля/пути оружейных звуков;
полный менеджер их времени жизни ещё не реализован.

| Корпус | Object / BG | Frame occurrences | Bitmap / Frame malloc | Сравнённые байты + такие же маски |
| --- | --- | ---: | --- | ---: |
| Весь исходный реестр, text/a5 | 137 / 17 | 15388 | 829 / 14586 | 112 063 739 |
| Весь исходный реестр, raw/00 | 137 / 17 | 15388 | 829 / 14586 | 112 063 739 |
| Чередование и повторные ID | 3 / 2 | 720 | 26 / 744 | 82 089 953 |
| Всего | 277 / 36 | 31496 | 1684 / 29916 | 306 217 431 |

Каждый корпус загружает неизменённый исходный stage.dat: 25 стадий / 138 фаз.
В числе байтов две встроенные BG дополнительно сравниваются в отдельной форме
родительских ссылок; это не число уникальных игровых данных и не процент игры.

Контрольная копия реестра вызывает Pein → District → Pein → Sasuke → District,
с повторными source ID и различными ordinal. Исходные файлы персонажей/арены
не меняются. Начальная сумма `fffff123` и токен с байтом ff проверяют совместный
wrap checksum; итог — **1496213**, звуков — **29**. Повторный Pein не добавляет
новые звуки, но получает отдельные Object/bitmap/Frame allocation.

Нет чтений до отслеженной записи в Catalog, Object или выделенных heap-записях;
это утверждение не относится ко всем stack/globals/Windows состояниям.
Тела файлов и все конечные записи/маски сохранены lossless DEFLATE с размером
и SHA-256; native проверяет распаковку и хеш. Сжатие только в dev target.

## Воспроизведение

```sh
uv run tools/oracle_loaded_catalog.py
uv run tools/oracle_loaded_catalog.py --raw-zero
uv run tools/oracle_loaded_catalog.py --interleaved
uv run tools/oracle_loaded_catalog.py --accept
swift test --package-path native --filter OriginalLoadedCatalogTests
```

Первые три команды сохраняют непринятые снимки в `build/original`. `--accept`
сравнивает все три с release Swift и только после успеха обновляет fixture и
[evidence](../evidence/loaded-catalog.json). В полном снимке остаются stdio traces
и device events; fixture опускает события, не входящие в нативное сравнение,
сохраняя все записи и их хеши. Три fixture занимают вместе 9 666 012 байт.
SwiftPM-команды запускать последовательно.

Проверка текущего этапа: все **27 прежних Swift-тестов** прошли после выделения
общего состояния (198.991 с), затем **3 новых теста полной композиции** прошли
в debug (135.451 с). Release-сравнение трёх упакованных fixture также прошло
до их принятия. Всего проверены 30 тестов; прежние fixture/evidence не менялись.

## Следующее действие и открытые границы

Новый [enabled-audio corpus](CATALOG_SOUNDS.md) выполняет этот полный каталог
с настоящими4014e0 и SetVolume из Frame/weapon registry в том же CPU/стеке.
Все137 Object и связанные записи снова совпали с native; дополнительно
сравнены400 PCM loads/буферы и path cache при каждом вызове. Старые disabled
fixtures не изменены. Далее соединить полный первый41bc90 со звуками, пулом
и UI; это всё ещё не вывод микшера или старт готового матча.

Этот каталог уже используется вместо синтетических заголовков в
[общей подготовке матча](MATCH_PREPARATION.md): World/400 Actor, исходный участок
`42d1ff..42d6ed`, 50 случаев против Swift. Перед расширением R01.2 ещё нужны
происхождение menu/RNG-входов, пролог режима и продолжение
запуска. [Буфер записи повтора](REPLAY_INITIALIZATION.md) уже создаётся и
сравнивается через настоящий вызов меню после подготовки. Загрузочный пул из
[BOOTSTRAP.md](BOOTSTRAP.md) остаётся отдельным
loading-time состоянием, а не спавном выбранных бойцов.

Открыты общий CRT `%lf` lexer/rounding, Windows stdio/startup и фактическое
binding DLL, отказные пути, освобождение/повторное использование каталога,
полные владельцы/связи типов и широкая нормализация состояния. Parent native
scanner по-прежнему явно отклоняет неполные записи и числа вне прежнего
in-range домена; весь исходный реестр внутри него, общий wrap32 есть в сканере
Object/BG/Stage. Доказательство DLL не расширяет автоматически этот parent API.

Устройство выдаёт только размеры/opaque surface, часы фиксированы, `%c` decoder
и операции файлов — объявленные host-границы. Пиксели, загрузочный экран, вывод
звука, управление, выбранный матч, весь игровой такт и Windows W этим этапом
не проверены. Приложение не зависит от reference target или EXE.
