# R02.1 / R03.1 — загрузка и ресурсы арен

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Продолжение [Object loader](OBJECT_LOADER.md). Новый стенд
[oracle_backgrounds.py](../../tools/oracle_backgrounds.py) выполняет оригинальные
`40c160..40c901`, `4148a0`, `40c030..40c0db`, `40c0e0..40c157` и `43ee50`.
Нативный [OriginalBackgroundLoader](../../native/Sources/NTSDCore/OriginalBackgroundLoader.swift)
переносит разбор целого файла, отдельную загрузку слоёв и освобождение ресурсов.
Общий decoder/scanner и конструктор bitmap используются вместе с Object loader.

Это компонент основания каталога, ещё **не подключённый к игровой практике**.
Вызовы загрузки/выгрузки слоёв в корпусе заданы стендом: это проверка функций,
а не запись работы исходного меню. Отрисовка, таймеры анимации, камера,
параллакс/перспектива, обработка прозрачности и реальный Windows W остаются
отдельными задачами. Соответствие загрузчика не доказывает вид всей арены.

## Устройство записи и инициализация

`ECX = Catalog`; аргументы `40c160`: ordinal, source ID, filename; `ret 12`.
Запись находится в `Catalog + 0x4d45db0 + ordinal * 0x990`. Второй аргумент
(source ID) **не читается в этом пути** (S полного тела функции). Исходные ID
и порядковые номера реестра различаются; перенос не сортирует арены по ID.

В начале `40c22f..40c23b` обнуляются только `+1c,+c,+10`. Остальные байты
сохраняют переданный backing и маску. При повторном разборе старые поля не
становятся неизвестными. Нулевой allocator fill сам по себе не делает поле
инициализированным. В корпусах не наблюдалось чтений BG/bitmap/heap до
зарегистрированной записи; стек и вся таблица globals этим утверждением не охвачены.

| BG offset | Размер / значение | Инструкции записи |
| --- | --- | --- |
| `0` | Int32 width | `40c362..40c375` |
| `4,8` | Int32 zboundary, пара `%d %d` | `40c38c..40c3a6` |
| `c,10` | Int32 perspective, пара `%d %d` | `40c3bd..40c3d7` |
| `14,18` | Int32 координаты тени из `%s %s %d %d` | `40c3ee..40c417` |
| `1c` | Int32 число слоёв | `40c22f`, `40c890` |
| `20 + 30*i` | 30 байт пути слоя, i = 0..29 | `40c470..40c49c` |
| `3a4` | 40 байт пути тени | `40c404..40c417` |
| `3cc` | 32 байта под имя | `40c2c4..40c34c` |
| `98c` | bitmap* тени | `40c452` |

Имя сначала читается в scratch buffer, принудительный NUL в `40c2e2`
оставляет не более **29 байт**. Подчёркивания заменяются пробелами, затем
копируются имя и NUL. Байты после нового NUL не очищаются. Контроль
`ABCDEFGHIJKLMNOPQRSTUVWXYZ_123456789 → X_Y → Q` сохраняет старый хвост,
и сравнение проверяет его тоже. Строковая длина здесь байтовая, не Unicode.

Каждый `layer:` инициализирует двенадцать Int32-полей своего индекса нулём
(`40c4b7..40c55c`), затем читает до `layer_end`. Нет обработки комментариев
или искусственного EOF после строки. Данные всех 17 исходных арен укладываются
в 30 слоёв; CastleRoof использует все 30.

| Array base + 4*i | Токен / роль | Чтение значения |
| --- | --- | --- |
| `3ec` | transparency | `40c5d2` |
| `464` | width | `40c60d` |
| `4dc` | x | `40c648` |
| `554` | y | `40c683` |
| `5cc` | height | `40c6be` |
| `644` | loop | `40c7a6` |
| `6bc` | c1 | `40c81c` |
| `734` | c2 | `40c857` |
| `7ac` | cc | `40c7e1` |
| `824` | счётчик; только нулевая инициализация в загрузчике | `40c54d` |
| `89c` | rect / rect32 | `40c6f9`, `40c76b` |
| `914` | bitmap* слоя; пока 0 | `40c55c` |

`rect32:` читает исходный signed 32-bit `long`. `rect:` после `%ld`
**всегда** выполняет `40c70e..40c737`, даже при matching failure:

```text
r = (value >> 11) & 31
g = (value >> 5) & 63
b = value & 31
rect = (((r << 9) + g) << 7) * 8 + b * 8 + 0x70707
```

Результат хранится с dword wrap. Это точные сдвиги EXE; нельзя заменять их
стандартным RGB565-конвертером. Например, `rect: -1` даёт `0x010003ff`,
а `rect32: 33 rect: nope` преобразует прежнее 33 в `0x00070b0f`.
Контроль также проверяет последующую перезапись через `rect32` и `rect: 0`.

## Порядок ресурсов и время их жизни

- `40c160` сразу выделяет и создаёт bitmap тени при каждом `shadow:`.
  Второе слово после пути — произвольная строка, имя метки не проверяется.
  Изображения слоёв на этом шаге **не загружаются**; их указатели нулевые.
- `40c030` выделяет по новой обёртке `0x1f50` для каждого слоя, вызывает
  `43ee50` и записывает указатель. Порядок исходный; повторяющиеся пути не
  объединяются. Число нарезанных кадров и четыре массива bitmap не задаются:
  в этом пути записываются только surface/width/height, первые 12 байт.
- `40c0e0` проверяет только **первый** layer pointer. Если он ненулевой,
  для каждого из `count` слоёв вызывает surface `Release` (`40c11e`), затем
  `free(wrapper)` (`40c123`). Обнуляется только первый pointer; остальные
  содержат прежние адреса уже освобождённых объектов. Тень не освобождается.
- Повторный release с первым pointer = 0 не освобождает остальные повторно.
  Следующий load создаёт новые обёртки. Новый parse сбрасывает count и поля
  только встреченных слоёв, сохраняя нетронутые старые поля/маски.

Нативные ссылки — индекс bitmap сессии + 1, **0 = null**, как в Object loader.
Это другой контракт, чем ненулевые ordinal-ссылки bootstrap. Адаптер сравнения
нормализует только 30 layer pointers и shadow pointer, если их маска определена;
числа, padding и неизвестные байты не переписываются.

`releaseLayers` выдаёт упорядоченные запросы освобождения и сохраняет набор
освобождённых индексов. Старые wrapper records пока удерживаются для снимков;
это модель хранения, не завершённый менеджер нативных графических ресурсов.
Native `parse`/`loadLayers`/`releaseLayers` не оставляют частичных изменений
при ошибке. Переданный bitmap provider может быть вызван до ошибки;
транзакционность касается возвращаемого состояния и состояния загрузчика.

## Проверка и воспроизводимость

```sh
uv run tools/oracle_backgrounds.py --suite
swift test --package-path native
```

[BackgroundReference](../../native/Sources/NTSDReferenceChecks/BackgroundReference.swift)
сравнивает decoded bytes, исходные хеши, каждую запись **до и после** вызова,
все байты/маски BG и bitmap, последовательность внешних токенов/checksum,
аллокации, порядок surface Release → wrapper free и сохранённые старые ссылки.
В метрике байты BG учитываются один раз за контрольную точку, bitmap — один раз
за аллокацию; повторная проверка входа не удваивает число. Это не процент игры.

| Корпус | Вызовы / разборы | Bitmap / releases | Сравнённые байты и маски |
| --- | --- | --- | --- |
| 17 исходных арен, text stdio, fill a5 | 69 / 17 | 334 / 302 | 2 846 256 |
| Те же арены, raw stdio, fill 00 | 69 / 17 | 334 / 302 | 2 846 256 |
| Контроль и повторные загрузки | 11 / 5 | 5 / 4 | 67 008 |
| Всего | **149 / 39** | **673 / 608** | **5 759 520** |

Исходные файлы идут в порядке `data/data.txt`: сначала разбор всех 17, затем
явные load/release/release каждой, затем повторная загрузка District. Это
302 слоя исходных арен плюс 15 слоёв повторной District; тени создаются при
17 первоначальных разборах. Контроль использует ordinal 98, крайние source ID,
отрицательные/повторные поля, частичные преобразования, прямоугольники,
длинное имя, байт ff, переполнение checksum, повторный parse поверх старой
записи, нулевое число слоёв и EOF после отсутствующего числа/второго числа пары.

Последние два случая выявили ошибку общего нативного scanner: `%d` после
завершающих пробелов обязан выставить EOF и сохранить destination. До исправления
Swift ещё раз обрабатывал старый внешний токен и добавлял checksum. Теперь
исправлен общий механизм `integer()`, а не отдельный путь арены.

Полные неизменённые снимки таблицы BG, heap, живых/освобождённых wrapper,
инвентарь обращений и stdio-вызовов сохраняются в `build/original/backgrounds-*.json`.
Отчёт [background-loader.json](../evidence/background-loader.json) фиксирует
хеши всех корпусов, входов и offline fixture. В fixture bitmap сжат **без потерь**:
стенд сначала проверяет, что последние 8004 байта равны allocator fill, а их
маски нулевые; Swift восстанавливает их и сравнивает полные 8016 байт.
Fixture и отчёт обновляются только после прохождения всех нативных сравнений.

Регрессия: `swift test --package-path native` — 22 теста без ошибок.
Все четыре прежних Object-корпуса повторно совпали, их evidence и fixture
не изменились после выделения общего bitmap-конструктора и исправления EOF.
Все 15 056 определений прежнего изолированного Frame corpus также повторно
совпали (15 025 групп, прежние 349 исключений); его evidence/хеш не изменились.

## Границы результата

Исполняются исходные декодер и bitmap wrapper; CRT/GDI/DirectDraw/allocator
остаются объявленными границами. Общая граница stdio задаёт C-locale `%s`, `%c`,
`%d`, `%ld`, `%d %d`, `%s %s %d %d` с Int32 в диапазоне; реальный MSVCR80,
ошибки открытия/аллокации, overflow, переполнение буферов и незакрытые слои
не восстановлены. Bitmap dimensions взяты из неизменённых BMP; `SetColorKey`
исполняется до opaque device call, но пиксели/цветовой ключ пока не реализованы
нативным storage-компонентом. Release/free успешны; после free стенд специально
сохраняет мёртвые байты, не утверждая поведение настоящего heap allocator.

Text/raw — два явных stdio-контракта из [исследования Object](OBJECT_LOADER.md).
Исходные хвосты после DAT-декодирования дают разные checksum: для отдельной
последовательности 17 BG это 570400 / 568906. Эти суммы **не** являются checksum
целого каталога: вклад parent, Object и Stage здесь отсутствует. Реальная
установка `_fmode` и численные края CRT остаются открытыми.

[Stage `40c910`](STAGE_LOADER.md) теперь также перенесён отдельно для всего
исходного файла. [LOADED_CATALOG.md](LOADED_CATALOG.md) теперь соединяет
parent и все исходные Object/BG/Stage с общими checksum/звуками/ссылками,
включая четыре встроенных bitmap и BG99/100. Menu-driven
выбор/смена арены, освобождение теней/каталога, полноценный
renderer и Windows-сравнение не закрыты этой работой.
