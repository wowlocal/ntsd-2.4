# R02.1 / R03.1 — непрерывная загрузка Object

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Продолжение [родительского реестра](CATALOG_REGISTRY.md). Исполняется целый
`40ef70..4122e7`, включая вызовы декодера `4148a0`, 400 конструкторов `40bbf0`,
bitmap-обёртки `43ee50` и регистрации оружейных звуков `40bd90`. **Object больше
не заменяется готовыми заголовками внутри этого стенда.** Внешний родитель,
BG/Stage, выбранный матч и устройства в этот проход не входят.

## Что перенесено

Нативные компоненты:

- [OriginalDATDecoder](../../native/Sources/NTSDCore/OriginalDATDecoder.swift):
  суффикс имени, пропуск 123 байт с продвижением ключа, побайтное декодирование
  и явно выбранный контракт текстового/непреобразованного stdio.
- [OriginalObjectLoader](../../native/Sources/NTSDCore/OriginalObjectLoader.swift):
  один непрерывный поток заголовков/оружейных параметров/кадров, общий checksum
  и звуковой кэш между объектами, данные bitmap и прямых/зеркальных спрайтов.
- [OriginalFrameLoader](../../native/Sources/NTSDCore/OriginalFrameLoader.swift):
  прежний разборщик используется и для отдельных секций, и внутри Object.
  Второго независимого набора правил кадров не появилось. Внутри целого файла
  нет искусственного EOF после каждого найденного регулярным выражением кадра.

Публичная загрузка Object сохраняет состояние сессии только при успешном
завершении: сбой не оставляет новый checksum, кэш звуков или bitmap-обёртки.
Callback `onFrame` — диагностическое наблюдение; он может быть вызван до ошибки.
Игровая практика пока использует прежний импорт; новый загрузчик ещё не соединён
с каталогом и полным тактом. Новые играбельные техники этим этапом не добавлены.

## Инициализация и поля

`40efd0..40efe0` вызывает конструктор всех 400 кадров. В полном сыром Object
после участка `40ef70..40f0c2` определены **130 894 из 152 416 байт**:
400 × 325 байт кадров и 894 байта вне них. Это результат инструкций/маски,
не обнуление всей аллокации. Оставшиеся поля сохраняют allocator backing.

| Участок / поле Object | Поведение |
| --- | --- |
| `40efe2..40f01a`, `+90,+94,+98,+9c,+a0,+a4,+a8,+ac` | HP/drop hurt и три sound pointer получают 0; три sound index получают -1 |
| `40f020..40f059`, `+700`, `+25324`, `+498` | Строки `none`, счётчик листов 0; пути small/прочие поля не приобретают выдуманные defaults |
| `40f066..40f071`, `+6f4,+6f8` | Переданные ID и type без выбора по персонажу |
| `40f077..40f0ad`, `+62c..650` | Десять dword = 3000; это исходные записи в области смещений листов, не универсальные размеры спрайта |
| `40f0b3..40f0c0`, `+b0..<3d0` | 800 нулевых байт таблицы оружейных параметров |
| `40f799..40fa5a`, `+0,+18`, `+8,+10,+20..88` | Два Int32 frame rate и 16 binary64 параметров движения. Конструктор не задаёт им нулевых скоростей |
| `40fa5a`, `+25324..<25360` | Последнее имя с NUL; байты после нового NUL сохраняются |
| `40fb48..40fd23` | HP/drop hurt и три пути/индекса оружейных звуков; пути имеют отдельные malloc-аллокации |
| `4101b0..4103f8` | Таблица weapon strength, stride 80; имя entry записывается по **предыдущему** индексу, вычисленному до `%d %s` |

Оружейный helper `40bd90` сохраняет прежний индекс, если новый путь не найден
в кэше, а поле индекса уже не равно -1. Frame sound отдельно сбрасывает индекс
в -1 (`41097b`) перед поиском. Нативная общая регистрация учитывает это различие;
синтетический поток проверяет повторное присваивание обоих видов звука.

## Листы и bitmap

В заголовке проверяются лишь первые четыре байта `file` (`40f232..40f24e`).
Числа в `file(0-69)` не разбираются. Предыдущий лист завершается при следующем
таком токене (`40f254..40f6a2`), последний — при `<bmp_end>` (`40fd28..410165`).
Индексы листов начинаются с 1; начало следующего вычисляется из суммы `row*col`
предыдущих, с dword wrap. Контрольный поток содержит обратный/нечисловой диапазон,
и исходные инструкции всё равно дают смещения из размеров сетки.

| Поле Object для листа n | Назначение |
| --- | --- |
| `+474 + 40*n` | Путь исходного BMP |
| `+628 + 4*n` | Начальный индекс спрайтов листа |
| `+650/+678/+6a0/+6c8 + 4*n` | w/h/row/col |
| `+750/+778 + 4*n` | Указатели прямого/зеркального bitmap |

Bitmap имеет размер `0x1f50`: opaque surface в `+0`, width/height в `+4/+8`,
число нарезанных кадров в `+c`, четыре массива по 500 Int32 начиная с
`+10,+7e0,+fb0,+1780`. Для индекса i:

```
x = (i % row) * (w + 1)
y = (i / row) * (h + 1)
mirrorX = bitmapWidth - x - w
```

Операции сохраняют исходную 32-битную арифметику. Порт не заменяет шаг сетки
на w/h без однопиксельной границы. Неиспользованные элементы массивов остаются
неопределёнными по маске и сохраняют исходные байты.

Сначала запрашивается `_mirror.bmp`. Если устройство сообщает отсутствие,
EXE оставляет неудачную обёртку, выделяет ещё одну из исходного BMP и вызывает
DirectDraw mirror Blt. Нативная модель сохраняет обе аллокации и `mirroredFrom`,
но не производит пиксельный Blt в этом компоненте. В корпусе kunai отказ зеркала
**принудительно задан на границе устройства**; исходный файл не удалён/не изменён.

## Непрерывный файл: kunai и кадр 49

В исходном `weapon4.dat` есть 59 маркеров `<frame>`, но оригинал загружает
58 определений. У кадра 48 не закрыт `itr`; он поглощает часть следующей секции
до её `itr_end:`. В результате кадр 49 остаётся сконструированным, с presence=0,
а itr кадра 48 получает, среди прочего, dvx=8, fall=70 и injury=55.

Нативный общий поток даёт тот же результат без правки DAT. Прежний изолированный
корпус по-прежнему содержит 349 исключённых групп: его формат не позволяет
исполнить этот переход через границу секции. Новый результат закрывает конкретный
целый файл kunai в объявленном домене; остальные четыре `heart*.dat` с подобным
обрывом здесь ещё не проверены. Число исключений старого корпуса не переписано.

## Обнаруженная граница старого декодера

Исходный EXE открывает DAT/временный файл через `fopen(...,"r"/"w")`. Старый
`oracle_dat.py` подставлял непреобразованные байты, включая завершающий CRLF
зашифрованных Naruto/Sasuke. Его прежнее побайтное совпадение остаётся верным
**для этого контракта**, но не доказывает Windows file I/O.

Microsoft описывает замену CRLF на LF при текстовом чтении, обратную замену при
записи и обработку CTRL-Z как EOF; режим без `b/t` зависит от `_fmode`.
Источники: [file translation constants](https://learn.microsoft.com/en-us/cpp/c-runtime-library/file-translation-constants?view=msvc-170),
[_fmode](https://learn.microsoft.com/en-us/cpp/c-runtime-library/fmode?view=msvc-170).
В EXE `4454ff..44550b` передаёт `_fmode` значение из `4596fc` (BSS; статически
найденное обращение). Это основание для явного текстового контракта стенда,
**не исполнение настоящего MSVCR80 или полная проверка CRT startup**.

Оба контракта теперь сохранены и проверены. Текстовый вариант даёт после последнего
перевода строки Naruto байт `98`, старый — `9b c8`; Sasuke — `a9` против `ac 95`.
После последовательной загрузки Naruto/Sasuke checksum равен соответственно
1 143 922 и 1 143 759. Заголовки/кадры в этих двух конкретных случаях совпадают,
но хвост и checksum различаются. Старые fixtures, импорт и исходные DAT не изменены.

Нативный `OriginalDATDecoder` воспроизводит оба **выбранных** контракта, включая
повторное открытие результата через текстовый поток. Он не распознаёт DAT по
наличию plaintext-маркера: оригинал проверяет только последние три байта имени.
Короткие/неполные заголовки остаются вне проверенного домена.

## Корпус и доказательство

[oracle_objects.py](../../tools/oracle_objects.py) исполняет оригинал через
настоящие возвраты. Виртуальны только CRT/файлы, аллокатор и границы устройств.
`43ed10` получает реальные размеры BMP; `43ee50` исполняется, включая SetColorKey.
Message pump видит пустую очередь, время фиксировано; звуковое устройство выключено,
но регистрация/поиск/перекрытие строк общего кэша исполняются. Временный файл
создаётся и очищается внутри виртуальной файловой системы.

`%lf` получает конечный binary64 от Python, Swift независимо разбирает ту же
десятичную строку. Это проверяет хранение/использование переданных битов, **не**
округление MSVCR80. `%d` ограничен Int32, `%s` — объявленными размерами буферов.
Пиксели, DirectSound mix, аппаратная задержка, отказ обычного bitmap/памяти,
весь Windows-цикл загрузки и другие CRT-пограничные случаи не проверены.
Текущий нативный домен ограничен девятью неперекрывающимися слотами листов,
500 нарезками на bitmap с положительным row, Int32 и размерами строковых полей
(в частности, имя кадра до 19 байт). Выход за эти границы не разрешается
приблизительным преобразованием; исходные перекрытия/переполнения требуют анализа.

Четыре корпуса, шесть загрузок:

- Naruto → Sasuke с текстовым stdio и с прежним raw-контрактом;
- kunai с нулевым backing и принудительным отказом готового зеркала;
- синтетический plaintext-поток: произвольные диапазоны file, signed zero,
  дробь `.125`, matching failure/числовой префикс, повторные имена/звуки/кадры,
  weapon entry с порядком 3 → 1 и кадр до заголовка.

Это три исходных объекта, а не шесть разных персонажей. Naruto/Sasuke загружаются
из пустого звукового кэша именно в этом порядке; это ещё не порядок всех записей
реестра и не полный исходный startup. Сырой стенд хранит целые Object, все malloc/
bitmap и маски. В исследованных Object/heap обращениях инструкций нет чтений
до наблюдённой записи; поля, которые не читались, от этого не становятся известными.

С Swift совпали **308 688 байт и маски заголовков/хвостов/bitmap**, 37 bitmap-обёрток,
1233 определения кадров после каждого появления и 2400 конечных записей кадров,
пути и общий кэш звуков, checksum и источник запроса mirror fallback.
Цифры перекрывают друг друга и прежние корпусы; они не являются процентом игры.
Отчёт и хеши: [object-loader.json](../evidence/object-loader.json).

Для кадров сравниваются все определённые числовые слова, имена, sound и bdy/itr;
сырой padding, указатели кадров и мёртвые malloc-блоки пока **не сравниваются
с нативным raw storage**. Они сохранены в полном исследовательском корпусе.
В заголовках нормализованы только известные bitmap/weapon-string pointers:
bitmap index+1 / ordinal+1, ноль — null. Это другая явно заданная кодировка,
чем непустые индексы слотов загрузочного пула. Surface bitmap заменяется на
opaque present=1/absent=0. Настоящего устройства из такого значения не выводим.

```bash
uv run tools/oracle_objects.py --suite
swift test --package-path native
uv run tools/oracle_frames.py --corpus
```

`--suite` обновляет evidence/фикстуру только после независимого сравнения каждого
корпуса с Swift. Запуск без флага создаёт только непринятый исследовательский дамп.
SwiftPM-команды последовательны. Проверяющий target отсутствует в зависимостях app.

Продолжение: BG `40c160`, Stage `40c910`, соединение дочерних загрузчиков с родителем
в исходном порядке. Параллельно нужны настоящий MSVCR80, остальные DAT и сырые
ссылки/маски Frame. Эти зависимости остаются в [R03.1](R03.1.md) и [R02.1](R02.1.md).
