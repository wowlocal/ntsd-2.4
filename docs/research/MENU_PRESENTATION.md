# R02.1/R14/R15 — завершение меню и переход World=1→2

Эталон EXE: SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Этап продолжает [MAIN_MENU.md](MAIN_MENU.md): общий вывод, latch кнопки,
реальный возврат из диспетчера и его следующий вызов при World+0=1.
Нативный World=2 теперь получается исполнением восстановленного перехода,
после чего используется в сравнении подготовки матча и буфера повтора.
Это ещё не весь путь экранов выбора и не готовое начальное состояние такта.

COM/GDI, allocator free и PostMessageA — явно предоставленные платформенные
границы. Стенд исполняет EXE до них и записывает все запросы и аргументы.
Bitmap `43f010` остаётся границей запроса, как в родительском исследовании.
Это не готовый renderer, реальный звук или исполнение Windows API.
Идентичность MSVCR80 .6195 и границы её исполнения прежние:
[CRT_SCANNER.md](CRT_SCANNER.md), [RANDOM_INITIALIZATION.md](RANDOM_INITIALIZATION.md).
Четыре строки overlay формируются настоящим DLL sprintf, не Python-форматированием.

## Курсор, latch и следующий вызов диспетчера

Общий tail рисует `451170` с frame=-1, flags=1, mirror=0 на переданной
поверхности. X ограничен сверху775. Y сначала прибавляет2 с Int32 wrap,
затем ограничивается сверху535. Нижней границы у обоих сравнений нет.
После `4028a0` и `43e940` проверяется выход, затем всегда выполняется
`44d060=457580`, даже если PostMessageA вернул0.

Сетевые ошибки родительского меню идут прямо к `4287de`: общего рисования,
уведомлений, выхода и обновления latch на этом пути нет. Проверяется реальный
epilogue, а не заменяющий его return boundary.

Следующий вызов `4246b0` с World+0=1 сначала вызывает `423910`. Если `4511ac`
ненулевой, `43ef50` освобождает его первую surface pointer и обнуляет только
эти4 байта. Даже если surface уже0, сам bitmap всё равно передаётся free,
после чего очищается `4511ac`. Остальные байты и masks остаются прежними.
Размер bitmap1f50 дополнительно подтверждён S-вызовом allocation в4238b9;
сам загрузчик423840 ещё не исполнен в этом корпусе.
Затем рисуется `45118c` в(0,0), frame=-1, flags/mirror=0, записывается
World+0=2, вызываются overlay/present и epilogue. **Курсор и latch здесь
не обрабатываются.** Проверены отсутствующий bitmap, bitmap с surface0
и bitmap с ненулевой surface, включая ошибочный результат Release.

Для tail корпус исполняет настоящий prologue до `4246eb`, затем задаёт
объявленный bounded entry `42873e`/`4287de`. Предшествующий выбор экрана
между этими точками не исполнен. Для World=1 выполняется весь вызов от
`4246b0` до ret4, без пропуска середины. Во всех случаях подтверждены
EBX/EBP/ESI/EDI, cookie, восстановление FS:0 и ESP после `ret4`.
Это не модель полного Windows thread/SEH, лишь настоящий frame этого вызова.

## Громкость и уведомления

Байт `4553f2==64` выбирает направление-1, `4553f3==64` затем заменяет его
на+1. Другие значения не считаются нажатием. При изменении `44d000+direction`
сначала оборачивается в Int32 и затем ограничивается0..100.

Музыка (`401f30`) при ненулевом `44f040` запрашивает интерфейс с IID
`56a868b3-0ad4-11ce-b03a-0020af0ba770`. Отрицательный HRESULT QueryInterface
прерывает helper. После успешного query вызывается get_Volume(+20).
Его отрицательный HRESULT, включая E_NOTIMPL, пропускает установку громкости,
но полученный интерфейс освобождается. При успехе get_Volume запрашивается
put_Volume(+1c): volume0→-10000, иначе `34*volume-3900`.
Значение, прочитанное get_Volume, не участвует в этой формуле.
Результаты helper/put/release не влияют на продолжение `402810`.

После музыки **все пять** указателей `45560c..45561c` получают вызов+3c:
volume0→-10000, иначе `((volume-100)*3800)/100` с делением к нулю.
Null-ветви у этих пяти вызовов нет. Не переносить сюда null-gate из другого
звукового helper. Эти две различные шкалы подтверждены инструкциями.

Изменение громкости задаёт `44f190=100`. Если этот таймер положителен и
`450b70==0`, выводится `Volume: %d`, затем таймер уменьшается на1.
Уведомление о записи скрывает громкость, сохраняя её таймер.

`450b70` — код уведомления. Если он знаково>0 и `450bfc==0`, `450b6c`
увеличивается с wrap. Только результат>240 очищает счётчик и код и сразу
возвращает из overlay. Иначе:

| Код | Строка | Raw COLORREF |
| --- | --- | --- |
| 1 | `Start recording '%s'...` | `ff7800` |
| 2 | `Recording file '%s' saved!` | `00ff00` |
| 3 | `Recording canceled!` | `0000ff` |

Для кода3 после sprintf счётчик увеличивается **ещё раз**, даже при
`450bfc!=0`. Поэтому его нельзя заменить одним общим увеличением.
Имя берётся из C-string `44fd98`; байты не перекодируются в Unicode.
Нативная граница исключает перезапись stack cookie длинной строкой:
recording notice занимает не более499 байт плюс NUL.

`401290` получает GetDC у **глобальной** поверхности `455608`; аргумент
surface, переданный самому `4028a0`, не используется для выбора поверхности.
При отрицательном HRESULT GetDC остальные операции пропускаются. При успехе:
SetBkColor(DC,0) → SetTextColor(DC,color) → lstrlenA → TextOutA(DC,3,531,...)
→ ReleaseDC. Ошибки GDI/ReleaseDC не изменяют таймеры и порядок продолжения.
Raw COLORREF сохранён; это не предположение о порядке RGB в новом renderer.

## Показ поверхности и выход

`43e940` получает значение `458348`. Для1 вызывается Flip(+2c) у `453e0c`,
для2 — Flip у `455634`, аргументы0/1. Для3 вызывается Blt(+14) у `455634`:
rect `453ccc` целиком, source `455608`, null sourceRect, flags01000000,
null effects. Другие значения не вызывают устройство. HRESULT вызывающим
кодом игнорируется. Rect сохраняется как16 исходных байт, без пересчёта.

Выход требует одновременно signed x<63, signed y>=514, `44d060==0`,
`457580==1`. Порядок:

1. `4019b0`: если `44eecc!=0`, release всех положительных количеств
   `458438`/`45843c` из массивов `452948`/`451db0`, затем устройства `44eecc`.
   Очищается только `44eecc`: массивы и counts сохраняются. Если устройство
   отсутствует, оба массива не читаются.
2. `401d30`: ненулевые `44f04c`, `44f048`, `44f044`, `44f040` последовательно
   освобождаются и обнуляются. Порядок обратен порядку их адресов.
3. `43d2a0`: `43d280` для `4588a8`, затем для `4588ac`; ненулевой pointer
   передаётся free и очищается. Флаги записи не сбрасываются.
4. PostMessageA(window `4546f4`, WM_CLOSE10,0,0), результат игнорируется.
5. Общая запись latch. Следующий tail без изменения кнопки не повторяет release.

## Корпус и нативное сравнение

[oracle_menu_presentation.py](../../tools/oracle_menu_presentation.py)
расширяет MainMenu, сохраняя исходный каталог, общий CRT state, пролог,
подготовку и все буферы записи. До первого menu probe исполняется201 контроль:
границы громкости и Int32, сочетания клавиш, HRESULT query/get/set/GetDC,
уведомления и оба увеличения счётчика, все режимы present, cursor wrap,
границы выхода, отсутствующие/полные списки звука (до400+2), оба replay slots,
три варианта menu bitmap и повторный tail без нового нажатия.

Это явные control/device inputs, не запись достижимых пользовательских
действий. COM handles могут повторно предоставляться между контролями;
их загрузка и внутренний COM reference count здесь не восстанавливаются.
Menu bitmap supplied allocation содержит все8016 байт: первое слово задано
на device boundary, остальные bytes/masks непрозрачны. Два free-only replay
контроля сохраняют64/128 непрозрачных байт; они **не** выдают эти блоки за
настоящие буферы записи. Полные6491672-байтные буферы проверяются далее
родительской цепочкой. Все live/dead allocations и guards сохраняются.

После каждого из510 menu probes в каждом корпусе исполняется tail/epilogue,
а при World=1 — следующий полный вызов диспетчера. Финальный пункт1 даёт
World=2 без supplied selector2 между меню и матчем. Контекст следующей
функции429730 и выбор бойцов/режима/арены всё ещё предоставляются отдельно.
Нативные callbacks `beforeMenus`/`afterProbe` соединяют сравнения в том же
порядке; ожидаемые globals/World/RNG не становятся входами нативного движка.
Предыдущий replay pointer связывается с уже проверенной allocator identity;
обычные menu tails его не освобождают, он остаётся во владении parent begin.

[OriginalMenuPresentation.swift](../../native/Sources/NTSDCore/OriginalMenuPresentation.swift)
воспроизводит общие правила без персонажных обработчиков. Его отдельный
ownership adapter сохраняет opaque allocation identities и byte provenance;
это ещё не подключённый к окну macOS backend. Проверка находится в
[MenuPresentationReference.swift](../../native/Sources/NTSDReferenceChecks/MenuPresentationReference.swift).
Полные snapshots и упорядоченные события — в packed fixtures;
[a5](../evidence/menu-presentation.json) и [ramp](../evidence/menu-presentation-ramp.json)
содержат SHA и читаемые инвентари. Raw captures дополнительно сохраняют
instruction access inventories. Исторические fixtures не переписываются.

Release-сравнение **обоих** корпусов прошло до принятия fixtures:

- **1482 возврата,66 переходов World=1→2**,177955008 байт/масок этого этапа.
- **5382 события,184 вызова настоящего CRT sprintf**,8 free,12 quit requests.
- Связанный родитель:1020 menu probes,50 подготовок/записей и324583600
  байт/масок полных буферов повтора; полный исходный каталог также сравнивается.

Два выбранных XCTest прошли за249.281s: новый корпус132.072s и прежний
MainMenu117.209s. Это проверка новых и затронутых цепочек, не повтор всего
набора тестов. Release-сборка `NTSDNative` прошла за2.53s. Все исторические
fixtures сохранились без изменений; приложение по-прежнему Practice0.4.0.

```sh
uv run tools/oracle_menu_presentation.py
uv run tools/oracle_menu_presentation.py --ramp
uv run tools/oracle_menu_presentation.py --accept
swift test --package-path native --filter '(OriginalMenuPresentationTests|OriginalMainMenuTests)'
```
