Эталон: исходный EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Участок4297ae..429e5a продолжает [включённую музыку](MUSIC_PLAYBACK.md).

## Порядок и поля

Префикс всегда копирует текущий menu44d020 в previous4512cc. Старый4512c8
попадает в caller local+3c; local+20/+28/+34/+38 обнуляются. Значение44d07c
проверяется на любое ненулевое значение, а не только1. При нуле загрузка,
сброс таблиц участников и разметка SPARK пропускаются; предыдущие ресурсы остаются.

При ненулевом флаге выполняются11 malloc(1f50) в указанном порядке.
Ненулевой результат передаётся43ee50(flags40, resource, optional0).
Нулевой результат пропускает конструктор и записывает0 в соответствующий global.
Замена старого global pointer не сопровождается его освобождением.

## Нулевой последний malloc

Если SPARK allocation вернул0, предыдущие11 global stores и три массива
участников уже записаны, но44d07c ещё не сброшен.429b21 пытается писать20
по адресу0000000c. Стенд останавливается **перед этой инструкцией**: страница0
в нём отображена только для SEH и не должна создавать ложный успешный NULL write.
Это воспроизводимый снимок границы; настоящий Windows access violation здесь
не исполняется и не заявляется проверенным.

`OriginalMenuResourceResult.nullSpark` сохраняет эту частичную нативную память
и запрещает считать участок готовым к dispatch. Это отдельное продолжение,
а не успешный пропуск SPARK. Нулевые malloc остальных десяти ресурсов не мешают
достичь429e5a при ненулевом последнем wrapper. Missing SPARK surface также
допускает разметку, если сам wrapper существует.

## Реализация и проверка

`OriginalMenuResourceLoading` использует общий `OriginalBitmapConstructor` и
`OriginalLoadedBitmap.storage`; параллельного bitmap parser или обработчиков
персонажей нет. Registry сохраняет все старые wrappers после повторной загрузки.
Native caller получает сохранённый selectionAtEntry и явный результат участка.

`oracle_menu_resources.py` заново выполняет и сверяет прежние loading/local/
control/replay/round/music родители. Оба новых первых входа продолжают4297ae
на том же CPU/stack; у control сохраняется прежняя граница предоставленного
4229cc после паузы. Музыка не отключается, menu и загруженные данные не подменяются.
Далее предоставляется только объявленный контекст повторных входов и API-входы.

Проверяются prefix, каждый global store, конец сброса массивов, промежуточный
сброс44d07c и завершение. На checkpoints сравниваются все globals и все текущие
wrappers. После каждого случая сравниваются все сохранённые bitmap records.
Surface+0 нормализуется1/0; wrapper pointers и остальные байты не нормализуются.
Проверяются настоящие ret12, ESP, EAX=this и nonvolatile registers.
World/400Actor, saved playback, replay pointers, оба replay buffers и wide-path
allocations музыки остаются неизменными в исходном исполнении. Native получает
своё ранее проверенное состояние; expected after-state не используется как вход.
После нового callback вся прежняя374-case music и полная round/input/loading
цепочка по-прежнему сравнивается.

Оба свежих полных захвата и независимые release-сравнения прошли. На каждый
проход приходится187 случаев,1049 настоящих конструкторов,1122 allocation
requests (73 null),1688 checkpoints и4468 событий. Среди них97 message/debug
пар,51 surface Release и6 остановок перед null-SPARK write. Native сравнил
82363 полные записи /731749936 байт и масок на проход. Суммарно374 случая,
2098 конструкторов и1463499872 байта/маски; повторяемый объём памяти не является
числом независимых игровых сценариев.

Помимо естественного первого входа, корпус содержит20 неизменённых повторных
входов,49 сочетаний menu/selection при load flag0, ненулевые signed границы
флага, отдельные и совместные malloc/device failures, signed HRESULT границы
для каждого ресурса, смешанные результаты и20 последовательных входов с
перезагрузкой каждые пять шагов. Обратный порядок Actor allocations и ramp
backing второго прохода сохраняются от исходной загрузки.

Только после успешной проверки **обоих** проходов приняты
[основной](../evidence/menu-resources.json) и
[контрольный](../evidence/menu-resources-control.json) fixtures. Их SHA и SHA
обоих raw corpora проверены; все16 унаследованных fixtures остались неизменными.
Оба XCTest прошли без ошибок:294.964s (146.542+148.422), включая все восемь
нативных родителей на проход. Release-сборка NTSDNative прошла за2.93s.
Запуск окна, реальное изображение/звук и чистая macOS этим не проверены.

```sh
uv run tools/oracle_menu_resources.py
uv run tools/oracle_menu_resources.py --control
uv run tools/oracle_menu_resources.py --accept
swift test --package-path native --filter OriginalMenuResourcesTests
swift build --package-path native -c release --product NTSDNative
```

SwiftPM-команды запускать последовательно. Существующие fixtures и исходные
ресурсы не изменяются. Число сравнений полных записей не является процентом
готовности игровой логики.

## Продолжение

Следующий адрес429e5a проверяет mode и выбирает тело экрана, в том числе431d10
для текущего menu10. Реальный dispatch/экран, отрисовка, paused helpers41d73b,
gameplay41e339, практика, Windows и чистая macOS остаются открытыми.

Следующий [общий bitmap draw](BITMAP_DRAWING.md) уже отдельно сравнивает
весь43f010/43ef70 до Blt и ret24. Это изолированный корпус с явными входами,
не продолжение текущей CPU-цепочки. В естественном состоянии после ресурсов
4511a0/451178 ещё0; для полных draws431d10 требуется их ранняя загрузка.

Статические ориентиры следующего этапа (S, ещё не D/native):

  остальные ветви проверяют текущий menu. Естественный вызов431d10 находится429eb2.
- 431d10..432aaa: тело экрана имеет три настоящих ret16. Начало очищает451b7c,
  вызывает415160, при null4511ac загружает фон через423840, затем4236d0 и draw
  calls. Восстановить связанные helpers и переходы, не ограничиваться префиксом.
  Уточнение:431d10 выбирает режим игры, не персонажа. Его общий431b70 и keyboard
  transitions4322ad..4328f8 отдельно перенесены/сравнены в
  [MODE_SELECTION.md](MODE_SELECTION.md); соединение целого экрана ещё открыто.
