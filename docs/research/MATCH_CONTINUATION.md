# R02.1 — оставшаяся обработка меню и возврат

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.

[OriginalMatchContinuation](../../native/Sources/NTSDCore/OriginalMatchContinuation.swift)
продолжает исследование после [пролога](MATCH_PRELUDE.md),
[подготовки](MATCH_PREPARATION.md) и [создания записи](REPLAY_INITIALIZATION.md).
Объём: **`42d704..42e0f9`**, включая ветвь `450c2c==1`, команды меню и
настоящий `ret 12`. Это ещё не исполнение всей `429730`: более ранний ввод,
выбор команды и решение о начале матча остаются заданными входами.

## Как построена проверка

[oracle_match_continuation.py](../../tools/oracle_match_continuation.py) сначала
повторно исполняет неизменные 25 сценариев соответствующего a5/ramp-пролога,
включая весь каталог/bootstrap, подготовку и запись. Каждый полученный сценарий
сравнивается с закреплённым capture, затем также проверяется прежний cleanup.
Его освобождение буфера записи — отдельная исследовательская операция, не новое
правило запуска игры; продолжение не обращается к этому буферу.

Далее полученный World/Actor/BG/global state проходит последовательность новых
проб без восстановления ожидаемого состояния между ними. Входы каждой пробы
записаны отдельно: подтверждение, код команды, режим, параметры/флаги и RNG.
Для охвата схем команд меняются **входные байты таблицы RNG**, а не результат
`417170` или переходы оригинальной программы. RNG исполняется целиком.

[MatchContinuationReference](../../native/Sources/NTSDReferenceChecks/MatchContinuationReference.swift)
сначала заново проверяет весь нативный родительский corpus. Его `onFinished`
передаёт полученное нативное состояние в новые проверки. Сравниваются все
400 Actor, World, 101 BG, globals, маски, новые bitmap, освобождения и общий
порядок конструкторов, RNG, списков кандидатов, музыки, звука и заливки.
Ни один ожидаемый снимок не становится входом native.

Ссылки сохраняют прежние представления: Object/Actor — ненулевые ordinal,
BG bitmap — index+1 с zero-null, Frame — сырые адреса. Неизвестные слова
не нормализуются. Новые bitmap получают адреса отдельной арены стенда
`26000020...`, чтобы удерживать освобождённые записи всех проб. Полные байты,
маски и защитные области этих записей проверяются и после всей цепочки.

## Обычные команды

`confirmation` — Int32 из локального `esp+18`, команда — Int32 `44d06c`, режим —
`451160`. Ненулевое подтверждение включает следующие действия. Все сложения
и вычитания ниже сохраняют 32-битное переполнение.

| Команда / адрес | Действие |
| --- | --- |
| 4, `42d715..42d753` | Вычесть 1 из `450c30`. При отрицательном результате и `458428==0`, либо результате ниже -1, записать 2; затем звук подтверждения |
| 5, `42d758..42d787` | Звук, `44d020=10`, `457580=0`, полный общий сброс ввода `431c70` |
| 1, `42ddc4..42deb5` | Звук; всем восьми seat поставить status `451288=0` и latch `451268=1`. Только при `451228==1` записать selected ordinal `451248=-1`. Затем `44d078=150`, `4512c8=0` |
| 3, mode=1, `42decc..42def7` | Звук; stage `450b94 += 10`; только точный результат 60 становится 0 |
| 3, прочий mode, `42df0b..42df5e` | Звук; `44d028=0`; BG100→99, BG99→0, иначе BG+1. Только результат, равный count BG, заменяется на100 с `44d028=1` |
| 2, `42df64..42e0b0` | Звук, новый случайный персонаж для каждого seat с `451228!=0`; status/activity здесь не проверяются |

Сброс выбранного персонажа использует **`==1`**, а новый подбор — **`!=0`**.
Нельзя превращать оба поля в один Boolean. Без подтверждения команды 1–5
не исполняются. В самом конце, независимо от подтверждения: если `44d078<=0`
и `4512c8==0`, поставить `4512c8=1` (`42e0b6..42e0c8`).

## Общий случайный подбор

`42d840..42d8d1` и `42dfd0..42e05d` строят одинаковый список кандидатов:
ordinal от **1** до count Object-1; Object type (`+6f8`) равен 0; исходный
ID (`+6f4`, signed Int32) **меньше 30**; ordinal отсутствует во всех восьми
текущих `451248...451264`. Неактивные seat также исключают свой ordinal.

Список строится заново для каждого seat в исходном порядке. После RNG
выбранный ordinal немедленно записывается в соответствующий `451248+4*seat`
и Object reference базового Actor. Следующий seat видит уже изменённый список.
Нативная реализация использует один механизм для обеих ветвей; имена персонажей
и индивидуальные обработчики не нужны. Проверяются сами списки перед RNG.

Для команды 2 используется stream `ea`, для ветви ниже — `e1`.
Пустой список в оригинале приводит к чтению первого элемента stack scratch без
новой записи в него: значение может быть старым или неизвестным. Происхождение
этого значения здесь не восстановлено; native явно отклоняет такой вход.
В исходном полном каталоге исследованные списки непусты. Каталоги с count<=1
и исчерпанными кандидатами этим corpus не покрыты.

## Ветвь `450c2c==1`

Проверяется точное равенство 1 в `42d795`. Эта ветвь выполняется между командами
4/5 и командами 1/2/3, также **без подтверждения**. Назначение флага во всём UI
пока не восстановлено; имена `demo-*` у проб не доказывают готовность режима игры.

1. Вызвать `4025d0` (здесь проверена только выключенная музыка `44d010=0`),
   обнулить `44d020` и **все 400** activity bytes. Поставить `44d028=1`.
2. Выбрать BG через RNG `(e0,count-2)`; результат count-3 заменить на99.
3. Заново подобрать всех восьмерых по общему правилу выше, независимо от флагов.
4. Сохранить `450c2c=1`. Повторно сконструировать **только Actor10..17**,
   скопировать Object из базового seat и его `+90` в Actor `+31c`, поставить
   frame `+8=75`. X: RNG `(e2,width/2)` + width/4 с усечением делений к нулю;
   Z: RNG `(e3,upper-lower)` + lower. Обновить и целые, и binary64 координаты;
   `+308=200`, `+354=slot`. Поле Y и остальные defaults приходят из конструктора.
5. Выбрать схему команд через RNG `(e4,30)` по таблице ниже.
6. У каждого активного Actor с team=0 записать team=slot+10. Обнулить десять
   dword `450c04..450c28`, освободить слои всех BG и загрузить выбранный, кроме99.
   Поставить `44d034=1`, `450bbc=0`, очистить `(0,0,794,550)` цветом0,
   затем `450bdc=0`.

| Результат e4 | Команды и активность |
| --- | --- |
| 0..6 | Активны все 10..17. Team10=0; каждому из 11..17 — RNG `(e5,5)` |
| 7..17 | Активны все восемь; команды 1 у10..13 и2 у14..17. Если RNG `(e6,3)==0`, выключить activity13/17. Если RNG `(e7,6)==0`, записать team13/17=3, в том числе неактивным |
| 18..24 | Команды 1,1,2,2,3,3,4,4; включить первые `4+2*RNG(e8,3)` слотов начиная с10 |
| 25..29 | Team10..13=0; включить первые `2+RNG(e9,3)` слота начиная с10 |

В отличие от общей подготовки, здесь **нет** повторных конструкторов неактивных
20..399, переноса team базового seat, mode-dependent MP, сброса RNG counter
или создания нового буфера повтора. Сохранность этих областей проверяется.

## ABI, устройства и ограничения

Стенд задаёт saved-register frame, прежний SEH и cookie по настоящему прологу
`429730..429765`. После новых ветвей исполняется весь эпилог `42e0d2..42e0f9`,
включая настоящий `4450b2` и `ret 12`. Проверяются восстановленные EBX/EBP/ESI/EDI,
FS:0, адрес возврата и итоговый ESP. Native переносит состояние игры; Windows SEH
и cookie в приложение macOS не входят. Это не исполнение самого раннего пролога/UI.

Звук использует общий перенесённый `401a30`, сброс ввода — общий `431c70`.
Условия отсутствующего устройства/буфера и ответы COM 0/`80004005` заданы явно.
Реальные sound/fill helpers исполняются до методов устройства; звук и пиксели
не выводятся. Enabled DirectShow `4025d0` остаётся неподдержанным. Полные файлы
исходного каталога неизменны; renderer, AI и полный такт этой проверкой не закрыты.

кандидатов, 150 методов sound buffer и 68 заливок. Метрики не означают готовность
всей игры или проверку аудиовизуального вывода.

Весь `swift test`: **34 теста, 0 ошибок, 811.498 с**. Новая проверка полных
продолжений и родительских цепочек прошла за 172.950 с. Предыдущие корпуса
пролога, подготовки, записи, каталога и игровых механизмов также прошли.

```sh
uv run tools/oracle_match_continuation.py
uv run tools/oracle_match_continuation.py --ramp
uv run tools/oracle_match_continuation.py --accept
swift test --package-path native
```

Нужны закреплённые raw capture полного каталога и двух прологов в
`build/original`. Их хеши и 25 сценариев проверяются перед продолжением.
`--accept` сравнивает обе упакованные записи нативно до сохранения fixtures.
Старые fixtures не изменяются. Большая оболочка corpus допускает до64 MB;
отдельные сжатые записи сохраняют прежний лимит20 MB. Это формат тестовых
артефактов, не игровых ресурсов или файлов повтора.

Статические ориентиры следующего этапа, **ещё без исполнения и переноса**:

- `422ac0..422af7` делает 3000 вызовов CRT rand (IAT447198), пишет
  `rand()%255+1` в `44ff90..450b47`, затем `450b48=0`. Индекс `450bcc`
  и счётчик `450c34` эта функция не сбрасывает. В исходном PE эти области — BSS,
  поэтому исходные нули сами по себе не являются готовой игровой таблицей.
- Вызовы генератора — `427a2c` и `427a71` в более раннем меню. Их входы
  и весь путь к подтверждённому старту ещё требуют исследования.
- `43cf55/43cf5a` передаёт timeGetTime в CRT srand (IAT4470ec).
  Нужно сохранить все последующие потребления того же CRT-генератора, включая
  обнаруженные вызовы rand `414774/431a42/431a86`; нельзя считать, что генератор
  таблицы вызывается сразу после seed без промежуточных потребителей.
