# R02.1/R13/R15 — замена bitmap информационной панели

Эталон — EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Выполнено всё тело `43cc60..43cf3a` вместе с настоящими constructor `43ee50`
и destructor `43ef50`. Проверены обычный возврат, stack balance, сохранение
nonvolatile registers и восстановление SEH chain. Это отдельный helper;
родитель `4236d0` и его caller `427127` этим корпусом ещё не исполняются.

## Владение и порядок операций

1. Прочитать bitmap pointer `458420`. При ненулевом значении вызвать `43ef50`.
   Тот читает surface из wrapper+0, при ненулевом вызывает Release и только
   после возврата записывает wrapper+0=0. Нулевая surface пропускает обе операции.
2. Освободить wrapper, затем записать `458420=0`. При изначально нулевом pointer
   destructor/free и эта запись пропускаются.
3. Запросить malloc(`1f50`). При ненулевом ответе вызвать настоящий `43ee50`
   с flags=`40`, optional=0 и строкой по `453d40`. Устройство берётся из `457578`.
4. Записать в `458420` полученный wrapper, включая0 при неудачной аллокации.
5. При null wrapper или null surface вернуть0. В остальных случаях записать
   все44 поля прямоугольников, затем count=11, вернуть1.

Предыдущий bitmap освобождается до новой аллокации: ошибка новой загрузки его
не восстанавливает. Missing resource сохраняет новый wrapper с null surface и
нетронутыми width/height/count/rectangles. При отрицательном SetColorKey HRESULT
общий constructor сохраняет уже полученные width/height, выводит diagnostics,
освобождает новую surface и обнуляет только wrapper+0. Оболочка остаётся живой
до следующего вызова. Неотрицательный SetColorKey считается успехом, включая
положительные значения. Результат Release не влияет на продолжение.

Native `OriginalMenuPanelBitmap` вызывает прежний общий `OriginalBitmapConstructor`
без изменений. Адреса — непрозрачные tokens платформенного allocator.
`records` хранит отдельные поколения выделений: address, live, исходный input,
raw surface binding и полный bitmap record. После free старое поколение остаётся
в проверочном состоянии с байтами и маской на момент освобождения. Тот же адрес
может быть выдан новой аллокации; она получает свой явно предоставленный backing.
Повторная выдача ещё живого адреса отвергается.

В source harness освобождённые bytes/masks также замораживаются до переиспользования
физической памяти. Native не получает эти после-снимки как вход. Surface+0
нормализуется только в известном поле wrapper; raw token отдельно сравнивается
для каждого поколения и используется в Release. Остальные слова не нормализуются.

## Буквальная разметка

`43ccf2..43cf10` содержит фиксированные записи. Для каждого frame сначала x
в `+10+4i`, затем y в `+7e0+4i`, width в `+fb0+4i`, height в `+1780+4i`.
Count в `+0c` записывается последним.

| Frame | x | y | width | height |
| --- | ---: | ---: | ---: | ---: |
| 0 | 0 | 0 | 397 | 34 |
| 1 | 397 | 0 | 397 | 34 |
| 2 | 0 | 34 | 198 | 194 |
| 3 | 198 | 34 | 198 | 194 |
| 4 | 396 | 34 | 198 | 194 |
| 5 | 594 | 34 | 198 | 194 |
| 6 | 0 | 228 | 198 | 194 |
| 7 | 198 | 228 | 198 | 194 |
| 8 | 396 | 228 | 198 | 194 |
| 9 | 594 | 228 | 198 | 194 |
| 10 | 0 | 422 | 794 | 128 |

Ширина и высота bitmap не меняют эти значения. Координаты не обрезаются по
размеру изображения. Все нетронутые слоты, bytes и defined masks сохраняются.
Сравнение фактического вывода этих кадров относится к следующему draw/device пути.

## Исходные ресурсы и контрольные входы

`sprite/sys/ad0.bmp` и `sprite/sys/ad1.bmp` отсутствуют в закреплённом
дистрибутиве; это проверяется перед capture. Первые два случая отдельно вызывают
helper с этими путями и отсутствующей surface. Они не утверждают, что полный
Windows startup достигает bitmap helper после неудачного `43c780`.

Для успешных ветвей поле пути явно получает имена трёх оригинальных embedded DIB:
MENU_CLIP794×500, MENU_BACK1 809×547, SPARK612×256. Сами DIB сохраняются с SHA и
проверенными заголовками. Эти входы проверяют общий helper с существующими
ресурсами; они не создают замену отсутствующим ad-картинкам. Native не добавляет
такие контрольные привязки в игру.

## Дифференциальная проверка

Два независимых прохода: A5 backing/прямое размещение и ramp/обратное размещение.
В каждом59 случаев: два отсутствующих исходных пути, все16 сочетаний старого
и нового bitmap (null allocation, missing resource, failed key, live surface),
пять signed HRESULT для трёх DIB и десять последовательных замен с переиспользованием
адреса и различными результатами Release.

Каждый проход совпал с native по следующим наблюдениям:

| Наблюдение | Число |
| --- | ---: |
| Constructor / destructor returns | 51 / 50 |
| Malloc / null / повторно выданные адреса | 59 / 8 / 22 |
| Всего событий / parent writes | 1 406 / 1 009 |
| Release / free | 37 / 50 |
| Успех / неуспех | 20 / 39 |
| Полные records / bytes и masks | 1 437 / 13 768 544 |

В конце прохода сохраняются51 поколение на29 уникальных адресах. После каждого
вызова сравниваются весь global region, каждое живое и освобождённое поколение,
input binding, surface, live flag, все bytes/masks. По порядку сравниваются
constructor/destructor/free, device requests/diagnostics, global и metadata writes.
Child return sites — `43cc9c` после destructor и `43ccd9` после constructor.
Их реальный ret/pop и nonvolatile ABI проверяются источником; метаданные возврата
проверяет native comparator. Malloc и COM остаются объявленными границами.

```sh
uv run tools/oracle_menu_panel_bitmap.py
uv run tools/oracle_menu_panel_bitmap.py --control
uv run tools/oracle_menu_panel_bitmap.py --accept
swift test --package-path native --filter OriginalMenuPanelBitmapTests
swift build --package-path native -c release --product NTSDNative
```

Release-сравнения [основного](../evidence/menu-panel-bitmap.json) и
[контрольного](../evidence/menu-panel-bitmap-control.json) корпусов прошли до
принятия fixtures. Все27 прежних fixture SHA неизменны; новые raw/packed SHA,
длины и полное обратное распаковывание проверены. SwiftPM выполняется последовательно.
Два новых XCTest прошли за0.474 s, release NTSDNative собран за2.36 s.
Shared constructor не менялся; оконный и графический вывод этим не проверены.

Следом — cache/default writers `43c690/43c710`, затем соединение с уже проверенным
`43c780` во всём `4236d0` через настоящий `427127` после ранних ресурсов/настроек/
первого рисунка. Более ранний startup `43cf40`, worker, весь начальный экран,
пиксели, интерфейс приложения, законченный матч и Windows остаются открытыми.
Аллокатор здесь не доказывает происхождение реального Windows heap backing.

[STARTUP_PANEL](STARTUP_PANEL.md) теперь включает весь helper в настоящем
43cf94..43cfb4:32 пары вызовов проверяют собственные поколения и повторную
выдачу адресов. Ошибочный новый wrapper сохраняется через defaults; поздний
отказ нативного общего вызова откатывает и освобождение старого поколения.
Все118 прежних bitmap-контролей сохранены, Windows/device ещё не проверены.
