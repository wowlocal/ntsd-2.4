# R02.1/R15 — чтение настроек после ранних ресурсов

Эталон: EXE `3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`;
VC80 DLL `c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
Исходный `data/control.txt` имеет SHA-256
`cc7f84872d9b95fe64c1c95cc7895b3e2c0a52a3ae0f7f7970f0b3c56b7037c0`.

Первый вход теперь непрерывно проходит свежие World constructor/ранние ресурсы,
call `427089 → 423480`, настоящий ret в `42708e` и store `427092` до `42709b`.
`fscanf` (`78175f0b`), `fgets` (`7817a00d`) и `feof` (`78179e0d`) исполняются
из исходной DLL **на том же CPU/стеке**, что и EXE. Нативный
`OriginalSettingsLoading` продолжает собственное состояние после независимого
World/`OriginalFrontMenuResources`, а не загружает ожидаемый снимок родителя.

## Порядок

`4234a2` открывает `data\control.txt` в режиме `r`. Проверки результата нет.
Далее 44 отдельных `%d`: четыре группы по 11 Int32 в `44fb70 + 50*player`,
шаг поля 4. Используется общий нативный `OriginalFrameScanner`, с прежним
32-битным переполнением и потреблением знака при неудачном преобразовании.
Неудача не обнуляет прежнее значение и не прекращает остальные попытки чтения.

`423511` читает `%s %s %s %s\n` в `44fcc0/cb/d6/e1`. Ограничения ширины у `%s`
нет: длинное имя может перекрыть соседние поля, а следующий token перезаписать
часть предыдущего. Четыре прохода `423520..42355e` заменяют backtick на пробел
до NUL каждой текущей строки, без ограничения длиной 11 байт.

Затем `%d\n` записывает `450be8`, потом `450be4`. Завершающий whitespace формата
потребляет весь следующий пробельный участок, включая пустые строки перед
профилем. Имена настроек здесь не выводятся из их адресов или значений.

Два `fgets(...,100,FILE)` читают `44fd18` и `44f890`: максимум 99 входных байт
плюс NUL. Исходные циклы удаляют с конца только space, CR и LF; TAB сохраняется.
NUL внутри файла не прекращает `fgets`, но последующая обработка C-строки
видит только префикс до NUL. Остальные записанные байты всё равно сохраняются.

В `42363d` обнуляется только первый байт `44f900`. Пока `feof` равен нулю,
`fgets(...,100,FILE)` пишет в stack scratch, после чего вся C-строка вместе
с NUL добавляется к `44f900`: сначала `rep movsd`, затем остаток `rep movsb`.
После каждого добавления снова вызывается `feof`.

**Результат `fgets` не проверяется.** Если последняя строка заканчивается LF,
следующая попытка чтения устанавливает EOF и оставляет прежний scratch.
Оригинал ещё раз добавляет эту строку. Ровно 99/198 байт без LF также могут
требовать дополнительного чтения для обнаружения EOF. Проверяются все записи,
а не только отображаемая строка. Длинное описание может затронуть соседние
globals; оно не обрезается до придуманного безопасного размера поля.

После `fclose` настоящий helper возвращает его EAX, сохраняя nonvolatile
registers. `427092` записывает в `44d068` **caller EBX**, а не literal zero.
В естественном раннем пути EBX=0. Нативный `flagClearValue` по умолчанию равен0;
контрольные входы могут явно предоставить другое значение caller.

## Проверка и границы

Два свежих корпуса по94 случая: A5/прямые allocations и ramp/обратные allocations.
Первый случай использует исходный файл с явно объявленным CRLF→LF входом `_read`.
Далее проверяются raw bytes, три размера read chunk (1/7/4096), EOF/пустой файл,
строки с TAB/NUL/backtick, перекрывающиеся имена, 99/100/198/1500 байт описания,
повреждённые числа, знак без числа, 1024 цифры, close results и load flags.

Последующие случаи — **явные повторные входы caller `427089`** на сохранённом
состоянии, а не полные новые итерации меню. Globals и scratch продолжают
собственные прежние значения. При null FILE источник останавливается перед
первым вызовом `fscanf` в `4234db`; native возвращает `.nullFile` без очистки
флага. CRT invalid-parameter handler/завершение Windows этим не исследуются.
Последующий supplied caller после такой остановки не изображает реальное
восстановление приложения после ошибки.

Именно эта проба выявила ошибочную нативную literal-zero запись: EBX остался
`44fb70` внутри прерванного helper. Уточнён вход вызывающей функции и нативная
запись. После свежего захвата **все исходные события, снимки и blobs совпали
с предыдущим захватом буквально**; добавлено только описание входного EBX.

На корпус: 4 371 actual CRT scan, 348 gets, 255 feof, 93 настоящих settings
returns, одна null-FILE boundary, 7 564 события / 2 310 записей родителя.
Сравниваются полные globals и 500 байт scratch с масками после каждого CRT
возврата, после helper и после caller: 10 324 записи / 240 777 836 байт и масок.
Отдельно сравнивается свежий нативный родитель с 24 настоящими конструкторами.
Источник проверяет неизменность World и всех bitmap records после каждого случая.

Перед первым helper scratch backing явно задан A5/ramp. Его500 байт заканчиваются
перед cookie; это не заявление о размере исходного C-массива. Native сохраняет
нетронутые байты/маски и явно отклоняет строку без NUL в предоставленной области.
Весь Windows stack lifetime, дальнейший выход за глобальную область, read errors,
locale вне C, открытие/закрытие файла и низкоуровневая text translation остаются
открытыми. Fopen/fclose — платформенные ответы; `_read` получает объявленные
байты. PTD предварительно инициализируется настоящим `_initptd` в общем CRT
стенде, затем переносится как binding одного потока. Активация DLL в Windows
имеет прежнее ограничение из [CRT_SCANNER.md](CRT_SCANNER.md).

Оба независимых release-сравнения прошли до принятия
[основного](../evidence/settings-loading.json) и
[контрольного](../evidence/settings-loading-control.json) fixtures.
Все21 прежних fixture hashes сохранились; SHA обоих новых raw/packed корпусов
и полное обратное распаковывание проверены. Изменение старого front comparator
добавляет только необязательный callback собственного проверенного состояния;
его прежние145-case корпуса сохраняются.
