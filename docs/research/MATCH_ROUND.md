# R02.1 / R10 / R11 — исход раунда и восстановление участников

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Вход `41d714`, выходы `41d73b`, `41e339`, `4229cc`, `422a95`.
**Статус: объявленный обработчик перенесён, оба расширенных свежих исходных
корпуса совпали с Swift. Паузный вывод, тела следующих стадий и R02.1 открыты.**

## Граница и происхождение

[oracle_match_round.py](../../tools/oracle_match_round.py) заново исполняет
всю первую загрузку, естественные local/control/received/replay участки.
Три исходных загрузочных transport воспроизводятся побайтно, первые local,
control и replay случаи сверяются вместе со всеми blobs. Только затем
первый новый случай продолжает `41d714` на том же CPU/стеке/загруженном мире.
В основном проходе естественный выход — menu; в контрольном — pausedRendering.
В обоих случаях menu остаётся 10, mode — 0; только неприостановленный проход
увеличивает периодические счётчики. Menu10 нельзя вручную заменить на0 ради
перехода в физику: требуется восстановить настоящий следующий обработчик.
Это фактические выходы предоставленного начального контекста, не выбранный бой.

[MatchRoundReference](../../native/Sources/NTSDReferenceChecks/MatchRoundReference.swift)
получает собственное нативное состояние через `ReplayTickReference.onNatural`.
Ожидаемые после-состояния не становятся входами движка. После callback продолжают
проверяться весь прежний replay corpus и его control/local/loading родители.
Шесть fixtures каждого прохода закреплены SHA. Контроль использует обратное
размещение Actor, ramp backing и естественную паузу предыдущего корпуса.

Остальные случаи задают явные входы: globals, activity, связи World/Actor/Object,
здоровье, команды, поля восстановления и платформенные результаты. Исходные
Object загружены из оригинального каталога; заголовки не заменяются синтетическими.
Два полных буфера и saved settings унаследованы как объявленные входы; их
происхождение из файлового playback startup здесь не восстанавливается.

`pausedRendering` останавливается **перед** `41d73b`: фон, объекты, HUD и PAUSE
ещё не рисуются. Остальные выходы останавливаются перед игровыми проходами,
телом меню или общим эпилогом. Они не заменены пустыми вызовами. Новый
[OriginalMatchRound](../../native/Sources/NTSDCore/OriginalMatchRound.swift)
возвращает эту границу явно, вместе со значением caller local `+64` там,
где оригинал его определил. Это не весь `41bc90` и не новый режим Practice.

## Пауза, счётчики и живые команды

`41d714..41d734` пишет `450c00 = (450bfc == 2)` независимо от локальной паузы.
При паузе следующие действия относятся к отдельному пути отрисовки. Без паузы
`450bfc==2` меняется на 1; `450bd8` получает `1-old`, а `450bd0/450bd4` —
`(old+1)%12` и `(old+1)%3`. Сложение/вычитание 32-битное с переполнением,
остаток знаковый. При произвольных входах переключатель не обязательно 0/1.

При mode != 1 оригинал обходит все 400 мест и считает 40 команд. Участник
учитывается, только если activity ненулевая, signed HP `+2fc` положителен,
Object type `+6f8` равен 0, а signed team `+364` находится в 1…39, кроме 5.
Ссылки читаются из World; повторные ссылки учитываются повторно. При последующем
обходе команд `450bf8` получает номер каждой непустой команды по возрастанию.

Если живых команд меньше двух, menu равен 0 и либо `451b7c==1`, либо mode != 4,
таймер `450bdc` увеличивается. При отсутствии команд winner становится -1.
При ровно новом значении 80 выполняются исходные звуковые действия. Для modes
0/2/3/4 музыка не останавливается, для 5 также не ставится `44d02c=1`; для
остальных вызывается весь `402100`. Звук `401a30(&45561c,0)` запрашивается
во всех этих ветвях. Неудачный HRESULT не отменяет последующие вызовы.

Когда условие завершения не выполнено, modes 2/3 сохраняют найденный либо
прежний winner; остальные пишут -1. Таймер при этом **не сбрасывается**.

Mode 1 при ненулевом входном menu пропускает сканирование. Иначе весь пул
проверяется теми же условиями, без раннего выхода при первом живом участнике.
Caller local `+64` получает 1 только при отсутствии подходящих участников.
Таймер растёт при этом флаге или signed `450ba8>0`. При `450ba8<=0` и новом
таймере 80 устанавливается `44d02c=1`, останавливается музыка и запрашивается
тот же звук. Положительное `450ba8` обходит эти действия на отметке 80.

`402100` при ненулевом `44f04c` сначала вызывает `44f044` method+24, затем
`44f04c` method+20 с binary64 +0. Указатели не освобождаются и не очищаются.
Входы COM являются объявленными непрозрачными handles; звуковой слот связывается
с загруженным registry buffer явно. Настоящее назначение startup слота,
работа DirectShow и физический аудиовыход остаются открытыми.

## Отметки 145/350 и подтверждение

Ровно при `450bdc==145` и `450c2c==0` оригинал возвращает таймер к 144.
Другие значения не ограничиваются этим правилом. При таймере >=350 сначала
идёт восстановление участников и смена режима меню — даже если menu уже
ненулевой. Проверка обычного menu выполняется только на оставшемся пути.

При menu==0 и таймере >=144 читаются `+d1/+d2` первых восьми мест. Требуется
байт **ровно 1**, activity/HP/status не проверяются. Ссылки разрешаются по месту.
При mode1, `450c2c==0` и `450ba8==1` первое подтверждение меняет `450ba8` на 3.
В остальных mode1 случаях продолжение разрешено только при `450ba8` равном
0 или 2. Остальные modes обходят это ограничение.

Разрешённое подтверждение записывает `(450b94/10)*10` со знаковым делением
к нулю, ставит таймер 350 и очищает `450c2c`. Поздние места видят изменения
ранних. Выход этого вызова всё ещё `gameplay`: восстановление при >=350
будет проверяться в следующем проходе, а не немедленно после нажатия.

## Полный проход восстановления

`41ddf2..41e0e1` обходит все 400 мест с activity !=0 без фильтра HP/type.
Активированный или изменённый ранним местом объект влияет на последующий обход.
Нативный механизм разрешает исходные ID через загруженный каталог, сохраняя
порядок и повторные записи.

1. Если Actor `+324 > -1`, ищется первая запись с этим source ID. При успехе
   меняется Object pointer и `+324=-1`; при неуспехе флаг сохраняется. В обоих
   случаях остальные варианты для этого места пропускаются.
2. Если текущий source ID равен **50** и `458428==0`, выполняется поиск source
   ID **6** и условная замена Object pointer. Остальное восстановление места
   снова пропускается. Это исключение EXE `41de84..41dedb`, а не ограничение
   прототипа по персонажу.
3. Иначе при `+328 > -1` поле очищается до -1, `+338` получает 900, а `+32c`
   выбирает место второго участника. По всему каталогу: совпадение ID с текущим
   `+330` меняет Object исходного Actor; иначе совпадение с текущим `+334`
   выполняет весь `4061d0` для второго Actor, назначает Object/header+90,
   позиции 580/-200/300 и активирует его место. Поиск не прекращается после
   первого совпадения. Поля исходного Actor перечитываются после конструктора.

Затем HP и recoverable HP второго Actor получают половины исходных значений,
после чего половины записываются исходному Actor. Деление знаковое к нулю.
При ссылках на один Actor порядок даёт повторное деление, его нельзя заменить
одним заранее вычисленным значением для двух назначений. Копируются x/z;
второму задаются y=0 и соответствующие binary64 координаты. Обоим обнуляется
`+40`, второй получает byte `1-facing` с переполнением; обоим назначается frame
112 и MP `+308=0`; команда второго копируется из текущей команды первого.
Constructor сохраняет нетронутые bytes/masks прежней аллокации.

Нативная область поддерживает ссылки на принадлежащие миру Actor и каталог.
Выход `+32c` за 0…399, неизвестные Object pointers или доступ за памятью не
эмулируются как корректное поведение игры. Переход кадра 112 здесь является
прямой записью оригинала, а не вызовом ещё не перенесённого frame handler.

## Выход из раунда

После восстановления menu получает 28 для mode2, 128 для mode3, 202 для
mode4, иначе 2. `450bdc` очищается и выполняется весь `431c70`. При ненулевом
`450b88` и menu !=10 устанавливается mode6; при ненулевом playback pointer
выполняется весь `43df00` и возврат двух флагов из буфера. Затем очищаются
`450b88/450b84`, menu становится 10. Освобождения буфера здесь нет.
Выход направлен в `422a95`, не в обработчик меню текущего вызова.

## Проверка

Корпус проверяет modes/menu/timer, все исходные типы Object, диапазон команд,
пять unrolled lanes всего 400-местного пула, activity/HP, повторные ссылки,
точные байты подтверждения, восстановление по ID, оригинальную ветвь 50→6,
реальные конструкторы, самоссылки и знаковое деление/координаты. Последовательность
из 275 участков продолжает таймер от 75 до перехода при 350 без новых входов
в постоянное состояние после первого вызова. Caller stack/регистры задаются
между участками; физика, AI, вывод и полный игровой такт здесь не выполняются.

Сравниваются полные World/400 Actor bytes/masks, globals, saved settings,
указатели и оба целых replay buffers. Дополнительно — команды и окружающие
28 stack bytes, local+64, выходные PC, порядок событий, аргументы helpers,
ESP/ret и сохранность nonvolatile registers. COM результаты — входы платформы;
teams/stageScan — наблюдения реальных внутренних контрольных точек.

Первый диагностический корпус дал 2 002 случая на проход и совпал с Swift,
но не вызвал ни одного конструктора: Object[0] имеет ID50 и входы обходили
split restoration через оригинальное исключение. Эти результаты не были
приняты как достаточная проверка всего обработчика. Расширенный корпус явно
включает `458428=1` для этого пути, отдельный gate mode4 и числовые контроли.

его результат с полным происхождением заново воспроизведён в обоих захватах.

окно приложения и чистая macOS этим запуском не проверены.

```sh

uv run tools/oracle_match_round.py --control
uv run tools/oracle_match_round.py --accept
swift test --package-path native --filter OriginalMatchRoundTests

```

Далее нужны настоящие паузные render helpers и путь menu `4229cc→429730`,
а также соединение с игровыми проходами после `41e339`. Ранние playback/camera,
файловый lifecycle, animated loading и остальные startup/CRT связи остаются
задачами карты. Practice, полная Windows-игра и чистая macOS этим этапом
не проверяются.
