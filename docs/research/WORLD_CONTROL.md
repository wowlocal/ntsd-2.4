# R02.1 / R04 / R05 — полный проход управления World

Эталон: NTSD 2.4 EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.

[OriginalWorldControl](../../native/Sources/NTSDCore/OriginalWorldControl.swift)
переносит весь `41e339..41e634`: управление активными слотами через настоящий
общий [Actor control](ACTOR_CONTROL.md), телепортации и превращения. Это
очередная стадия собственного матча, ещё не полный такт и не игровой UI.

## Правила и порядок

| Исходные инструкции | Перенесённое поведение |
| --- | --- |
| `41e339..41e364`, `41e61a..41e62e` | 400 слотов по возрастанию; любой ненулевой activity; `413080(450b90,451160)` |
| `41e364..41e3c6` | Состояния400/401 при `450bd8==0` вызывают `403270(slot,1/2)` |
| `403270..4034d3`, `4034e0..4034ea` | Полный выбор цели, перемещение и обнуление скоростей |
| `41e3c6..41e3fe` | Состояние500: кадр0 при `Actor+33c==-1` либо `Actor+324>-1` |
| `41e3fe..41e494` | Состояние501: первый Object с sourceID=`Actor+33c`, сохранение прежнего ID в324, замена368, кадр0 |
| `41e494..41e61a` | Все живые активные связанные Actor с owner2f4=текущему слоту получают новый Object; кадр212 при integer y<0, иначе0 |

Состояние перечитывается после каждого блока. Переход500→frame0 может сразу
войти в501, если такое состояние определено у кадра0. Привязка Object также
перечитывается после изменения. Поиск идёт по исходному ID, но сохраняется
ordinal конкретной записи: повторяющиеся ID не объединяются. Нет проверки
имени персонажа или отдельного Swift-обработчика его превращения.

Цикл связанных объектов включает самого бойца, если его owner равен текущему
слоту. Уже посещённые слоты получают новую привязку без повторного управления;
последующие управляются уже с новым Object/кадром. Пять развёрнутых исходных
проверок внутри80 итераций сохранены как эквивалентный проход0..<400.
World-таблица допускает несколько ссылок на одну Actor-аллокацию; нативный
проход сохраняет эту связь и последовательные записи, не копирует Actor по слоту.

Телепортация1 выбирает ближайшего живого активного противника типа0 с
манхэттенской дистанцией строго меньше10000. Телепортация2 выбирает самого
далёкого живого активного союзника типа0, начиная с лучшей дистанции−1.
Сам текущий слот исключён; другой слот с той же Actor-ссылкой не исключён.
При равенстве остаётся первая цель. Вычитания, abs(Int32.min) и сложение
дистанции сохраняют знаковое32-битное переполнение.

При найденной цели integer y=0, z=target.z+1, x=target.x±120 либо±60.
Нулевой facing выбирает минус, любой ненулевой — плюс. Binary64-координаты
получаются из этих целых. При отсутствии цели x/z и их дробные значения
сохраняются; обнуляются y и все три скорости. Кадр/facing/wait не меняются.
Прочие kind helper возвращают без записей; caller вызывает только1/2.

Нативный проход фиксирует pool/globals только после успеха всей стадии.
Внешний наблюдатель обязан буферизовать события до принятия полного такта.
Это гарантия обработки пока неподдержанных путей, не правило Windows-игры.

## Проверки

[oracle_world_control.py](../../tools/oracle_world_control.py) исполняет весь
caller и настоящие413080/403270/abs/RNG/sound helpers в1491 синтетическом
сценарии. Actor и World создаются исходными конструкторами над a5/ramp;
400 указателей, активность, четыре Object, Frame и globals заданы явно.
Конструкторский memset остаётся ранее объявленной границей. В игровом участке
нет подменённых функций. Проверяются границы памяти, маски чтений и каждый
вложенный возврат с его стеком и сохраняемыми регистрами.

Корпус включает порог10000, Int32 min/max и переполнение суммы, фильтры
HP/type/team/activity, разные ненулевые facing, равные и различные расстояния,
alias, отсутствующие и повторные ID, нулевой/отрицательный count, состояния
500/501 и повторное чтение кадра, ввод перед dispatch, все400 активных слотов,
связанных бойцов до и после текущего и порядок RNG→два звука.
Сравниваются SHA всех424408 байт World/400 Actor и их масок, всех46144 байт
globals и упорядоченные события. Эти входы не выдаются за исходные DAT или
естественные последовательности полного матча.

Первое сравнение всех1491 случаев прошло за1.093с (release build91.87с).
Исходный корпус содержит45461 вложенный возврат и949 уникальных выполненных
инструкций. Совпали SHA632792328 байт pool и стольких же элементов маски,
68800704 байт globals; события RNG→sound→sound совпали в своём сценарии.
Release NTSDNative собран за33.99с. Отдельная проверка отката требует ошибки
на втором Actor после завершившегося управления первым и расхода RNG.

Вторая проверка продолжает собственный [MATCH_LAUNCH](MATCH_LAUNCH.md):
нативная цепочка заново создаёт и проверяет меню, каталог, выбор участников,
District, музыку и recording, достигает41e339 и вызывает OriginalWorldControl.
Ожидаемые снимки не становятся входами движка. Сравниваются полный pool,
globals, ранние ресурсы/CRT, saved settings, replay pointers/полный буфер,
101 BG, все854 bitmap, музыка и освобождённые ресурсы до и после управления,
а также оба Actor сразу после413080. В этих первых естественных входах нет
удерживаемых кнопок; полное состояние после управления остаётся прежним.

Источник — два ранее снятых GAMEPLAY_ENTRY, каждый после воспроизведения
своего полного закреплённого MATCH_LAUNCH на том же CPU/стеке.
[accept_gameplay_control.py](../../tools/accept_gameplay_control.py) проверяет
SHA/размер raw, все внутренние blobs и родительский fixture, выполняет Native
и лишь затем публикует новый корпус. Исходные evidence/fixtures не меняются.
Внутри lossless capture сохранена следующая секция physics; здесь она явно
**не сравнивается нативно**. Остановка нативного сравнения —41e634, а не41eed1.
Промежуточные checkpoints префикса Actor остаются исходными наблюдениями;
эта проверка сравнивает их конечные control-return и полные World-состояния.

Оба сравнения собственных запусков прошли за35.590с; вместе с сохранёнными
секциями MATCH_LAUNCH они проверили50762 записи /454920452 байта состояния
с масками,902 helper returns и54 полных checkpoints. Само новое продолжение
содержит40 helper returns и4 Actor control-return, по два на запуск.
Отчёты: [синтетический](../evidence/world-control.json),
[собственный a5](../evidence/gameplay-control.json),
[собственный ramp](../evidence/gameplay-control-control.json).
SHA всех109 прежних fixtures сохранены; raw/packed SHA, размер и полное
распакованное содержимое всех трёх новых корпусов проверены независимо.
Сохранённые корпуса, оба отката и прежние ActorInput/ActorControl/MATCH_LAUNCH
прошли вместе:11 XCTest/96.950с, release build93.61с. Следовательно проверены
и новые packed artifacts, а не только raw файлы перед публикацией.

```sh
uv run tools/oracle_world_control.py
uv run tools/oracle_world_control.py --accept
python3 tools/accept_gameplay_control.py
swift test --package-path native -c release --filter 'Original(WorldControl|GameplayControl|ActorControl|ActorInput|MatchLaunch)Tests'
```

Следом — полная физика40e490 и окружающий проход41e634..41eed1 на собственном
состоянии, затем контакты, связанные объекты, камера/вывод/планировщик и возврат
всего такта. Начальные скорости0.1 и наблюдённый первый landing frame219
сохраняются; Practice с обнулёнными скоростями не заменяет этот путь.
UI приложения, законченный матч, реальный Windows-эталон и чистая macOS открыты.

Продолжение: [ACTOR_PHYSICS](ACTOR_PHYSICS.md) и [WORLD_PHYSICS](WORLD_PHYSICS.md)
теперь переносят обе эти стадии и нативно сравнивают оба собственных запуска
до41eed1. Прежний control-only corpus/check сохраняет остановку41e634;
новые physics fixtures сравнивают обе секции. Далее исходный Z/contact и весь такт.
