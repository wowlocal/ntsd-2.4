# R02.1 — родительский загрузчик каталога

Эталон EXE SHA-256:
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Продолжение [BOOTSTRAP.md](BOOTSTRAP.md). Восстановлен родительский проход
`4122f0..4127fb`: встроенные записи, чтение реестра, счётчики, порядок обращений
к дочерним загрузчикам. **Содержимое Object/BG/Stage/bitmap здесь не загружается.**
R02.1 и R03.1 остаются открытыми; этот результат ещё не подключён к практике.

## Правила родительского прохода

| Участок EXE | Восстановленное поведение |
| --- | --- |
| `41233b..4124f3` | Разреженные поля фона 99: width=2400, z=350/470, `+14=37`, `+18=9`, имя Lee On Road. Четыре запроса bitmap размером 0x1f50: shadow1, back99_1, back99_2, back99_3; конструктор `43ee50(64, name, 0)` |
| `4124f9..41251c` | Только строка Random в имени фона 100; остальные байты не считать нулевыми или определёнными |
| `412529..412543` | NUL-копирование имени файла, обнуление счётчиков объектов и фонов |
| `41256f..4125c6` | Чтение внешнего токена, добавление суммы `signedByte(token[i]) * i` к `44f620`, с переполнением dword |
| `4125cc..4126e0` | Внутри `<object>` реагирует на `id:` до `<object_end>`. Формат следующего чтения — `%d %s %d %s %s`. Два слова-подписи не проверяются |
| `41265b..4126a8` | Loading progress → аллокация 0x25360 → `40ef70(id,type,path,surface)` → запись возвращённого указателя в текущий слот → увеличение счётчика |
| `4126e6..4127ad` | Внутри `<background>` до `<background_end>`: `id:` и `%d %s %s`, затем `40c160(ordinal,id,path)` и увеличение счётчика |
| `4127c2..4127fb` | Закрытие реестра, вызов стадийного загрузчика `40c910`, возврат указателя каталога, `ret 8` |

Записи добавляются **в порядке чтения**, повторяющиеся ID не объединяются.
Порядковые индексы продолжаются через повторные секции. Исходный реестр содержит
137 объектов и 17 фонов. Первая запись — ID 50; загрузочный пул использует
именно её порядковый индекс 0. Исходные ID фонов идут `0,1,4,2,3,5,...,16`;
индекс массива нельзя заменять ID. Это основа общего реестра R06.1, без условий
по именам персонажей.

У этого прохода нет обработки комментария до конца строки. Нераспознанный токен
пропускается; последующие токены продолжают участвовать в обычном разборе.
`<file_editing>`, путь `data\\nothing.txt` и `<file_editing_end>` из исходного файла
не вызывают здесь отдельного загрузчика, но входят в родительскую контрольную сумму.

Контрольная сумма меняется **только на внешнем проходе** этой функции. Внутренние
строки объектов/фонов он сам не суммирует; вызванные загрузчики отдельно меняют
тот же global. `parentChecksum` в Swift поэтому не является контрольной суммой
загруженной игры.

После неудачного внешнего `%s` исходные инструкции используют старое содержимое
буфера. При объявленном ниже контракте stdio завершающий пробел даёт дополнительную
внешнюю обработку `<background_end>` после внутренней секции. Для исходного файла
родительский вклад равен 57858; без завершающих пробелов — 45922. Разница 11936 —
вклад этого токена. Это D с подменённым stdio, **не отдельная проверка MSVCR80/W**.

## Исполнение и границы доказательства

[oracle_catalog.py](../../tools/oracle_catalog.py) выполняет оригинальную функцию
от входа до возврата, включая SEH-пролог/эпилог и проверку security cookie.
Функция loading progress `4242e0` также исполняется: постоянный `timeGetTime=100`
выбирает ветку ожидания; `Sleep(5)` не задерживает стенд. Графическая ветка progress
этим не проверяется.

Явные границы:

- `fopen/fclose/feof/fscanf`: неизменяемый виртуальный поток, text-mode CRLF,
  ASCII-пробелы C locale, `%s` и знаковый `%d` в диапазоне Int32. Настоящий MSVCR80
  не исполняется. Точность его overflow/locale и всех случаев EOF ещё открыта.
- `4450ac`: успешные ненулевые токены аллокаций; их размер, место вызова и порядок
  проверяются. Тела выделенных Object/bitmap непрозрачны; отказы памяти не проверены.
- `43ee50`: сохраняются аргументы конструктора bitmap, возвращается `this`;
  устройство и память изображения не создаются.
- `40ef70`: сохраняются ID/type/path/surface и возвращается `this`, без записей
  дочернего загрузчика. `40c160`: сохраняются ordinal/id/path, без загрузки фона.
- `40c910`: проверяется вызов после закрытия реестра, без загрузки стадий.

Стенд не заменяет эти дочерние функции выдуманными заголовками. Их побочные эффекты,
включая изменения контрольной суммы, отсутствуют и явно исключены из сравнения.
Следующий этап должен выполнять сами загрузчики.

Отображены только страницы родительских областей каталога; отверстие стадий и
обычные записи фонов не объявляются загруженными. Любой доступ родителя за пределы
четырёх заявленных областей останавливает стенд. Каждое чтение инструкциями внутри
них требует уже установленной маски записи. Все нетронутые байты сравниваются
с исходным шаблоном. Это не дамп всех 81 МБ каталога.

## Нативный перенос и сравнение

[OriginalCatalogRegistry](../../native/Sources/NTSDCore/OriginalCatalogRegistry.swift)
сохраняет упорядоченные запросы дочерней загрузки, родительскую сумму и четыре
области `OriginalStateRecord`: таблица 500 Object*, фоны 99/100 и хвост счётчиков/
имени файла. Остальные области остаются задачей дочерних загрузчиков.

В канонических записях только подтверждённые указатели заменяются непустыми
ссылками по порядковому номеру: Object* → индекс запроса объекта, bitmap* → индекс
одного из четырёх запросов bitmap. Ноль означает существующий объект/bitmap 0.
Проверяющий адаптер предварительно требует совпадения исходного ненулевого адреса
и маски инициализации. Непрозрачные байты не нормализуются.

12 случаев: шесть входных потоков × два размещения указателей/шаблона памяти.
Во втором размещении адреса аллокаций идут в обратном порядке. Проверены:

- весь исходный реестр с CRLF и его вариант без завершающих пробелов;
- повторные секции/ID, произвольные подписи, крайние Int32;
- числовые префиксы без пробела перед следующей строковой конверсией, байты
  выше 127 в контрольной сумме, её переполнение и имя файла длиной 31 байт;
- пустые секции;
- все 500 мест таблицы объектов и 99 фоновых запросов перед встроенными слотами.

Совпали **48 записей, 83 232 байта и маски инициализации**, 3446 упорядоченных
запросов, внешние токены и контрольная сумма. Принятый отчёт и хеши:
[catalog-registry.json](../evidence/catalog-registry.json). Сравнение реализовано
в development-only `NTSDReferenceChecks`; приложение не зависит от этого target.

Нативный разборщик явно отклоняет неполные секции/числовые поля, переполнение
Int32, NUL/DOS EOF, длинные строки и выход за проверенные границы таблиц.
Общий scratch и путь объекта ограничены 199 байтами + NUL; путь фона — 179 + NUL,
поскольку дальше лежит security cookie. Это границы нашего проверенного домена,
**не добавленные правила оригинальной игры**. В частности, лимит 99 фонов пока
исключает неисследованное перекрытие встроенных слотов, а не доказывает отказ EXE.

```bash
uv run tools/oracle_catalog.py
swift test --package-path native
```

`--capture-only` записывает лишь непринятый корпус в `build/original`; основной
режим обновляет evidence/автономную фикстуру только после сравнения с Swift.
Исходные файлы не изменяются. SwiftPM-команды запускать последовательно.

## Продолжение

Object `40ef70` уже выполнен отдельно с настоящими конструкторами, заголовками
и последовательным чтением объявленных целых файлов: [OBJECT_LOADER.md](OBJECT_LOADER.md).
Следующее — BG `40c160` и Stage `40c910`. Нужно восстановить и подключить
побочные эффекты дочерних загрузчиков к вызовам
родителя, включая общий звуковой реестр и checksum. Только после этого можно
подменять нынешнюю синтетическую загрузку широкого такта реальным каталогом.
Инициализация выбранного матча также остаётся отдельной открытой задачей R02.1.
