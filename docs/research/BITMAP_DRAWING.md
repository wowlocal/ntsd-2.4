# R13/R02.1 — общая отрисовка bitmap и обрезка прямоугольников

Эталон: исходный EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Исполняются весь43f010..43f2fe (ret24),43ef70..43f000 и43ee50..43ef41.
Граница устройства — настоящий запрос Blt через COM vtable+14. DirectDraw,
пиксели, драйвер и оконный вывод не исполняются этим стендом.

Это зависимость меню431d10 и остальных bitmap callers. Ранее43f010 был границей
целого вызова; теперь исследуется его тело. Новый корпус имеет явно заданные
входы функции и **не** заявляет непрерывный первый вход из загрузки/меню.
Существующие загрузочные, музыкальные и меню-корпуса остаются неизменными.

## Вход и порядок

ECX указывает на wrapper1f50. Шесть аргументов: x, y, frame, color-key flag,
horizontal-mirror flag, destination surface. Оба флага проверяются на любое
ненулевое UInt32. Viewport берётся из44d78c/44d790. Все координаты и размеры
обрабатываются как Int32, с исходным32-bit wrap при сложении и вычитании.

При mirror!=0 сначала обнуляются все100 байт DDBLTFX, затем пишутся size100
и flags2. Этот буфер не создаётся только после успешной обрезки.

Если wrapper+0c==0 **или frame<0**, вычисляются прямоугольники целого изображения:
source=(0,0,width,height), destination=(x,y,x+width,y+height), где width/height
берутся из+4/+8. После43ef70 успешная ветвь вызывает Blt.

Затем, независимо от видимости/результата первого Blt, **повторно** читается+0c.
Если signed frame>=count, функция возвращает frame в EAX. Иначе она читает
прямоугольник кадра в порядке x,width,y,height из массивов+10/+fb0/+7e0/+1780,
обрезает и может выполнить второй Blt. Нет раннего return после целой картинки.

Смещение4*frame вычисляется с32-bit wrap. Отрицательные и большие положительные
индексы могут адресовать другие слова того же wrapper. Проверка frame<count
не является проверкой0..<500. Например frame=-1/count0 читает x из+0c и может
рисовать дважды; frame=0x40000000/countInt32.max адресует index0.
Стенд отдельно останавливается перед чтением, выходящим из предоставленного
wrapper: отображённый guard/device arena не должен делать такой доступ допустимым.

## Обрезка43ef70

Видимость отвергается, только если обе горизонтальные координаты строго<0,
обе строго>viewportWidth, обе вертикальные строго<0 или обе строго>viewportHeight.
Касание границы не отбрасывается. Нулевые и инвертированные прямоугольники,
отрицательный viewport и переполненные суммы не нормализуются заранее.

Для принятого прямоугольника порядок изменений: left,top,right,bottom.
Отрицательная destination left/top переносится на0, с соответствующим сдвигом
source left/top. Превышение правой/нижней границы уменьшает source right/bottom
и ставит destination right/bottom в размер viewport.

Для кадра при mirror!=0 после обрезки повторно читаются исходные x и width:
sourceLeft=2*originalX-clippedSourceRight+originalWidth;
sourceRight=originalWidth-(clippedSourceLeft-originalX)+originalX, всё с wrap.
Для целого изображения этой коррекции **нет**: отражается уже обрезанный source.

## Blt и возврат

Flags=01000000 | (colorKey!=0 ? 8000 :0) | (mirror!=0 ?800 :0).
Effects pointer null при mirror0, иначе указывает на указанные100 байт.
Null source surface передаётся устройству; wrapper не пропускается по этому
условию. HRESULT не вызывает retry, release или пропуск второго рисования.
После кадрового Blt EAX содержит его HRESULT; при отвергнутой обрезке кадра —0.

Null target останавливается перед чтением vtable, с исходным частичным порядком:
в whole ветви target читается **до** wrapper surface, в frame ветви — после.
Нативная граница сообщает ошибку, не подставляя успешный возврат. Уже выданные
platform requests принадлежат вызывающей стороне и не откатываются.

## Инициализация и представление указателей

43ee50 задаёт только surface/dimensions. Поле+0c и массивы остаются в исходном
allocator backing. Поэтому отрисовка может читать байты с defined=false.
`OriginalBitmapDrawing` получает этот backing явно и сообщает порядок чтений,
значения и маски; она не изменяет маски и не присваивает неизвестным полям0.
Общий строгий `OriginalStateRecord.integer` не изменяется.

Wrapper surface+0 хранится в нативных loaders как1/0. При чтении как числового
поля (например x при frame=-4) требуется исходный opaque surface token из
объявленной привязки. Нельзя использовать нормализованную1 как координату или
нормализовать остальные слова по сходству с указателями.

Данные allocator boundary не доказывают, какие байты имел реальный Windows
heap при запуске. Ранний startup и этот источник поведения остаются открытыми.
После предыдущего menu-resources corpus указатели4511a0/451178 всё ещё0,
поэтому следующие реальные draws431d10 требуют восстановления ранней загрузки;
замена этих указателей синтетическими успешными ресурсами не решает provenance.

## Корпус и проверка

Свежий EXE-корпус содержит3971 случай,96 наборов входной памяти и76 реальных
конструкторов. Использованы34 исходных embedded DIB:11 ресурсов меню,10 UI
первой загрузки и13 MENU_BACK. Все DIB bytes/SHA и размеры сохраняются.
Два allocator backing — A5 и ramp; дополнительно явно заданные метаданные,
не выдаваемые за выход DAT loader.

Покрыты границы обрезки и целого изображения, частичное отражение, signed
и unsigned границы, wrapped/negative indices, missing surface/SetColorKey
failures, нулевой source, оба HRESULT при двойном рисовании и сохранность памяти.
Исходное исполнение записало21475 чтений (9055 undefined),3330 возвратов clip,
2297 Blt и198 случаев двойного рисования.18 выходов за wrapper и2 null-target
случая заканчиваются **перед** недопустимой инструкцией.

Сравниваются все before/after rectangles каждого clip, порядок bitmap reads,
все аргументы и100 bytes effects каждого Blt, реальные EAX/ret24/nonvolatile
registers и неизменность полных bitmap/globals. Независимое release-сравнение
с Swift прошло:8038 полных записей /215838896 байт и масок. После этого принят
[новый fixture](../evidence/bitmap-drawing.json). XCTest прошёл без ошибок
за4.510s, release-сборка NTSDNative — за2.28s. Все18 прежних fixture hashes
сохранились; SHA нового raw corpus и packed fixture проверены. Оконный запуск
и конечное изображение этим не проверены.

Первое сравнение обнаружило использование нормализованной1 вместо исходного
surface token в координате при frame=-4. Исправлена нативная привязка этого
единственного слова перед арифметикой; expected snapshots и исходный корпус
не изменялись. Повторное сравнение прошло для всех3971 случаев.

```sh
uv run tools/oracle_bitmap_drawing.py
uv run tools/oracle_bitmap_drawing.py --accept
swift test --package-path native --filter OriginalBitmapDrawingTests
swift build --package-path native -c release --product NTSDNative
```

Команды SwiftPM последовательны. Fixtures принимаются только после успешного
независимого сравнения. Дальше — pixel/device backend и соединение с реальным
menu431d10, восстановив фон423840, ресурсы раннего startup и остальные helpers.
