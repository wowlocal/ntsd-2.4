# Экран выбора режима из собственного startup

R02.1/R04/R15. Продолжение [MENU_STARTUP.md](MENU_STARTUP.md) от429e5a.
EXE SHA-256: `3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
MSVCR80 8.0.50727.6195 SHA-256: `c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.

Статус: оба свежих source corpus и их packed документы совпали с Native Core;
приняты два новых fixtures.
Обычный экран до ret16 не включает файловую ветвь Playback и включённую
информационную панель. UI приложения, пиксели, звук и полная игра остаются открытыми.

## Происхождение состояния

Первый431d10 продолжает настоящий429e5a на том же CPU, World и стеке после
ранних119 вызовов меню, загрузки всего каталога, local/control/replay/round,
музыки и11 menu constructors. Перед продолжением стенд заново сравнивает все
четыре закреплённых loading документа и полный startup, включая их blobs.
Первому экрану не подставляются Actor, globals или готовые bitmap.

Поздние входы429e5a — явно объявленные повторные caller probes. Они сохраняют
состояние между вызовами, но не исполняют весь внешний игровой цикл. Их
EDX=1/ECX=2 соответствуют4297db/de при пропуске и429e4e/57 после загрузки
ресурсов. Остальные caller constants: ESI=0, EBX=-1, EBP=&menu, EDI=World.
Нельзя оставлять volatile registers от предыдущего431d10 и называть это
настоящим входом следующего меню.

Native `MenuStartupReference.onReady` передаёт собственные проверенные
OriginalMatchPreparation, input context, CRT, music и menu resources. Новый
reference продолжает эти значения, а ожидаемые после-снимки использует только
для сравнения. Early bitmap принадлежат общей presentation memory; menu
bitmap и music сохраняются в своих владельцах. Очистка глобального указателя
сама по себе не освобождает старый wrapper.

## Строки, клавиши и мышь

Три literal copies и алгоритм byte−(index&3) общие с ранним экраном. Здесь
локальные строки начинаются при body ESP+28/+44/+78. Авторские highlights
копируют suffix через NUL в+ac, затем отдельно ставят NUL в+b6/+b8. Результат
сравнивается вместе с оставшимися байтами и defined mask всей локальной области.

Ссылки используют previous4513c4, а не ранний44d060. Базовая y=45757c+491
с исходным Int32 overflow. Website hover: x>591, mouseY>y+30 и
(mouseY<y+60 или45757c=0). Первый автор:611<x<686 и y<mouseY<y+20;
второй: x>692 с той же y-проверкой. При previous=0/held=1 код очищает held,
вызывает401a30, Sleep300 и ShellExecute. Стенд лишь записывает OS-запросы.

`OriginalKeyName` переносит весь422b00..422f59. Исходные названия клавиш
не заменяются системными строками macOS. Helper сначала пишет `none`/8,
затем выбранное имя и поправку x, сохраняя переписанные хвосты. A..Z/0..9
имеют поправку0; Keypad0..9 и пять keypad operators —15. Остальные имена,
знаки пунктуации и ширины следуют исходным ветвям; неизвестный Int32 даёт none/8.

При положительном4513c0 рисуется frame7 bitmap45117c в(5,39), затем четыре
колонки по семь клавиш. Config=44fb74+80*seat+4*button. Text position:
x=130+108*seat−adjustment, y=93+20*button; цветаFFFFFF/652512. Только после
всех28 подписей таймер уменьшается. Width scratch перекрывает прежний menu local.

Курсор использует min(mouseX,775), min(wrapped(mouseY+2),535) без нижнего
ограничения. Щелчок held=1 внутри223≤x<574 и offset+194<y<offset+432
очищает held и ставит4513c0=450. Последняя запись4513c4 копирует уже изменённый
held. Поэтому подсказка появляется со следующего прохода и живёт450 проходов.

## Проверяемая область и воспроизведение

Каждый корпус содержит632 случая: первый собственный экран,
idle и последовательное появление подсказки, все8 highlights с пятью network
bytes, комбинированные команды и Int32-пределы, все13 фонов, все256 key codes
и четыре внешних Int32 значения, края URL/подсказки, held/previous и GetDC results.
Первый вариант использует A5 backing, контроль — ramp и обратные Actor addresses.
Финальное VS-подтверждение даёт menu3; это ещё не выбранные персонажи.

Сравниваются World/все400 Actor/globals/context, early bitmap bytes/masks и
liveness, CRT, локальные704 bytes/masks, порядок запросов/read/clip/blit,
helper returns и настоящий ret16. Cookie и сохранённые регистры вне этих704
байт проверяет source ABI observer. Новые menu/music records не используются
экраном; source дополнительно проверяет их неизменность во всей серии.

Allocator/backing, таймер, GDI/DirectDraw/DirectSound и Shell/Sleep ответы
остаются явными платформенными входами. Настоящие graphics/text/key/input/
sound/release функции исполняются до этих границ. Native использует прежние
общие helpers; новых персонажных условий нет.

В собственном первом состоянии sound slot455610 остаётся0. Все25 вызовов
401a30 на проход исполняют реальный helper, но здесь не доходят до sound-buffer
COM methods: поздний контроль этого slot идёт уже после Quit с device=0.
Полные методы отдельно проверены в MODE_SELECTION; происхождение начального
m_ok.wav из WinMain43d0c4, реальный звук и его задержка этим соединением не доказаны.

В диагностике исправлены ошибки исследовательских наблюдателей: перекрытие
раннего SetColorKey token со старым catalog import, оставшийся Sleep import
и отсутствие EDX=1/ECX=2 при объявленных повторных caller entries. После
исправлений оба source корпуса заново исполнили всю предшествующую цепочку.
Native reference сначала пропускал return43f0d5 clipping helper; дизассемблирование
43f0d0 и43f20d подтвердило оба call sites. Исправлена проверка ABI, не Core
clipping и не ожидаемые snapshots. Старый диагностический корпус с неверным
caller ABI не принят. Новые packed документы проходят весь native parent и
все632 пробы каждый до записи fixtures; ожидаемые после-снимки не редактировались.

## Открытые продолжения

Первый собственный внешний возврат теперь продолжен и проверен в
[MENU_RETURN.md](MENU_RETURN.md): menu ret12 →41bc90 ret4 →early ret4,
включая вывод и424746/held clear. Следом остаётся полный следующий внешний
вход с phase/input/control и подтверждение выбора режима. Перечень ниже
сохраняет остальные границы этого экрана и адресные опоры дальнейшего переноса.

- Playback останавливается до43249c:431c70, GetOpenFileNameA,43e620 и43dfa0
  не заменены успешным результатом.
- Enabled423b00, worker/status2 children в данном связанном потоке остаются
  открытыми. Null panel не доказывает соответствия включённой панели.
- После429eb7 оригинал проходит общий эпилог42e0d2..42e0f9/ret12. Затем нужен
  полный следующий внешний вход; эти поздние probes его не исполняют.
  S уточняет собственную цепочку возвратов: настоящий call429730 расположен
  в4229dd, return PC —4229e2. Затем условный network notice4229e2..422a5c,
  volume4028a0/present43e940, menu0 timer reset и422a95..422ab8/ret4. Caller
  424746 только после этого очищает held457580 и идёт в ранний эпилог4287de.
  Следующий этап должен закрыть эти возвраты на собственном стеке, а не
  перескочить прямо в новый character-selection caller.
- Menu3 сбрасывает8 status/choice/parameter triples и начинает character
  selection через menu1. Mode1 назначает team1 первым20 Actor, mode4 — двум
  группам первых8 и10..17. Обычный42a140 проверяет team всех400 Actor, затем
  рисует CHARMENU. Это пока статический разбор429f09..42a1ea, следующий этап.
- S для следующего этапа: правая навигация42a651..42a704 читает Actor+d0 и
  отдельный seat latch451268. Она перебирает registry ordinals, пропуская
  Object type!=0. Для signed sourceID/10, усечённого к нулю, группы3 и5
  доступны только при458428==1 (42a69e..42a6c6). Это исходное ограничение
  данных, а не основание вводить отдельные обработчики персонажей. Здесь
  исследован только этот путь навигации; остальные ветви ещё нужно сверить.
- S: random roster42b660..42b720 исключает все8 выбранных ordinals и требует
  type0/sourceID<30, затем вызывает общий417170 с bound=candidate count.
  Выбранная запись сразу связывается с Actor+368. Следует использовать общий
  механизм кандидатов/RNG, сохранив его живое чтение после каждого выбора.
- Меню выбора персонажей/арены нужно соединить с общей подготовкой матча,
  затем с полным игровым тактом. Windows output/latency, приложение и чистая
  macOS остаются обязательными проверками полной цели.
