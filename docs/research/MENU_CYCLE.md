**Проверено D против Native Core.** Оба свежих исходных прохода и оба packed
документа совпали, приняты два fixtures. Повторный пролог соединён с прежним

music/resources/mode/output. Следующий character-selection dispatcher и
оконное приложение остаются открытыми.

## Проверяемый переход

После собственного первого полного ret4 остаётся World2, phase450b90=1,
menu44d020=10, выбранный mode451160=0 и живые загруженные ресурсы. Внешний
caller вновь вызывает4246b0; он сам выбирает41bc90. Стенд предоставляет только
внешний ABI и объявленные клавиатурные байты, не восстанавливает внутренний
стек и не задаёт Actor/menu/phase из ожидаемых снимков.

Следующий41bc90 должен пройти собственный пролог, пропустить уже завершённую
загрузку, выполнить local/control/received/replay/round и обычный429730.
Первые три вызова каждого корпуса проходят экран режимов и все внешние возвраты.
Четвёртый останавливается в429e5a перед dispatch выбранного menu3. Сам
character-selection dispatcher429f09 и экран участников этим corpus пока
не исполняются; их предстоит продолжить на полученном состоянии.

## Последовательность входов

Проверенный сценарий использует первое место и его собственные status450b4c,
config44fb20+80*status и attack key config+20 из загруженного control.txt.
Стенд записывает только acquired keyboard byte455378+key:100 нажатие,
117 отпускание. Это граница уже полученного OS-ввода; WndProc/keyboard polling
и физическая задержка устройства здесь не воспроизводятся.

1. Нейтральный повторный вызов: phase1→0, menu10.
2. Нажатие перед следующим вызовом: phase0→1; новые keyboard bytes пока не
   копируются в текущие команды персонажа.
3. Удержание: phase1→0; общий input читает клавишу,431b70/4322ad должны
   подтвердить VS и получить menu3; исходные возвраты завершают этот вызов.
4. Отпускание перед phase0→1: полный внешний путь снова достигает429e5a,
   уже с собственным menu3. Не менять current Actor bytes вручную.

Последовательность фаз0/1/0/1 подтверждена исходным исполнением и Native D.
При четвёртом вызове acquired keyboard уже117, но current Actor+d1 ещё1:
отпускание станет текущей командой только в следующую phase0. Как и раньше,
mode screen рисует выбор
до обработки нажатия, а held457580 очищается только после41bc90/ret4.

## Доказательства и воспроизведение

```
uv run tools/oracle_menu_cycle.py
uv run tools/oracle_menu_cycle.py --control
uv run tools/oracle_menu_cycle.py --accept
swift test --package-path native -c release --filter OriginalMenuCycleTests
```

Генератор заново проверяет все pinned loading/startup документы и blobs,
первый mode case и первый полный menu-return case. Старые поздние mode/return
probes он не заменяет и не выдаёт за полные внешние вызовы. Все snapshots,
события, command buffers и ABI новых этапов сохраняются для будущего native
сравнения. Промежуточный `build/research/menu-cycle-partial*.json` служит
диагностике и не является принятым fixture. Source bindings COM/GDI/clock
переключаются между уже существующими наблюдателями; игровое состояние при
этом сохраняется.

Первая исходная диагностика заново воспроизвела всю загрузку/startup/первый
mode/return, затем остановилась в неактивном control observer: ранее
транслированный блок пересёк41c5e5 несмотря на emu_start(until). Новый observer
останавливается на этой инструкции явно, только при активном local-input
этапе. После исправления оба свежих прохода полностью воспроизвели родителей
и всю новую последовательность. Ожидаемое игровое состояние под native результат не менялось.

ModeScreenReference/MenuReturnReference теперь выделяют проверку случаев на
собственном состоянии в общий compareCases. Весь прежний набор операций и
assertions сохранён; старые два release OriginalMenuReturnTests прошли за25.443s
после сборки89.49s, включая полные mode/startup/loading native родители.
Это регрессия прежних областей, не результат новой последовательности.
