# R02.1 — собственный Start до входа в игровой проход

Статус: оба непрерывных исходных прохода и нативные сравнения восьми секций
завершены; новые fixtures приняты после успешного сравнения обоих корпусов.
Проверку всей игры, приложения и Windows этот этап не закрывает.

Эталон: исходный EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
CRT: закреплённый MSVCR80 8.0.50727.6195, SHA-256
`c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
Реальная привязка Windows assembly остаётся отдельной непроверенной границей.

## Задача и происхождение

[Стенд](../../tools/oracle_match_launch.py) продолжает
[MATCH_SELECTION](MATCH_SELECTION.md) на том же CPU, стеке, World, пуле
400 Actor, каталоге и графических ресурсах. Перед продолжением заново
исполняются и полностью сверяются закреплённые 50 кадров выбора матча,
34 кадра выбора персонажей и их прежние родители. Для MODE_SCREEN и
MENU_RETURN исходная цепочка повторяет первые собственные вызовы; Native
также заново проверяет все632 и95 прежних случаев соответственно. Нет восстановления
World или выбора из ожидаемого снимка, подстановки replay metadata либо RNG.

Собственный Start оставляет World=2/menu=1/mode=0, option=0, CPU=0,
District=0/random=0. Выбранные ordinals всех восьми мест:
17,21,24,38,39,32,22,36; активны и готовы только первые два. Остальные
привязки получены прежним общим случайным выбором. RNG index/counter=35/35,
музыка включена, последний выбранный путь — `bgm\boss2.wma`.

Нативное сравнение получает результат полного прежнего родителя через
`MatchSelectionReference.onLast`, сохраняя его состояние и ресурсы.
Ожидаемые снимки используются только для сравнений. Нативная сторона
вызывает общие `OriginalMatchPrelude`, `OriginalMatchPreparation`,
`OriginalMusicPlayback`, `OriginalReplayRecording`, `continueMenu`,
`OriginalMenuReturn` и `OriginalLoadedMatchCycle`.

## Непрерывный путь

| Граница | Что исполняется |
| --- | --- |
| `42cf8a..42d1ff` | Пролог Start, имя повтора, подтверждение |
| `42d1ff..42d6b6` | Реконструкция выбранных бойцов, позиции/RNG, команды, освобождение и загрузка слоёв арены |
| `42d6b6..42d6bb` | Настоящий вызов `4025b0 → 402020` с включённой музыкой |
| `42d6bb..42d6ed` | Реконструкция неактивных 20–399, сброс ввода `431c70` |
| `42d6ed..42d704` | Настоящий caller и полная инициализация записи `43d2c0`, включая `43d280` |
| `42d704..42e0d2` | Оставшееся меню с собственным confirmation=1/action=0 |
| `42e0d2..STOP` | Реальные вложенные возвраты меню, матча и внешнего диспетчера, вывод и очистка held |
| Следующий полный `4246b0` | Собственная фаза, ввод, запись первого пакета/контрольной суммы, исход раунда до `41e339` |

`41e339` — граница **перед** игровыми проходами. Полный первый игровой такт
и законченный матч этим переходом не считаются реализованными.

## Наблюдения первого диагностического прохода

Оба прохода a5/control воспроизвели всех родителей и четыре первые секции.
В control меняются backing Actor/World и порядок их адресов, а исходный каталог
и данные игры сохраняются. Это не другой набор игровых правил.

Оба диагностических четырёхсекционных префикса уже совпали с Native:
по 9682 записи / 54 487 682 байта и маски, всего 19 364 / 108 975 364.
Полные прежние нативные родители также проверяются, их счётчики сюда не входят.
Это отдельная диагностическая проверка префикса; полные результаты приведены ниже.

Пролог вызывает GetLocalTime и два настоящих sprintf в загруженной DLL на том
же CPU. Его четыре события: время, дата, имя файла, запрос подтверждения.
Исходный слот `455610` по-прежнему нулевой: звуковые COM-вызовы не достигнуты.
Отсутствующие пять ранних WinMain-загрузок звуков не заменены вручную.

Подготовка вызывает 17 освобождений слоёв и загрузку District с 15 bitmap.
Два выбранных Actor реконструируются, четыре RNG-вызова для x/z переводят
index/counter с35/35 на39/39. Перед музыкальным child этот курсор уже виден.
В хвосте реконструируются 380 неактивных мест 20–399, затем сбрасывается ввод.

Включённая музыка даёт 27 событий, пять полных helper returns, один вызов
закреплённого CRT formatter для graph.log и вторую retained wide-path allocation.
Форматирование graph.log использует прежнюю отдельную DLL-границу общего
стенда музыки; его нельзя объявлять исполнением в CPU всей игры.

Первый запуск остановился на входе `43d280`: новый guard стенда не включал
этот настоящий helper. Дизассемблирование подтверждает, что caller вызывает
его и при нулевом recording pointer; проверка нуля находится внутри helper.
Исправлен observer, без изменения Core-правил или ожидаемых снимков.
Также после музыкальной секции требуется вернуть IAT sprintf к прямому
DLL-вызову для общего observer вывода меню. Оба свежих прохода после этих
исправлений повторили всех родителей и завершили все восемь секций.

## Полное сравнение нового участка

Каждый из двух корпусов совпал с Native: **8 секций, 22 597 записей,
198 816 950 байтов с масками, 450 событий, 431 helper return и25 checkpoints**.
В сумме —16 секций /45 194 записи /397 633 900 байтов с масками,
900 событий /862 helper returns /50 checkpoints. Полные прежние родители
тоже проверяются, но их счётчики не включены повторно. Новые helper counts
охватывают launch/music/return; ABI local/received/recording следующего
внешнего входа дополнительно проверяется общим `MenuCycleReference`.

После собственной подготовки Naruto стоит в x=442/z=504, Sasuke — x=289/z=519,
y=0, команды10/11, HP500/500. Числа — результат исходной DAT/арены и RNG,
а не заданные позиции или правила конкретных персонажей.

`43d2c0` создаёт весь буфер записи из собственного состояния и сбрасывает
RNG counter39→0 при неизменном index39. `450b8c` сбрасывается с88 на0.
Имя при объявленном SYSTEMTIME: `20260909_123456_VS.lfr`.
После оставшегося меню полный внешний возврат имеет SP=`1000f42c`,
восстанавливает nonvolatile registers/SEH и очищает held по исходному порядку.
Этот возврат завершает Start-вход, уже посчитанный в MATCH_SELECTION;
его нельзя ещё раз считать новым внешним вызовом.

Следующий настоящий `4246b0` сам выбирает phase1. После локального ввода и
received-input исполняется `43db40` через caller`41d60e`, записывая десять
нулевых command bytes первого пакета. В `buffer+14b8` записывается checksum1000
из двух HP500; tick counter становится1. Вход заканчивается непосредственно
перед`41e339`, SP=`1000e9bc`, World2/menu0/mode0, RNG39/0. На два корпуса
приходятся **два новых внешних входа**, ещё без их полных возвратов.

Все байты/маски целого replay buffer сохраняются и сравниваются также после
вывода меню, пролога и каждой стадии нового ввода/записи/исхода раунда.
Ни один tracked undefined read в пяти собственных launch-секциях не допускается.
Старые безбуферные сравнения по умолчанию по-прежнему требуют пустую replay memory.

Отчёты: [a5](../evidence/match-launch.json),
[control](../evidence/match-launch-control.json). Оба raw и packed корпуса
содержат те же JSON-данные; дефляция не удаляет сравниваемые записи.

## Ресурсы и границы проверки

В состоянии матча теперь сохраняются десять ресурсов исходного интерфейса
`OriginalInitialInterfaceLoading`, полученных его собственным загрузчиком.
Раньше они сравнивались после загрузки, но не передавались вместе с World.
Новая проверка учитывает их наряду с каталогом и новыми слоями арены.

Снимки сохраняют World/400 Actor/globals, 101 BG, bitmap bytes/masks,
все прежние ранние ресурсы, CRT, music allocations и запись. Только известные
Actor/Object/BG/bitmap-ссылки нормализуются по соответствующим реестрам.
Нулевой non-null ordinal не превращается в null.

Граница calloc создаёт нулевой буфер `0x630e18` по адресу `72000020` и
регистрирует его в общей памяти input/replay. Настройки, имена, исходные ID
неактивных мест, музыка и RNG должны копироваться самим `43d2c0`.
После инициализации счётчик RNG обнуляется, индекс сохраняется.

OS time, COM/Win32/allocator results, bitmap surface и внешний caller ABI
остаются объявленными входами. Реальная клавиатура, пиксели, аудиовывод,
Windows, чистая macOS, подключение этой цепочки к UI и полный матч открыты.

## Воспроизведение

```sh
uv run tools/oracle_match_launch.py
uv run tools/oracle_match_launch.py --control
uv run tools/oracle_match_launch.py --accept
```

SwiftPM-команды запускать последовательно; не изменять Swift-входы во время
активной сборки или теста. `--accept` сначала проверяет оба новых корпуса
нативно, затем записывает оба fixture/отчёта. Прежние fixtures сохраняются.

Проверки этапа:

- Шесть прежних release XCTest (`OriginalMatchPreparationTests`,
  `OriginalReplayInitializationTests`, `OriginalMusicPlaybackTests`,
  `OriginalMatchSelectionTests`) прошли за87.819с, сборка97.16с.
- Два новых `OriginalMatchLaunchTests` прошли за36.288с (18.152/18.136),
  сборка91.75с. Всего восемь проверок за124.107с.
- Release `NTSDCatalogCheck`:93.36с/93.88с/57.65с; финальный `--accept`
  build0.18с. Два диагностических префикса, полный raw a5 и оба packed
  корпуса совпали. Release `NTSDNative` прошёл за2.81с.
- SHA всех104 прежних fixtures сохранены. Для обоих новых проверены
  raw/packed SHA и размеры, SHA/размер внутреннего DEFLATE и полное равенство
  распакованного JSON.106 pins: `build/research/match-launch-fixture-pins.json`.

Следующий участок начинает с собственного `41e339`, а не с данных старого
Practice/replay. Сначала весь проход активных400 мест `41e339..41e62e`
