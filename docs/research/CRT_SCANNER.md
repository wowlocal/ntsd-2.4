# R03.1 — числовое чтение Microsoft VC80

Эталон игры — EXE SHA-256
`3f7ac67c5890ef979ee24a6dae5528056e7f631725c292cf9cb0a928ebeff71c`.
Этот этап снимает ограничение Int32 при чтении десятичных полей. Нативный
сканер больше не отклоняет исходные большие литералы и сохраняет потребление
знака при неудачном преобразовании. Правило общее для Object/Frame/BG/Stage.

## Происхождение библиотеки и граница проверки

[oracle_crt.py](../../tools/oracle_crt.py) извлекает DLL из находящегося в
репозитории `downloads/vcredist_x86_2005sp1.exe`, не запуская установщик.
Git LFS хранит пакет с SHA-256
`8648c5fc29c44b9112fe52f9a33f80e7fc42d10f3b5b42b2121542a13e44adfd`.
Внешний CAB читается `bsdtar`, MSI — `olefile`, вложенный CAB — снова `bsdtar`.
Извлечённые файлы остаются в игнорируемом `build/original/crt`.

Библиотека **MSVCR80 8.0.50727.6195**, PE32, preferred base `78130000`, SHA-256
`c3ac989c8489a23bb96400b1856f5325ffc67e844f04651ea5d61bc20a991c6d`.
EXE запрашивает в своём manifest **8.0.50727.762**. В пакете есть политика
`policy.8.0.Microsoft.VC80.CRT`, перенаправляющая диапазон
`8.0.50727.42–8.0.50727.6195` на `8.0.50727.6195`;
SHA-256 policy manifest —
`e446fc3432a5d83eb96142ce40f4cc8ed417872539893ace445f7236ff4dd187`.
Это подтверждает применимость политики к запрошенной версии, **но не доказывает,
что именно эта DLL загружена конкретным запуском игры в Windows**. Проверка
Windows startup, активации assembly и исходной версии .762 остаётся открытой.

Стенд исполняет настоящий `fscanf` (`78175f0b`) → общий `_input_l`
(`7817b37d`), классификацию символов, арифметику, запись результата,
`_ungetc_nolock` (`781782b2`) и `_filbuf` (`781759a8`) до настоящих возвратов.
`_initptd` (`78132cf3`) сам инициализирует потоковую структуру на нулевом
backing, соответствующем вызывающему `_calloc_crt`. Исходные таблицы C locale
читаются из DLL. Скрипт не подставляет свой `atoi`, `strtol` или `%d`.

Явные границы:

- `_getptd` возвращает структуру после исполнения `_initptd`; TLS/Windows startup
  не выполняются. Необязательный поиск расширений через `GetModuleHandleA`
  возвращает отсутствие модуля.
- Блокировки представлены однопоточным проходом. `InterlockedIncrement` меняет
  указанный dword. Остальные непредусмотренные импорты останавливают стенд.
- FILE имеет read/buffer flags `9` и предоставленный буфер; `_read` получает
  уже подготовленные байты и возвращает 0 после их окончания. EOF-флаг,
  возврат `fscanf`, lookahead и возврат символа в поток формируют инструкции DLL.
  Преобразование CRLF/CTRL-Z, `_fmode`, открытие файлов и кодовые страницы ОС
  этим проходом не проверяются.
- Проверяются байты/маски всех восьми выходных слотов и защитные границы.
  Неудачное присваивание должно оставить backing `a5` нетронутым.

Ни DLL, ни Unicorn, ни исследовательский стенд не входят в зависимости приложения.

## Восстановленные целочисленные правила

Для `%d` и `%ld` в этой PE32-библиотеке используется один 32-битный накопитель:

```
value = value * 10 + digit       // modulo 2^32
if negative: value = -value     // modulo 2^32
store the four resulting bytes
```

Адреса: `7817be22` — `imul edi,edi,10`; `7817be56` — прибавление цифры;
`7817be8c` — `neg edi`; `7817bec7` — запись dword. В этой ветви нет saturation
или проверки диапазона. Нативный накопитель также не требует, чтобы текстовое
число помещалось в Int64.

| Вход | Полученный Int32 |
| --- | ---: |
| `2147483648` | -2147483648 |
| `4294967296` | 0 |
| `-6846518779` из kyubi.dat | 1743415813 |

Пробелы и необязательный знак потребляются до проверки наличия цифр.
`+nope` даёт 0 присваиваний и позицию 1; следующий читатель увидит `nope`.
Один знак в конце потока оставляет назначение нетронутым, устанавливает EOF
и возвращает -1. Нечисловой первый символ без знака остаётся в потоке.
После первого успешного присваивания в `%d %d` неудача второго не отменяет
первое: результат — 1. `errno` во всём принятом корпусе остаётся 0.

## Проверка и применение

[crt-integers.json](../evidence/crt-integers.json) закрепляет источники и хеши.
Из неизменённых 137 файлов реестра взят инвентарь **867 уникальных целочисленных
токенов**, включая **39 вне Int32**. Это инвентарь текста, а не утверждение,
что каждый токен передаётся `%d` на каждом пути исполнения игры.
Добавлены знаки без цифр, matching failure, суффиксы, NUL/старший байт,
границы 32/64 бит и 1024 цифры. Сочетания `%d`, `%ld`, `%d %d`, EOF и второго
числа дали **5364 случая / 16092 исполнения** при буферах 1, 7 и 4096 байт.
Все результаты, позиции, EOF и отсутствие записи при ошибке совпали с Swift.

Отдельный корпус [object-loader-msvcr80.json](../evidence/object-loader-msvcr80.json)
исполняет EXE целиком для **Pein → Naruto → Sasuke → числовой контроль**.
Все сканы, кроме побайтного `%c` декодера, выполняет настоящая DLL, включая
`%s`, составные форматы и `%lf`. С Swift совпали **817 определений кадров,
1600 конечных записей, 216480 байт/масок заголовков/bitmap, 26 bitmap**, общий
звук и checksum. Контроль содержит исходные большие литералы и повторный кадр
с ошибкой после знака. Три исходных объекта идут в порядке этого корпуса;
это не полная исходная последовательность реестра.

Таким образом, для встреченных здесь `%lf` проверены и биты, полученные DLL.
Общее округление/лексика `%lf` не восстановлены: например, исследовательский
вызов с `1e+` потребляет три байта и присваивает 1, тогда как прежняя регулярная
модель потребляет один. Не переносить эту непроверенную модель на новые ветви.

Старые корпуса Object и изолированных Frame сохранены со своими исходными
CRT-границами. Их 349 исключённых групп не удалены задним числом. Расширение
нативного `%d` само по себе ещё не доказывает корректность длинных имён,
указателей и непрерывного чтения остальных файлов.

```bash
git lfs pull --include=downloads/vcredist_x86_2005sp1.exe --exclude=""
uv run tools/oracle_crt.py
uv run tools/oracle_objects.py --crt-suite
swift test --package-path native
```

Оба инструмента принимают fixture/evidence после сравнения с Swift. SwiftPM
запускается последовательно. Полный исследовательский проход объектов:

```bash
uv run tools/oracle_objects.py --msvcr80 --all-registry
```

Он сохраняет повреждённые длинными именами sound pointers как
`opaqueSoundPointer`, не разыменовывает их и не выдаёт за путь звука.
Компактирование такого снимка для нативного сравнения явно запрещено до
восстановления сырого Frame storage. В частности, это следующий участок для
Kyubi; числовое переполнение больше не является его препятствием.

Первый полный проход завершился: **137 объектов, 15388 определений кадров,
54800 конечных записей, 808 bitmap-обёрток, 400 звуков**, Object-only checksum
**30847120**. Сохранены 15661 сырая область и маски; в отслеживаемых Object/heap
обращениях инструкций нет чтений до наблюдённой записи. Это не делает известными
все нетронутые байты. [Отчёт](../evidence/object-registry-research.json) явно имеет
`nativeCompared: false`; полный дамп (~597 MB) остаётся в `build/original`.
Прямой вызов 137 Object сохраняет общий кэш, но ещё не исполняет родителя,
BG/Stage или начало матча.

В 38 конечных кадрах семи файлов обнаружены непрозрачные указатели звука.
Например, Kyubi 325 хранит `0x00747361`, а Shikamaru 282 — `0x6e776f64` и
sound index -256: длинное имя затронуло оба соседних поля. В criminal2 143
индекс стал -65435. Кроме того, `4TK_ball.dat` использует **10 листов**, тогда
как нынешний нативный загрузчик разрешает девять. Следующий перенос должен
воспроизвести эти записи/перекрытия и их последующие использования без правки DAT.
